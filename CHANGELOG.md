# Changelog

Swarm is in pre-release. Version 0.0.1 is the first public version: it is for testing, and things may change between versions. This file records changes that matter to people installing Swarm.

## 0.0.1 (pre-release)

### Security

Found with a threat model of the whole application and a security review, then checked in the code.

- On the shared sending domain, only an instance admin can resume a warm-up that paused itself. Who paused it is now recorded instead of read from the reason text, which a publication admin could overwrite by pausing again; pausing an already-paused domain changes nothing. Migration `0069_review_fixes.sql`.
- Website code on this install's own domain and its DeBounce credits now need an explicit allow in Settings > Instance. Being an owner of a workspace no longer grants either, so a tenant can't gain them by promoting an instance admin's seat; workspaces an instance admin created stay allowed, and an instance admin is emailed when someone else changes their role.
- On an install with several workspaces, scripts a publication adds to its website run only on its own custom domain, unless the workspace belongs to an instance admin or an instance admin allows it under Settings > Instance > Code on websites. Saved code is kept, and the website settings say why it doesn't run.
- Removing a teammate also revokes the API keys they created and the apps they installed in that workspace, with audit entries. The API keys list shows who created each key.
- Export destination keys are sealed to their workspace and destination; older keys are re-sealed on the next save or run.
- An AI agent connected over MCP could change a scheduled post's content, subject, sender or audience after a person approved sending it. It can't any more: a person unschedules the post, and scheduling it again needs approval. Direct `/v2` calls with an API key are not affected.
- Creating or changing a feed source or a webhook endpoint through MCP now waits for approval in the default mode. A feed in send mode mails subscribers on its own, and a webhook endpoint receives subscriber data.
- On the install's shared sending domain, raising the pause thresholds for bounces and complaints, or resuming sending after it paused itself over a spike, now needs an instance admin. Every publication on the install sends from that domain.
- A deployed install with no sign-up setting saved now lets in only its first account and then needs invites, instead of letting anyone sign up. The installer always saves the setting, so this only affects installs made by hand.

From a second, deep threat model (security and privacy, 118 findings). These changes are checked by unit tests and the local browser tests, which run offline against stand-ins; none has been checked against a real provider or deployment yet.

- **SSO.** A workspace's identity provider signs in only people seated in that workspace (or new people through just-in-time seats); someone seated only elsewhere is refused and emailed. The provider's MFA claim no longer counts as the operator's own factor for factor changes, recovery codes or signing out everywhere, and an SSO session opens other workspaces only after the operator proves their own factor. Deleting, repointing or disabling a connection, or turning the SSO flag off, ends its sessions, and SSO sessions last at most 12 hours. Domain proof is re-checked after 24 hours and lapses after 7 days of failing. Migration `0085_sso_trust.sql`.
- **Standing feeds.** Creating or moving an API key, webhook endpoint or export destination needs a fresh factor of your own, and owners and admins are emailed. Each feed records who confirmed it and stops (shown as suspended) when that admin loses the role, its key or app is revoked, its publication is deleted or the plan drops; an admin can confirm it again. Endpoints created through `/v2` stay inactive until an admin confirms them. Migration `0086_feed_authority.sql`.
- **Sessions and roles.** A revoked session can't come back from a cached copy. Only owners grant, remove or demote the admin role. An API key works only while the admin behind it keeps the role, and invites from a demoted admin are withdrawn. Raising a seat's role is limited to 4 times a day, and the person is emailed every change. Instance admin settings need a factor of your own and fresh proof. Exports re-check the requester's role as they run, and admins can cancel them.
- **Footer links.** The Member Center link in every Broadcast footer now shows a masked summary and keeps cancel-at-period-end and keep one click away. The payment portal, PayPal cancellation, invoices, profile changes and turning tracking off need a fresh link emailed to the subscriber, who is also told about every change. Subscribers can turn older links off. Migration `0090_member_link_floor.sql`.
- **Checkout.** Paying with a typed address no longer activates or confirms anyone. A signed-out buyer becomes a pending subscriber who confirms by email, and the consent record names the checkout. Signed-in buyers see "Buying as …". Migration `0095_checkout_consent_source.sql`.
- **Public site.** A PDF sold as a Good is no longer served from its public media address. Media answers only on the media host and its own publication's site, and tracked links only on their own publication's link domain. Gift Pass claims no longer sign anyone in. Reader sessions can be signed out on every device and end after 90 days. Gift article links stop when the sharer loses access, after 50 reads, or when revoked. Website code no longer runs for signed-in readers or on gated text shown in full. Search is never cached and is limited per visitor.
- **Agents and Copilot.** A manual feed check no longer turns a stopped send-mode feed back on or schedules a post; resuming goes through the held update. Calls are held by their effect: adding subscribers, sending member events, changing status or replacing tags, widening a post's web visibility, and writes a live Flow listens for. An approval names its target and fails if the post's send fields change. API keys can be limited to the MCP server ("Who uses it"). Copilot hides subscriber addresses and names from the model by default. Optional settings require a second person to approve, or hold writes after an agent reads outside text. Migrations `0100_agent_holds.sql` to `0102_copilot_ceiling.sql`.
- **Webhooks and payments.** Stripe and PayPal event claims are scoped per account or Channel, stuck PayPal events are retried, and missed PayPal changes are reconciled every 5 minutes. PayPal verification is rate-limited per Channel. A Mailgun event that disagrees with the delivery record is ignored. Webhooks, Flows, feeds and exports can't target the install's own hosts. Migrations `0096` to `0099`.
- **Shared capacity.** Workspaces share the send, webhook, Flow and feed capacity fairly, and DeBounce single checks are budgeted per workspace.
- **Setup and releases.** The setup page asks you to approve the exact release (version, digest and key) before any step runs, and needs `RELEASE_MIN_VERSION`. Setup secrets expire after 8 hours idle, and the recovery kit is sealed under a passphrase you choose and downloads at most 3 times. Release builds need a clean tagged tree; signing is a separate `pnpm release:sign` with an encrypted key. Workers no longer answer on `workers.dev` or preview addresses, and a deploy with no environment can't replace production.
- **The vault.** A new internal worker, `swarm-vault`, is the only one that holds `FIELD_KEYS` and the provider keys of Channels and workspaces (own Stripe keys, PayPal, Shorthop, Copilot keys, export destination credentials, webhook and Flow signing secrets, TOTP and SSO secrets). It has no public address; api, capture, site and jobs reach it through service bindings, each through its own entrypoint with only its own operations, and it checks every request against the database and the caller's own session, key or token. Provider calls go through it to a fixed list of hosts. Sealed values are bound to their row, and a cron re-seals older values. When the vault is down, encrypted fields aren't shown and saving one returns an error. Bulk opens (exports, data requests) appear in the workspace audit log. The platform Stripe key and the DeBounce key are no longer held by capture or site. `pnpm swarm vault` shows its state and switches the sealed format once it's safe; `pnpm swarm doctor` reports re-seal progress. Migration `0150_vault.sql`.
- **Per-link keys.** Every kind of subscriber link (Member Center, confirm and leave, asks, data downloads, goods, checkout references, sponsor reports, previews, form stamps, join and signup journeys, bounce codes) has its own keyring instead of the one `MEMBER_KEYS`, and each worker holds only the keys it signs or checks with. Where a public worker only checks a link, the link is signed with Ed25519 and that worker holds the public key. New links name their publication or workspace, which is checked against the record. Erasure confirmations also carry a random value only the email holds. `pnpm swarm update` switches in two passes (every worker accepts the new links first), records the switch, and later removes `MEMBER_KEYS` from workers that no longer need it; links sent before keep working for their own lifetime, at most 90 days. Year-long sponsor report links end 90 days after the switch, and sponsors are emailed a new one. Migrations `0145` and `0146`.
- **Public queue.** capture and events can only queue to a new `swarm-<env>-public` queue, and the jobs worker accepts just "a publication changed" and a confirm-time email check there; anything else is refused and logged. Messages on every queue are checked against a schema, and a job never trusts ids or flags in a message over the stored rows.
- **Keys and secrets on your machine.** `pnpm swarm rotate-keys <KEYRING>` rotates any keyring (FIELD_KEYS values are re-encrypted in the background before the old key can go). `.swarm/<env>.secrets.json` is sealed under a passphrase you choose. CI installs pnpm through corepack with its hash checked.
- **Sign-in and tenancy, continued.** A per-publication role can only lower someone's access. Workspace audit logs record that a teammate signed in, not their network or browser; that detail is on their own Account activity page. New export destinations send subscribed readers without profile fields unless you choose more. Settings > Security has **Pause all outbound feeds**. SSO domains are re-checked daily (the jobs worker needs `DNS_RESOLVER`). Instance settings have a tamper-evident audit log with a dashboard view, and held website code stays off until it is allowed. The mail sent when an account adds its first factor has a "This wasn't me" link. Migrations `0110` to `0114`.
- **Webhooks, payments and capacity, continued.** Email checks on double opt-in forms run only after the person confirms. At most 4 webhook deliveries run at once per endpoint, workspaces share the per-second send rate, and a very large send on a shared install goes out in parts. Bulk email checks have a monthly budget per workspace (25,000 by default), and duplicated check messages no longer spend credits twice. Goods and order links no longer contain the buyer's address. Migrations `0115` to `0119` and `0140`.

### Privacy

- Each publication can turn off open tracking, click tracking (links then go straight to their address) and reader profiles (engagement scores and best-time sending) under **Sending & delivery > Tracking**. All three stay on after updating.
- Subscribers can choose "Don't track my opens and clicks" in their subscriber settings. Their recorded opens and clicks are deleted, and send report numbers stay the same.
- New **Settings > Privacy > Engagement history** (default 13 months; 6, 13, 24 or 36): after that, deliveries, opens, clicks and per-send address copies no longer name the person. Report counts and blocked addresses are kept, and unsubscribe links in emails older than the limit stop working. Migration `0063_tracking_choices.sql`.
- The inactive-reader cleanup no longer unsubscribes anyone while open tracking or reader profiles are off, or anyone who asked not to be tracked.
- Deleting your data from subscriber settings now asks you to confirm from your inbox, so someone holding a forwarded email can't erase you. Addresses Swarm can't email go to the Privacy Center for an admin to review. Migration `0064_rights_and_keys.sql`.
- On installs with several workspaces, one workspace's bounces and complaints no longer change another workspace's subscribers. Only hard bounces go on the Amazon SES account suppression list, and the installer now sets your SES account to keep only those; on older installs run `pnpm swarm` once with the AWS admin key, and `pnpm swarm doctor` tells you if it's still needed.
- Imported people who never confirm are deleted after 30 days, and attested imports leave a consent record saying who attested. A subscriber's copy of their data now includes network data and up to 25,000 rows per history, and admins can download the copy for addresses that can't receive email.
- Marking a known tracking tool (Google Analytics, Meta Pixel, TikTok, Hotjar and similar) as "Strictly necessary" on a website needs the owner's confirmation, which is recorded in the audit log. Migration `0065_site_code_rules.sql`.
- New guides: `docs/gdpr.md` for operators, and `docs/privacy-controls.md` for tracking and retention.
- An export to your own bucket that was paused or failing for more than 30 days never learned of erasures from that time, so erased people stayed in your copy. Erasures are now kept until every export destination of the publication has written them.
- **Delete subscriber** is not a full erasure, and the dashboard and the audience guide now say so and point to Settings → Privacy for a deletion request.
- The subprocessors page now lists PayPal, which receives buyers' addresses, and the product notes no longer claim a choice of EU data residency, which isn't built.
- The inactive-reader cleanup reads each person's own history over the whole period chosen, leaves alone readers whose opens can't be seen, and emails a notice 14 days before unsubscribing anyone, with a "Keep me subscribed" button. Migration `0105_sunset_notice.sql`.
- Unsubscribe links in emails older than the engagement-history limit keep working for 24 months more. Migration `0106_unsubscribe_refs.sql`.
- Erasure now also clears earlier requests' notes, errors and sealed addresses, metered reads and browser family, and the copy of a person's data covers every table that holds it. Erased-address markers are keyed with a secret that isn't in the database, and the request API's `emailHash` is now 12 characters. People whose request is declined or fails are told, and admins are reminded of failed requests. Migration `0107_privacy_markers.sql`.
- New **Settings > Privacy > People who left** (default 24 months; 12, 24, 36 or 60): names, fields, tags and activity of unsubscribed, bounced and complained people are then removed, keeping the address, status and consent records. A deleted publication's personal data is purged 60 days after deletion. Ended sessions, used sign-in codes and unaccepted invites are deleted after 30 days. Migration `0108_record_lifetimes.sql`.
- Signup checks with DeBounce are off by default, and a refused address gets the same answer as any signup unless the publisher turns on showing the result. On double opt-in forms an address goes to DeBounce only after the person confirms it ("Check signups once they confirm").
- New publications start with open tracking, click tracking and reader profiles off; turning them on says to get subscribers' consent first. Existing publications keep their settings. The inactive-reader cleanup never reads history older than the engagement-history limit.
- Paying subscribers can choose "Stop emails, keep my membership" in their subscriber settings. Migration `0115_member_emails_off.sql`.
- Anyone, subscriber or not, can ask a publication for a copy or deletion of their data from the "Your data" page linked in every website footer, confirmed by a single-use emailed link. Erasure of an address Swarm can't email always goes to admin review.
- Payment references kept after erasure are deleted after **Settings > Privacy > Keep payment records for** (6, 7, 8 or 10 years). The audit log has an age limit on every plan (1, 2, 3 or 5 years), and owners can remove a former teammate's details. A deleted publication's stored files are purged with its data, and its automations and webhooks stop. Consent records note the form version the server rendered, and the site the form was on next to what the server verified. Migrations `0116` and `0120` to `0124`.
- The anonymous paywall meter keeps no server record; signed-in readers' reads are kept 62 days. Migration `0094_meter_reads_minimal.sql`.
- A consent record made from an older form version says so (`version_claimed`), and that version's required box is enforced. Migration `0109_consent_version_claimed.sql`.

### Changed

- **Local development:** the workers need new keyrings and a running `vault` worker. In a clone where `pnpm setup:dev` ran before this change, delete `workers/*/.dev.vars` and run `pnpm setup:dev` again (it leaves existing files alone); a worker that is missing a keyring refuses to start. The browser tests run fully offline: outbound requests are refused and Turnstile is stood in for locally.
- The project website (`apps/www`, later `swarm-web`) is removed from the repository; it is no longer used. `pnpm dev` and `pnpm check:dry-run` no longer include it.
- Everything a reader or a person using the dashboard can read now uses plain words: post, subscriber, publication, plan, paywall, gift subscription, "Manage your subscription". This covers the website, signup and subscriber pages, system emails, the newsletter footer and messages from the server. Only built-in text changed; wording you saved yourself is untouched. `pnpm check:vocabulary` now checks reader-facing pages too.
- A page colour you choose for your website now fixes the site to the light or dark look that suits it, instead of following each reader's device and risking light text on a light page.
- On the install's shared sending domain, raising the warm-up ceiling above 5,000 a day or skipping warm-up now needs an instance admin. Publication admins could set any ceiling before.
- The SNS signature tests generate their key and certificate on each run, and the test key is no longer in the repository.

### Fixed

- Sending limits: a saved change applies to the next email everywhere, so a resumed send is no longer stopped again by a worker's cached copy. Sign-in links wait behind the part of a send already handed out (a few seconds at most), so all mail together keeps within the per-second limit.
- A send the email service stopped is tried again by itself (after 5 minutes, then less often, at most 6 hours apart) and goes on when the service takes mail. After 7 days it ends as failed, and the subscribers still waiting are recorded as not sent. Direct Sends of both kinds answer 429 while the service's quota is used up.
- Resuming a waiting send, and delayed or duplicate batches, no longer use a warming domain's daily limit twice (migration `0070_limits_fixes.sql`). A batch gives back what the limiter counted even after a later turn timed out.
- "Stop mailing" on a held subscriber, and "Apply to past bounces too", no longer fail after a block, and "Apply to past bounces too" reaches everyone when more than 500 subscribers are already held.
- A small email check finishes even when DeBounce keeps failing for some addresses; they stay not checked after 3 tries. The retention job no longer queries every old automation email, and operator notices end with "Swarm" instead of a dash.
- One email that a provider reported several times (Mailgun reports each retry) counted as several soft bounces, and could stop an address on its own. Blocks for the sender's own reasons (a blocklist, a DMARC failure) were treated as hard bounces and stopped the reader. Out-of-office replies counted as soft bounces. All three are fixed.
- Removing a bounced address under Blocked addresses now gives its subscribers back their earlier status; before, they stayed bounced for good.
- A provider's daily or monthly quota no longer fails a send and skips everyone left; a provider halt no longer breaks an automation for good.
- An image, button or paywall break inserted in a post could vanish when you typed or inserted the next block. The cursor now lands on the line after it.
- Opening a sent post no longer shows "Your latest changes are not saved".
- Home counts clicks by people, as the send report does, and tells you when a verified sending domain has no sender using it yet. The first steps on a new install always link to importing subscribers and adding a signup form.
- An import no longer creates empty tags from rows it skips, and the website's Newspaper layout is only offered when the feature is on.
- The text colour in your email design now applies to headings and body text, and your postal address is in the plain-text version of each post as well as the HTML one.
- The Sending and Deliverability pages no longer scroll sideways on a phone.
- The Links table on a send's report showed clicks under People, so someone clicking twice counted as two people. People now counts each person once, Their clicks has the old number, and the stats API adds `humanPeople`. The report no longer runs off the side of a phone's screen either.
- Imported past issues looked like drafts waiting to be sent, and could be emailed by accident. They now say Past issue, and Swarm refuses to send or schedule them. Migration `0060_post_archive_calendar.sql` marks earlier imports: a draft or scheduled post whose website date is older than the post itself.

- Amazon SES installs now set their SNS topic to signature version 2. Before this, Swarm would have refused every bounce and complaint report, so bad addresses weren't suppressed and sends didn't pause. If you installed with SES, run `pnpm swarm` with an AWS admin key to fix the topic and subscribe again. `pnpm swarm doctor` now reports this. It hasn't been tested against real AWS yet.
- A message Amazon SES refuses after accepting it is now marked failed, without suppressing the address.
- Renaming a publication now shows on its site straight away, instead of waiting for cached pages to expire.
- **Shorten all links** no longer shortens a short link again when Shorthop uses its primary domain.
- Resend's DNS records were written under a doubled name (`resend._domainkey.mail.mail.example.com`), so the domain never verified and no email could be sent. If you installed with Resend before this fix, rename those records on Cloudflare so `mail` appears once, then verify the domain in Resend.

### Added

- **Sending limits.** Set your email service's limits (per second, hour, day and month) under Settings > Instance, with presets for common plans and your AWS account's own limits. Every email Swarm sends counts against them together, and sign-in links, confirmations and receipts go first: posts and automations may use 90% of each limit. Migration `0066_sending_limits.sql`; every worker that sends mail now binds the realtime worker's `SendPacer`, so deploy realtime first, as the installer does. `MAIL_MAX_PER_SECOND` keeps working as a ceiling.
- **Nothing is lost over a limit.** A send that reaches an hourly, daily or monthly limit, or your email service's own quota, waits and continues by itself, and the send report, live monitor and Home say how many are left and when it continues. A send the email service stops (suspended account, refused key, unverified domain) pauses with everyone still waiting instead of failing, and an admin can choose **Resume sending** after the fix. Long throttling no longer sends batches to the dead-letter queue.
- **Bounce rules.** Choose under Sending & delivery > Bounces when Swarm stops mailing an address. The defaults are the first hard bounce, or 3 emails in a row that bounced softly, so weekly and monthly newsletters now also drop mailboxes that are full for good. Every bounce is classed as hard, soft or blocked from what the email service and the receiving server say; a block (blocklist, DMARC failure, spam filter) never removes the reader, and the deliverability check-up says which mailbox provider is refusing you. Subscribers on a paid plan are never stopped silently: they appear under Needs your attention and owners and admins get an email. Migration `0067_bounce_policy.sql`.
- **Email checks with DeBounce.** Check subscribers' addresses at signup (with "Did you mean…?"), on import, when someone is added, and across your whole list. Every address gets a green, orange or red check; filter and segment on it, and stop mailing red addresses in a click, with paying subscribers never changed automatically. A whole-list check shows the credits it needs and your balance first, runs in parts of 5,000, and can be stopped or resumed. Set it up with `pnpm swarm enable debounce`: the key stays a worker secret, and instance admins choose which workspaces may use the install's credits. Feature `email_verification`, on at install, does nothing until `DEBOUNCE_API_KEY` is set. Migration `0068_email_verification.sql`.
- **Warm-up explained where it matters:** on Home, under a verified sending domain, in the import review, before you confirm a send, and on the report of a post still going out. The plan asks how often you send and shows dates for that rhythm, so a weekly newsletter no longer sees dates only a daily sender would reach. The Warm-up section and `docs/warm-up.md` have a "How to warm up well" checklist.
- **Deliverability check-up.** The Deliverability page starts with one verdict and a list of what is keeping your email out of the inbox, most harmful first, each with steps to fix it and a link to the right setting. It looks at your sender, DNS records, DMARC, bounce and complaint rates, mailbox providers that may be filing you as spam, warm-up, list hygiene, your footer address and domain blocklists. Blocklists usually refuse automatic questions, so expect "Couldn't check" there with a link to look the domain up yourself.
- **Advice on the email before you send.** The checks before a send now point out shouting subjects, public link shorteners, links that look like phishing, image-only emails and similar. Advice never blocks a send.
- **Warm-up as a guided page.** Sending & delivery explains what warm-up is, shows where each sending domain stands, and gives a day-by-day plan with the date your whole list fits in one day. Choose a pace (Careful, Standard, Fast or your own numbers), skip warm-up for a domain that already sends this much mail, or start it again. Changing pace never lowers today's limit. Migration: `0062_warmup_plan.sql`.
- **Eight starter templates** in Templates from the first run: personal letter, weekly roundup, essay, announcement, interview, product update, invitation to go paid and welcome issue.
- **Emails built for every mail app.** Posts, sign-in links, confirmations and invites share one frame that handles Outlook on Windows, dark mode and phones, and keeps button labels and links readable whatever colours you choose. It has been checked in a browser only, not yet in real Outlook, Gmail or Apple Mail.
- **Website polish.** All five templates and the plain layout were reworked for phones, dark mode and reading comfort, with a proper page before your first post, a tab icon made from your initial, and readable links and buttons for any accent colour. Website → Branding sets your logo and accent colour, and the template picker shows who each template suits.
- **Guides for writers** in `docs/`: getting started, writing and sending, templates, audience, website, domains, warm-up, a deliverability guide and an FAQ, with an index at `docs/README.md`.
- `pnpm setup:dev` prepares a clone for local development in one step, and the installer's last screen says what to do after signing in.
- A send can go at each reader's best time: within 24 hours of the chosen time, each reader gets it at the hour they most often opened or clicked in the last 90 days. Readers with too little history get the chosen time, and the send report counts both. It's a choice on each send, and it can't run with a split test or cohort sample. While a domain warms up, it applies only if the day's limit reaches the whole audience.
- `MAIL_MAX_PER_SECOND` now holds across the whole install, not per batch, through a new Durable Object in the realtime worker. Deploy the realtime worker first; the installer does this for you. Nothing changes if the variable isn't set.
- PayPal payments now send the **Payment receipt** message once per sale, if the publication's owner has saved it, as Stripe payments already did.
- Posts can be archived and restored, one at a time or several at once. Archiving tidies the posts list only: stats, what was sent and the website stay as they are. Flag `post_archive`, on at install.
- The posts page has a calendar view: scheduled and sent posts on their days, in your time zone, and drafts on a planned date that has no effect on sending. Drag a draft or use Move, and change a real send only with Change time, which runs the usual checks. Phones get a list. Flag `content_calendar`, on at install.
- You can change email service on a running install, from the setup page or with `pnpm swarm mail switch`. Your current service keeps sending while each publication publishes its new records, and you can go back for 14 days. Warm-up starts again after the move. It has only run against stand-ins, not real accounts. Migration: `0053_mail_service_change.sql`.
- Deliverability now shows each sending domain's health in one place: its records, warm-up, bounce and complaint rates, and DMARC. It also has a guide to Gmail Postmaster Tools and, with a dedicated IP, Microsoft SNDS.
- During warm-up, a Broadcast now reaches engaged readers first and cold readers last, so the daily cap goes to the people likeliest to open. It uses engagement scores if they're on, and recent opens and clicks either way. Migration: `0052_warmup_send_order.sql`.
- Settings → Instance now shows your email service: the DNS records it needs, what DNS really has for each, and whether bounce and complaint reports are arriving. For Amazon SES it also shows the sandbox and your sending limits. **Check now** on a publication's sending domain shows the same record by record. It hasn't run against a real account of any service yet.
- Amazon SES on the browser setup page, as a preview. It asks for a key limited to what setup needs, forgets it once email is connected or after 2 hours, and won't finish until bounce and complaint reports are connected and a test email has gone out. It's tested against a stand-in for AWS only, not yet with a real account.
- PayPal for paid memberships: an Owner connects it under Settings → Payments, and readers get **Subscribe with PayPal** on monthly and yearly prices. It's off at install. It has never run against PayPal itself.
- Shorthop has a card on the Apps page, where it's connected. Settings → Applications now leads there. Posts have **Shorten all links** in the toolbar, which also covers linked images, and post stats show where shortened links go. Flows that watch one link keep matching after it's shortened.
- Publication owners can add Stripe under Settings → Payments with a restricted key, without command-line setup. It's off at install, with a switch in Settings → Instance. It has not been tested against a real Stripe account yet.
- Consent text on signup forms can use `<a href>`, `<b>`, `<strong>`, `<i>`, `<em>` and `<br>`. Links always open in a new window.
- Renaming a workspace can also rename its publication, when it has only one.

- The setup page's address choices: the dashboard's subdomain, and a publication at your main domain or a subdomain.
- A check that email works before an install can finish, including a real test email to the owner.
- `pnpm swarm restore`, which sets up a computer from a recovery kit, and a setup guide in `docs/setup-guide.md`.
- A browser setup page that installs Swarm through Cloudflare's API, in `apps/setup`, not yet run for a real install.
- `pnpm release:bundle`, which builds and signs a release locally.
- Your own mail server over SMTP, as a preview for advanced users: it's tested against a stand-in server only. Plain SMTP doesn't report spam complaints unless your server sends them to Swarm.
- Postmark as an email service, as a preview: it's tested against a stand-in for Postmark's API only, not yet with a real send.
- Mailgun as an email service, as a preview: it's tested against a stand-in for Mailgun's API only, not yet with a real send.
- Licence files for the fonts in the design mockups.
- A `license` field in every package, a code of conduct and issue templates.
- Resend on the subprocessors page.
