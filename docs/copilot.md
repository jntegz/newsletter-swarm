# Copilot

Copilot is the writing assistant in the Dispatch editor (flag `copilot`). It suggests subject lines and preview text, rewrites a selection (shorter, longer or in another tone), fixes grammar, translates, writes a teaser, and drafts social posts that share the Dispatch (Share Kit). Every result streams into a panel next to the editor and is applied only when the operator clicks to accept it. With flag `copilot_actions`, the operator can also ask Copilot to do something ("Ask Copilot to do it", below). It runs on Cloudflare Workers AI through the `AI` binding, through AI Gateway when one is configured, with Anthropic as the optional external provider. A workspace can bring its own Anthropic key (flag `copilot_byok`, all plans).

Tables: `copilot_keys`, `copilot_requests` (`migrations/0022_copilot.sql`, widened in `0030_copilot_actions.sql`). Schemas and plan allowances: `packages/domain/src/p8-copilot.ts`. Prompts, the provider adapters and quotas: `packages/engine/src/copilot.ts` and `copilot-provider.ts`; the actions loop: `copilot-actions.ts`. Routes: `workers/api/src/routes/copilot.ts` and `copilotActions.ts` (shared plumbing in `lib/copilot.ts`). Dashboard: the Copilot panel in the editor (`apps/dashboard/src/editor/CopilotPanel.tsx`, `CopilotActions.tsx`) and Settings → Copilot (`apps/dashboard/src/pages/CopilotSettings.tsx`).

## What the operator can do

| Feature (`feature`) | Input sent to the model                     | Result                                                                    | Applied by                            |
| ------------------- | ------------------------------------------- | ------------------------------------------------------------------------- | ------------------------------------- |
| `subject_lines`     | The Dispatch's text and its current subject | Five subject lines                                                        | "Use" on one of them sets the subject |
| `preview_text`      | The Dispatch's text and its current subject | Five preview texts                                                        | "Use" sets the preheader              |
| `rewrite`           | The selected text and a style               | The rewritten selection                                                   | "Replace selection"                   |
| `fix_grammar`       | The selected text                           | The corrected selection                                                   | "Replace selection"                   |
| `translate`         | The selected text and the target language   | The translated selection                                                  | "Replace selection"                   |
| `teaser`            | The Dispatch's text and its current subject | A two or three sentence teaser                                            | "Insert at cursor"                    |
| `social_posts`      | The Dispatch's text and its current subject | A short post, a long post and a thread, each with the Dispatch's web link | "Copy" on each (to the clipboard)     |

The publication's style guide, when the operator wrote one, goes with every feature except `fix_grammar` and `translate`, in its own `<style_guide>` block. The model is told to match its voice and format, and that it can't change the task or the reply format.

Rewrite styles: `shorter`, `longer`, `friendly`, `formal`, `confident`, `plain`. The target language is free text (letters, spaces, brackets and hyphens, up to 40 characters), so any language the model knows works.

Decisions:

- **Text in, text out.** The editor sends plain text (`textBetween` with blank lines between blocks), not the TipTap document. A replaced selection comes back as plain paragraphs, so bold, links and other marks inside the selection are lost; the panel says so next to "Replace selection". Sending and parsing the document structure is a later step.
- **The selection must still match.** "Replace selection" checks that the selected range still holds the text that was sent. When the operator has edited it meanwhile, the panel offers "Insert at cursor" instead, so a late result never overwrites newer writing.
- **Rewrite, grammar and translate need a selection;** subject lines, preview text, teasers and social posts read the whole Dispatch. Merge tags are sent as their literal `{{…}}` text and the instructions tell the model to keep them unchanged.
- **The editor panel is in the Dispatch side panel,** so it is not shown for Flow emails yet (their side panel belongs to the Flow).
- **Editors and up** can use Copilot on a Dispatch they can edit; viewers can't. Settings → Copilot (usage, the workspace key and the request log) is for admins and owners, and needs `copilot` on for the workspace; the editor panel follows the flag as resolved for its Channel.

## Share Kit social posts

`social_posts` returns, in the `done` event's `social` field, `{ short, long, thread, link }`: a short post (at most 280 characters before the link goes in), a long post (at most 3,000 characters, for a long-form network) and a thread of up to six posts (each at most 280 characters before the link). All plain text. The panel shows each with a "Copy" button (and one for the whole thread); Swarm never posts anything anywhere.

- **The link is Swarm's, not the model's.** The server works out the Dispatch's web address (`webUrlFor`: its slug, or the slug it will get, on the Channel's website origin; read only, nothing is reserved) and never sends it to the model. The model is told to write `[LINK]` where the link goes; the parser puts the address there and only there, and appends it to a post (the short, the long, or the thread's last) that has no `[LINK]`. A web address the model writes itself stays as plain text it wrote. Without a website (no site configured), `[LINK]` is removed and `link` is `null`.
- **Layout.** The model answers in `=== short ===`, `=== long ===` and `=== thread ===` sections, thread posts separated by `---` lines (`parseSocialPosts`). An answer without all three sections gives `social: null` and the panel shows the raw text.
- Same checks, quotas and request log as every other feature (`feature` `social_posts`).

## The request

`POST /api/v1/dispatches/{dispatchId}/copilot` with `{ feature, text, subject?, style?, language? }` (at most 24,000 characters of text). Checks before anything is sent to a model, each answering the usual JSON error:

1. The Dispatch exists and the operator has the editor role on its Channel (`channelAccess`; another workspace's Dispatch is `404`).
2. Flag `copilot` is on for the Channel (`feature_disabled` otherwise).
3. Which provider: the workspace's own Anthropic key when `copilot_byok` is on for the Channel and a key is saved, else the platform adapter (`COPILOT_ADAPTER`). A saved workspace key that can't be opened answers `unavailable` and asks for the key again; Copilot never falls back to the platform silently, because a workspace that brought its own key may have done so for its data-processing terms. A platform adapter that can't serve (`workers-ai` without the `AI` binding, `anthropic` without `ANTHROPIC_API_KEY`) and no workspace key: `unavailable`.
4. Rate limits and quotas (below): `rate_limited` with a detail at path `quota` (`month` or `minute`).
5. A `copilot_requests` row is written with status `pending`, so concurrent requests count against the limits at once.

The answer is `text/event-stream`:

```
event: delta
data: {"text":"Three ways to"}

event: done
data: {"requestId":"ai_…","text":"…","suggestions":["…"],"social":null,"remaining":42}

event: error
data: {"code":"rate_limited","message":"…"}
```

`suggestions` is the list for subject lines and preview text (one per line, numbering and quotes stripped, at most five, each cut to 200 characters), else empty. `remaining` is what is left of this month's platform allowance, or `null` with a workspace key. Error codes inside the stream: `rate_limited` (the provider's limit), `key_rejected` (the workspace key stopped working), `refused` (the model declined), `too_long` (the result hit the token limit), `unavailable` and `internal`. Closing the connection cancels the model call and logs the request as `canceled`.

## Quotas and rate limits

The platform's provider is shared, so its use is limited per plan (`COPILOT_PLAN_LIMITS`, decision 2026-10-28, reversible):

| Plan       | Units per month (workspace) | Requests per minute (operator) |
| ---------- | --------------------------- | ------------------------------ |
| free       | 30                          | 5                              |
| pro        | 500                         | 10                             |
| scale      | 2,000                       | 20                             |
| enterprise | 10,000                      | 30                             |

- **Units follow what a request consumes.** An editor request is one unit. An "Ask Copilot to do it" run, which can take up to six model turns, is one unit per started 25,000 input plus output tokens (`COPILOT_TOKENS_PER_UNIT`), at least one. A month is the calendar month in UTC. Every request on the platform key counts except those that failed before the model answered anything (`failed` with no tokens).
- **A fair share for low-privilege seats.** A viewer or author (the lower of workspace and Channel role, as everywhere) may use at most `COPILOT_LOW_ROLE_SHARE` (25%) of the plan's monthly units on the platform key, and `COPILOT_BYOK_LOW_ROLE_MONTHLY_UNITS` (100) a month on a workspace key; past that their requests answer `rate_limited` with quota `seat`, and editors and above keep using the pool. Viewers keep the feature, as documented, within that share.
- With a workspace key there is no Swarm allowance; the operator's own provider limits apply. An admin can set a monthly ceiling for it (`PATCH …/copilot/key` with `{ monthlyUnitCap }`, null for none; Settings → Copilot → Your model key), after which requests on it answer `rate_limited` with quota `month`; the settings show the units used on it this month, and the request log shows who used them. A per-operator limit of 30 requests per minute (`COPILOT_BYOK_PER_MINUTE`) still protects the API worker.
- Limits are counted from `copilot_requests` in D1. The check and the request's `pending` row are one conditional insert, so requests sent at the same moment can't take more than the free slots between them.

## Bring your own key

Settings → Copilot → Your model key (admins and owners, flag `copilot_byok`, every plan).

- `PUT /api/v1/workspaces/{workspaceId}/copilot/key` with `{ provider: "anthropic", apiKey }`. The key is checked with the provider first (Anthropic: listing models, which costs no tokens); a key the provider refuses answers `invalid_input` at path `apiKey`, and a provider that can't be reached answers `unavailable` without saving. A valid key replaces the previous one.
- Stored as `{ workspaceId, apiKey }` sealed with `FIELD_KEYS` (AES-256-GCM with a key derived by HKDF; the key id is bound as additional data). Opening it checks the workspace id, so a sealed value copied to another workspace's row doesn't open.
- Used only inside the vault worker (docs/security.md "The vault"): the api never opens the key. Before a request starts its stream, the api asks the vault whether the key opens for the operator (`checkCredential`); one that doesn't answers `unavailable` in JSON, before any stream, and a vault that doesn't answer does the same. The model's requests then go out through the vault's streaming proxy (`providerStream`), which attaches the key and hands the reply back as Anthropic sends it, so the editor's text still streams in word by word. A key the provider stops accepting is reported inside the stream as `key_rejected`.
- Only the last four characters are kept in clear (`last4`) and shown. No response returns the key, the audit entries (`copilot_key.saved`, `copilot_key.deleted`) record the provider and last four only, and the log redactor strips anything shaped like an Anthropic key (`sk-ant-…`).
- `DELETE /api/v1/workspaces/{workspaceId}/copilot/key` removes it; requests go back to the platform key and its allowance.
- `GET /api/v1/workspaces/{workspaceId}/copilot` returns the provider, model, whether BYOK is available, the saved key's last four and dates, the key source in use and this month's usage. `GET …/copilot/requests` lists the request log.

## Providers and the model

`@swarm/engine` exports the adapter interface `CopilotProvider` (`stream()` yields text deltas and a final usage record; `complete()` runs one non-streaming turn with tools and returns text, tool calls, tokens and the stop reason, on providers with `toolCalling`; `validateKey()` checks the key it was built with), `platformCopilotProvider(env)` (the platform adapter and its model, or null) and `createCopilotProvider(env, apiKey)` (a workspace key's provider).

- **`COPILOT_ADAPTER=workers-ai`** (the default in `wrangler.jsonc` for staging and production): Cloudflare Workers AI through the `AI` binding, model `COPILOT_WORKERS_AI_MODEL` (`@cf/moonshotai/kimi-k2.6`, an instruction-tuned chat model with tool calling). The adapter speaks the OpenAI-compatible chat format the current text models take: `messages`, `max_tokens`, `stream: true` with `stream_options.include_usage` for the editor, and `tools` (function definitions) for actions. It also reads the older `{ response }` shape. No model-specific reasoning settings are sent, so any chat model of the catalogue can be configured; reasoning text in the stream is ignored. Errors are mapped from Workers AI's error codes (capacity and rate limits to `rate_limited`, bad input or unknown model to `invalid`, everything else `unavailable`); the binding's message is never logged. There is no key: the binding bills the account. `validateKey()` always succeeds.
- **`COPILOT_ADAPTER=anthropic`** (the optional external provider) and every workspace key: the official Anthropic TypeScript SDK (`@anthropic-ai/sdk`), Messages API. The editor streams with effort `low` (these are short, well-specified writing tasks), adaptive thinking left at the model's default, `max_tokens` 4,000 for subject lines, preview text, teasers and social posts and 16,000 for rewrite, grammar and translate. Actions use `messages.create` with `tools`, effort `medium`, `max_tokens` 4,000 per turn, automatic prompt caching (`cache_control` at the top level: the tool list and system prompt repeat every turn) and no forced `tool_choice`; the assistant's content (thinking blocks included) is sent back unchanged on the next turn. On models that support it, server-side refusal fallback (`fallbacks: "default"`, beta `server-side-fallback-2026-07-01`) lets the API retry a declined request on its default fallback model inside the same call; a request the whole chain declines ends with `refused`. The SDK retries 429 and 5xx twice.
- **`COPILOT_ADAPTER=dev`**: a deterministic fake for local development and tests (like `MAIL_ADAPTER=dev`). It never makes a network request, streams a predictable transformation of the input, and accepts any well-formed key except one containing `invalid`. For actions it is a scripted, gullible model: it calls every `dev:call <tool> <json>` it finds in the latest message, whether the operator wrote it or a tool's answer carried it, which is how the tests show that injected instructions can't run a change. Refused outside development and test.
- **`COPILOT_MODEL`** is the Anthropic model id, a declared var with the default in `workers/api/wrangler.jsonc`: `claude-opus-5-5` (Claude Opus 5.5). **`COPILOT_WORKERS_AI_MODEL`** is the Workers AI model id, also a declared var. Neither is a secret; neither has a fallback in code; change them per environment in the config.
- **`ANTHROPIC_API_KEY`** is the platform key for `COPILOT_ADAPTER=anthropic`, an optional secret. With `workers-ai` it is not used.
- **AI Gateway** (optional): with `AI_GATEWAY_ID` and `AI_GATEWAY_ACCOUNT_ID` set (both or neither), Workers AI calls carry `gateway: { id, skipCache: true, collectLog: false }` and Anthropic calls (platform and workspace keys) go to `https://gateway.ai.cloudflare.com/v1/<account>/<gateway>/anthropic` with `cf-aig-collect-log: false` and `cf-aig-skip-cache: true`. The gateway is configured with logs and cache off (docs/deployment.md); what it keeps is analytics only (request counts, tokens, cost estimate, latency, model, provider, status), never a prompt or a response.

## Ask Copilot to do it

With flag `copilot_actions` on (and `copilot`), the editor panel has a box where the operator types a request ("tag everyone who joined this week as new"). Copilot turns it into calls to the same tools Open Operator serves over MCP, derived from the `/v2` document ([open-operator.md](open-operator.md)), and every call goes through `runAgentTool`: it is in the agent log, follows the workspace's approval mode, and reaches the `/v2` route through the router with the route's own checks.

`POST /api/v1/channels/{channelId}/copilot/actions` with `{ request, dispatchId? }` (at most 2,000 characters) answers `{ requestId, text, steps, stop, readWorkspaceContent, remaining }`. Each step is one call: `tool`, `risk` (the call's effective risk: a write whose effect is hard to undo counts as destructive, see [open-operator.md](open-operator.md#what-is-held)), `actionId` (its agent log row), `outcome` (`ok`, `error`, `denied`, `unknown_tool`, `pending_approval`), `statusCode`, the masked `arguments`, and for a held call `approval: { id, expiresAt, decider, reason, request, requestDigest, target, afterReading }`: `request` is the exact `/v2` request that runs if it is confirmed (`method`, `path`, `body`, as the admin approval view shows a pending call), `requestDigest` its SHA-256, `target` what the call acts on as the server looked it up (a post's subject, status, web visibility, sender and audience; a Member's id and status; a feed source's URL, mode and status), and `afterReading` whether the model had read workspace content before proposing it. `readWorkspaceContent` says the model read any tool result in this request. Every call's agent log row and approval carry the request's `requestId` (`copilot_request_id`), so an action can be traced to its run; the request text itself is still not stored. `stop` is `done`, `max_steps`, `max_tokens`, `refused` or `error` (the provider failed after some calls; the calls made are still listed). A provider failure before any call answers the usual JSON error.

- **Who it acts as.** The principal is the operator acting through Copilot: `principal_kind` `copilot`, `principal_id` the operator's id, `client_name` `Copilot`, `source` `copilot` in `agent_actions` (and `agent_approvals`). The approval queue labels it "<address> via Copilot". `/v2` writes it makes are audited with the operator as the actor and `metadata.via: { kind: "copilot", id }`.
- **Scope: the operator's own role, never wider.** The principal reaches only this Channel, with the scopes of the lower of the operator's workspace role and their role on the Channel (`COPILOT_ROLE_SCOPES`): viewers and authors get read scopes only (an author can't schedule a Dispatch, and `dispatches:write` includes scheduling), editors add the Member, Dispatch, Circle, field, Flow, import and Roster write scopes, admins and owners add webhooks, Direct Sends and the audit log. The model is offered only the tools those scopes allow; a call to any other tool still goes through `runAgentTool` and is recorded as `denied` (or `unknown_tool`). Shared write helpers see the operator's role, not the editor role API keys act with.
- **What waits.** A call is held as a pending approval (an `agent_approvals` row, the exact request stored) when:
  1. the workspace's approval mode holds it (`destructive` or `writes`; decider `admin`), or
  2. it is destructive (deleting, sending, adding a Member, an API event, changes to many Members; the Open Operator list), or a write whose effect is as hard to undo (an unsubscribe or tag replacement through `update_member`, making a post more public, tagging while a live Flow starts on it), whatever the mode, `never` included (decider `operator`), or
  3. it reaches outside Swarm (it sends email, calls a webhook endpoint or fetches a feed: `send_dispatch_test`, `send_webhook_test`, `check_feed_source`, …), on any turn, the first included (decider `operator`), or
  4. it changes data and the model had already read a tool's answer in this request (decider `operator`). Any answer can carry text someone else wrote: a Dispatch, a Member's name, a form answer.

  The panel lists held calls with what each acts on (from the server, never from the model), the request that would run (method, path and body; a call with no body says it acts on the target as it is when confirmed), whether it was proposed after reading workspace content, and "Confirm" (for destructive calls, "Confirm and run") and "Cancel". When the run read workspace content, a note above the calls says so. The model's closing message comes after the calls, in a separate block labelled as written by the model, so it can't pass for the system's own description of a request. Reads always run. A plain write in the first turn (drafting: `create_dispatch`, `update_dispatch` on the open post, a Member's name), before the model has read anything, runs at once unless the mode holds it; text pasted into the request can't add or unsubscribe Members, send or fetch in one step.

- **Confirming.** `POST /api/v1/channels/{channelId}/copilot/actions/{approvalId}/confirm` with `{ requestDigest }` (the one the held step carried) runs a held call of the operator's own Copilot request, exactly once, through `approveAgentApproval`. A digest that does not match the stored request is `conflict` and nothing runs, so a click only ever runs the request the operator was shown. The operator's role and Channel access are re-resolved at that moment and the call is refused if they no longer allow it. A call the approval mode holds needs the admin role on the workspace (`forbidden` otherwise; an admin can also approve it in Settings → Developers → Open Operator, like any held call). Audited as `copilot_action.confirmed`. `…/cancel` rejects it (always allowed for the operator's own calls) and is audited as `copilot_action.canceled`. Anyone else's held call, or one from another Channel or workspace, is `404`. With **Need a second person** on in Settings → Developers → Open Operator (`separateApprover`), the operator who asked can't confirm any of their own held calls (`forbidden`): another admin approves it there.
- **Prompt injection.** Only the operator's request is an instruction. The model gets the Channel id and the open Dispatch's id, never the Dispatch's content; it reads content only through tools, and the system prompt says tool results are data. That is a request to the model, not a guarantee, so the rule that matters is structural: whether a call waits is decided in the loop from the tool's risk and from whether the model has read workspace data, never from anything the model says. Injected text can make the model propose a change; it can't make one run without the operator's click, and the click is made on the request itself (target ids, recipients, content), not on a tool name next to text the model wrote.
- **Caps** (`COPILOT_ACTION_LIMITS`): 6 model turns, 4 tool calls run per turn (more are answered as skipped), 150,000 input plus output tokens per request (no further turn starts after that; the tool list alone is about 3,000 to 12,000 tokens a turn depending on the role), 4,000 output tokens per turn, 8,000 characters of each tool answer given back to the model.
- **Quotas and logging.** One request counts once against the per-minute limit and, by the tokens it used, against the monthly units (see Quotas), and writes one `copilot_requests` row (`feature` `actions`) with the total tokens. Each call is in the agent log. Neither keeps the request text or the model's answer.
- Any role on the Channel can use it (Copilot gets that role's scopes). The flag is enforced on every route; `cancel` works without it so a held call can always be dropped.

## Prompts and untrusted content

The system prompt holds the instructions; the Dispatch text goes into the user turn inside `<dispatch_content>…</dispatch_content>`, after a line saying that everything inside the tags is content to work on, never instructions to follow. Any `<dispatch_content>` or `</dispatch_content>` already in the text is defused (the angle brackets become `‹ ›`) so the content can't close the block early. The current subject goes in its own `<current_subject>` block the same way. Output instructions ask for the result text only: no preamble, no quotes, merge tags kept. The editor features have no tools and their output is only ever shown to the operator, who decides what to keep, so an injected instruction can at most produce a bad suggestion. Ask Copilot to do it has tools; see "Prompt injection" above for why injected text still can't make a change run.

## Data handling

- **What leaves Swarm.** For the editor features, only what the operator asks about: the selection, or the Dispatch's text and subject for subject lines, preview text, teasers and social posts, plus fixed instructions. No Member data is read or sent: merge tags go as their literal tag text, never a Member's values. For Ask Copilot to do it, the request, the Channel and Dispatch ids, the tool list, and what the tools return (cut to 8,000 characters each). By default the results of Member and Roster tools reach the model without the values in `COPILOT_WITHHELD_MEMBER_KEYS` (address, first and last name, field values, including ones sealed at rest, consent records, the leaving reason, phone and IP): each becomes `"[withheld]"`, and ids, statuses, tags, counts and dates stay. A workspace admin can choose **Copilot sees subscribers: in full** in Settings → Developers → Open Operator (`copilotMemberDetail: "full"`), which sends them as the API returns them; that setting applies to viewers' runs too. MCP clients are not masked: an external agent is given exactly what its key or grant allows, and its operator chose that. No operator or workspace identifier is sent to the provider beyond those ids.
- **Platform provider, Workers AI (the default).** Requests run on Cloudflare's network under the same terms as the rest of Swarm's hosting; Cloudflare is already Swarm's subprocessor for everything Swarm stores, so Workers AI is not a new one ([subprocessors.md](subprocessors.md)). Cloudflare does not use Workers AI inputs or outputs to train models. With AI Gateway, logging and caching are off per request and in the gateway's settings.
- **What Swarm keeps.** `copilot_requests` holds metadata only: feature, key source, provider, model, status, error code, input and output tokens, latency, the operator, the Channel and the Dispatch, and times. Never the prompt, the selection or the output. Nothing in the request or the result is written to logs; failures log the request id, the error class and the provider's HTTP status.
- **Training and retention, Anthropic on the platform key.** Anthropic does not train on inputs and outputs of its commercial API. Zero data retention is an agreement on the Anthropic organisation, not a per-request setting: the Messages API has no header or parameter that opts a single request out of training or retention, so Copilot sends none. The hosted service's organisation must have zero data retention enabled before `COPILOT_ADAPTER=anthropic` is set in production (docs/deployment.md), and the model in `COPILOT_MODEL` must be one that zero data retention covers (Claude Fable 5.1, for example, needs 30-day retention and is refused under it). Anthropic is listed in [subprocessors.md](subprocessors.md).
- **Training and retention, workspace key.** Only Anthropic keys can be brought. The request runs under the operator's own Anthropic organisation and its terms, as an export destination runs under the operator's own bucket. That provider is the operator's, not Swarm's subprocessor.
- **The key never reaches the browser.** The dashboard only calls Swarm's API; provider keys exist in the API worker's memory for the length of one request.
- **Retention of the log.** `copilot_requests` rows are deleted with their workspace; the operator column clears when the operator is deleted. Age-based pruning is not built yet.
