## Sending (Phase 2)

- **Unsubscribe.** Every Broadcast message carries `List-Unsubscribe` (an https URL and a mailto address) and `List-Unsubscribe-Post: List-Unsubscribe=One-Click`. The GET page only confirms; the POST unsubscribes. Codes are per delivery, signed with `UNSUBSCRIBE_KEYS`, and short enough for a mailto local part. A Broadcast sent to Rosters (Phase 8, [rosters.md](rosters.md)) leaves those Rosters instead, with "Unsubscribe from everything" on the page; with the `rosters` flag off it always unsubscribes from the Channel. A Member who left a Roster themselves can't be put back on it by a teammate, an import or the API.
- **Raw MIME.** Messages are built as raw MIME so these headers reach the inbox. Header values with line breaks are refused; names and subjects are RFC 2047 encoded.
- **DMARC gate.** A custom sending domain can't send until SES verifies DKIM and its published DMARC policy is `quarantine` or `reject`.
- **Mail service domains.** Adding a sending domain creates it at the mail service; a domain the service already has (the other environment's mail domain, or one of the operator's own) is refused with 409 and never taken over, so its verified status and DKIM key can't pass to a workspace. Removing one deletes only the copy its row created: nothing on a service the row isn't on, and while a service change has registered it at the next service (which the Worker can't reach) removal waits until the change is finished or dropped. Both environments' platform hosts (`mail.D` and `staging-mail.D`, and so on) are refused as sending and link domains.
- **Tracking.** Click tokens carry a delivery id and a link target id, never a URL, and expire after 400 days. A bad token shows a page and never redirects. IPs are cut to /24 or /48, user agents are stored as a family only, and no cookies are set. Each Channel can turn open tracking off.
- **Feedback.** SNS messages must be SignatureVersion 2, signed by a certificate on `sns.<region>.amazonaws.com`, for a topic in `SNS_TOPIC_ARNS`, and less than an hour old. A bounce stops the address across the workspace when the workspace's bounce rules say so ([deliverability.md](deliverability.md)); a complaint suppresses and unsubscribes. Svix-signed webhooks (Resend, `/smtp-feedback`) are applied once per `svix-id`, and Mailgun's once per token, so a captured request can't be replayed. An event matched to a delivery only ever acts on the address that delivery went to. Mailgun's signature covers only a timestamp and a token, not the event, so a Mailgun event changes nothing unless it agrees with what Swarm recorded for the send it names (the send's address among the event's recipients, and the provider message id Swarm stored, when it stored one); one that disagrees is acknowledged and ignored without using up its token. A token is also bound to the event it first came with: released after a failed apply, it is accepted again only with that same event. Each suppression a bounce causes is traceable to the send (`bounce_events.send_id`), and a complaint to its delivery (the `member.complained` audit entry); removing the suppression reverses it.
- **Idempotent sends.** Recipients are claimed before sending, so a retried or duplicated queue message never sends twice. The one at-least-once window is a worker dying after the provider accepted a message but before the delivery was recorded.
- **Test sends** go only to operators of the workspace, are untracked, and are limited to 10 a minute per operator.
- **Merge tags.** Member values are HTML-escaped and inserted in a single pass, so a name can never inject markup, links or other merge tags.
- **Live send monitor.** `GET /api/v1/broadcasts/:id/live` upgrades to a WebSocket only when the `Origin` is the dashboard's: browsers send cookies on cross-site WebSocket handshakes, and the CSRF guard skips GETs. Access is checked like any Broadcast read before the socket is handed to the `SendMonitor` Durable Object, which has no route of its own and ignores anything a client sends. A socket holds that check for 5 minutes at most, whether or not the Broadcast finishes: the monitor then closes it (code 4001) and the dashboard reconnects through the same check, so a removed seat or a revoked session stops receiving progress within 5 minutes.
- **Raw HTML** (flag `raw_html_mode`) is shown in the editor as text, and previewed only in an iframe with an empty `sandbox` (no scripts, no same-origin access). It is linted for non-web links, images without alt text and dark-mode traps.
- **Attachments** are download links to the media library, not MIME parts. The file URL carries a random 128-bit id, so it can't be guessed, and deleting the file revokes it. Uploads pass through a virus-scan hook (`workers/api/src/lib/scan.ts`) that accepts everything until a scanner is plugged in.

## Audience (Phase 3)

- **Subscribe.** Turnstile runs inside the form iframe and fails closed outside development. The worker also checks a honeypot field (a filled one gets an ordinary-looking answer that carries no token or Member reference), refuses disposable domains and checks the form's origin allowlist (Referer, and the parent origin reported over `postMessage`, checked both ways). The allowlist is a placement control for browsers (`frame-ancestors` and those checks): the origin it checks is what the client says, so a script can name any allowed site, and it is no proof of where a sign-up came from; a form whose source matters should use double opt-in. The consent record keeps the two apart (migration `0116`): `verified_host` is what the server checked itself (the hostname siteverify reported for a pass bound to this form, or the forms address where Swarm's own question was answered; widgets only render there, so it shows the check ran on Swarm's page for this form, not which site framed it), and `claimed_origin` is the site the submission named, shown in the subscriber drawer as not verified and never used as proof. A Turnstile pass is bound to the form it was solved on (the widget's `data-cdata` is the form id, checked against siteverify's `cdata` outside development), so a pass from one form's page can't be spent on another. The frame always says which publication the visitor is joining, under the button, whatever the embedding page says around it. Sliding-window limits: 10 per 10 minutes per IP and 600 per 10 minutes per form. The response is built before any lookup and is the same whether or not the address exists; the work happens in `waitUntil`. Only a new Member takes the submitted name, fields and referral, so typing someone else's address changes nothing about them. A redirect after sign-up carries a signed reference (purpose `member-ref`), never the email or the Member id.
- **No-JS fallback.** A plain form post without a Turnstile token gets a challenge page on the capture origin; nothing is accepted without passing Turnstile or, with JavaScript fully off, a small sum. The sum's answer travels only as an HMAC under a key derived from `CAPTURE_KEYS` (capture's own keyring) for this purpose alone (so it can't be checked offline), each question takes one answer, right or wrong (a wrong one gets a new question, so the few possible sums can't be tried in turn), and a sign-up that passes this way always confirms by email.
- **Embed.** The loader captures `document.currentScript` at the top level, never assigns `innerHTML` from data, and is byte-stable per form version so SRI holds. Scripts are CORS-readable without credentials; no other capture endpoint sends CORS headers. The frame sets `frame-ancestors` from the allowlist, and capture pages use `Referrer-Policy: same-origin` so token URLs don't leak.
- **Member tokens** each have a keyring of their own ([Per-link keys](#per-link-keys)), separate from session and tracking keys, with distinct purposes: `confirm` (7 days) and `leave` (unsubscribe from a confirmation email, 30 days) on `CONFIRM_KEYS`, `member` (Member Center, 30 days) on `MEMBER_SIGNING_KEYS` (Ed25519: capture holds the public key to check it), `member-ref` (1 day) and `challenge` (15 minutes) on `CAPTURE_KEYS`. A token for one purpose is refused for any other, and each names its Channel (`c`), which the checking route compares with the row it loads: a Member Center link for one Channel's Member opens nothing for another's.
- **Confirm** is a POST from a page, never a GET, and only moves a Member out of `pending` (or out of `unsubscribed` for a "welcome back" request). Replays do nothing.
- **Encrypted profile fields** use AES-256-GCM with a key derived from `FIELD_KEYS` by HKDF; the key id is bound as additional data and the newest key encrypts while every key decrypts. Circle rules can only test them for presence.
- **Circles** compile to SQL with every value bound as a parameter and every column and JSON path taken from a fixed list. Property tests compare the SQL with a reference evaluator on random rules; a fuzz test checks that hostile values never change the SQL text.
- **Exports** are admin-only, audited on creation and download, and downloaded with a 24-hour token (purpose `export`) plus a session with access. Cells that start with `=`, `+`, `-`, `@`, tab or carriage return are prefixed with an apostrophe so spreadsheets don't run them.
- **Imports** accept UTF-8 CSV up to 50 MB. Role, disposable and suppressed addresses are reported and skipped, and rows without a consent attestation become `pending`; those who never confirm are deleted after 30 days. An attested import records a consent record per new subscriber with the attestation's wording and who attested.

## Channel websites (Phase 4)

- **Tenancy by Host only.** The site worker resolves the Channel from the `Host` header: `<slug>.<PLATFORM_SITE_DOMAIN>` or a custom hostname whose row is `active`. Anything else gets a 404 page, never another Channel's content. Platform routes live under `/_swarm/*` and slugs in `RESERVED_SITE_PATHS` can't be taken by pages, sections or Dispatches.
- **Gates.** Paid and Member-only content is cut at the gate divider and the gated part is rendered on the server only for entitled readers (`canReadFull`). Search indexes only what anyone may read, and cards, feeds and excerpts never show more than the page. Emails of paid Dispatches stop at the gate.
- **Reader sign-in** is a magic link to a Member's address: its own tables, keyring (`READER_KEYS`, purposes `reader-signin` and `reader-session`) and cookie (`__Host-swarm_reader`, HttpOnly, SameSite=Lax), separate from operator sessions and Member Center links. The sign-in answer is the same for any address; the link works once, for 20 minutes, and is consumed by a POST from a page that names the Member's address first, and the one this browser is signed in as when continuing would replace it. Return paths are same-site paths only, and followed only by the browser that asked for the link (`__Host-swarm_reader_link`, HttpOnly, SameSite=Strict, 20 minutes, derived from the token and set by every sign-in answer) or one already signed in as that Member; a link continued anywhere else goes to the site's home page, so whoever sent it does not pick the page. Cross-site form posts are refused, here and on every site form: a post needs a matching `Origin` or `Sec-Fetch-Site: same-origin`, and `Origin: null` (a sandboxed frame, or a form on a no-referrer page) counts only with `Sec-Fetch-Site: same-origin`. Limits: 10 a minute per IP, 3 links per 30 minutes per Member. A reader session slides for 30 days of use but ends 90 days after sign-in whatever happens (`READER_SESSION_MAX_MS`). Starting a session deletes the one the browser had, so a replaced cookie can't be used from anywhere else. A Member who stops being a reader (unsubscribes, bounces, complains) loses every session at once (a trigger on `members.status`, migration 0092), so coming back later never revives an old browser. "Sign out on every device" (on the plans page for a signed-in reader, `POST /_swarm/reader/signout` with `everywhere=1`) ends all of a Member's sessions on that site.
- **Verified crawlers.** Gated content goes to search engines only when the Channel turns it on (flag `gated_seo_exposure`), Cloudflare verifies the bot as a search crawler, and forward-confirmed reverse DNS matches Googlebot or Bingbot. Those responses are never cached.
- **Edge cache** keys include host, the Channel's id, path, reader class and the Channel's `cache_version`, so a hostname moved to another Channel never serves the old Channel's pages and a page rendered for one class is never served to another; responses with `Set-Cookie` are never stored, and signed-in readers get `private` responses.
- **Headers.** Every page carries a CSP with a per-response nonce (`default-src 'none'`, scripts only by nonce, `frame-ancestors 'none'`, forms only to the site and the capture origin). A default site runs no JavaScript and loads nothing from other companies. An owner can add a cookie popup and their own code such as analytics (admin role, audit logged): that code is stored inert and starts in the reader's browser only after they agree, unless the owner marks it strictly necessary. The reader's choice is kept in `__Host-swarm_consent` (plain `swarm_consent` over http locally), so owner code on another Channel's site under the same domain can't set it, and the server and the page both ignore a choice made on other wording or code. Those pages get `'strict-dynamic'` and wider connect, frame and font sources, and the code stays off gift links, signup steps and account pages. It also never runs for a signed-in reader (on any page) or on a paywalled post shown in full (a free read, a gift link, a soft Gate passed): code on the site's origin, including a third-party tag whose vendor changes it later, could otherwise act with the reader's session, for example ask for a gift link, and read gated text. So it can read what a visitor who isn't signed in sees on a public page, but not a reader's session or their gated reading. Reader actions whose answer is a secret (sharing a gift link) also refuse posts that browsers mark as made by script (`Sec-Fetch-Mode` other than navigate, or a frame as destination), and the page with the link has `Cross-Origin-Opener-Policy: same-origin`, so an open tab from before sign-in can't take the link either. A page whose address holds a secret (a gift link, a signup step, any `/_swarm/` page) sends at most the site's origin as referrer, in the header and the page's meta element alike, so the next page's `document.referrer` never holds the token; signup steps send none. Otherwise pages run no JavaScript; raw HTML blocks render only in an iframe with an empty `sandbox`. A page showing a YouTube, Vimeo or Spotify embed is the one other case: it gets a small nonce'd script, and its `frame-src` names exactly the players on that page that the reader may see, decided per page and kept on a cached copy. The page loads nothing from those services until the reader clicks a button that says where the player loads from; the frame then uses `youtube-nocookie.com` or Vimeo's `dnt=1`, a narrow `sandbox` and `allow`, and sends only the site's origin as referrer. We set no cookie for this, though the service may set its own. X and Bluesky embeds stay links, because they need the service's own script in the page. Before such a click there are no third-party requests: fonts are system stacks and share links are plain anchors.
- **Where owner code runs** (`migrations/0065_site_code_rules.sql`). Every publication's platform address is a subdomain of the install's own domain (`<slug>.PLATFORM_SITE_DOMAIN`), so a script or a fake sign-in page there carries the install owner's name and can get the whole domain blocklisted, dashboard and sending domain included. Owner code (scripts, not CSS; verification tags load nothing and stay) therefore runs on the platform address only for a workspace an instance admin allowed, or every workspace when an instance admin turned on **Settings → Instance → Code on websites → Let every workspace add code to websites on this Swarm's domain** (off by default). On a publication's own active custom domain it always runs; Swarm refuses custom hostnames under its own domains. The rule is enforced twice: `PATCH /site/settings` refuses new or changed scripts (`forbidden`) when neither applies, and the site worker drops them from pages served on the platform address. Saved code that may no longer run is kept, and the dashboard says why and how to fix it. Turning on every workspace does not release code that was withheld at that moment: those workspaces are recorded in `site_code_held` (`0113_instance_assurance.sql`), their code stays off on the platform address and they can't change it there (`reason: held`) until an instance admin allows each one by itself, after looking at it. Workspaces with nothing waiting may add code under the new rule. Turning the switch off clears the list; stopping one workspace while it is on holds it. Changing a rule bumps the affected websites' `cache_version`. Allowing or stopping a workspace is written to that workspace's audit log.
- **Install-level grants are explicit rows** (`migrations/0069_review_fixes.sql`). Running code on the install's own domain (`site_code_workspaces`) and spending the install's DeBounce credits (`email_check_workspaces`, see [email-verification.md](email-verification.md#who-can-use-the-credits)) follow only rows an instance admin wrote, each with `allowed_by`, or the instance-wide switch. An owner seat held by an instance admin grants nothing: any owner may make any teammate an owner without asking (`PATCH /workspaces/{id}/seats/{seatId}`), so a tenant who invited the install owner as a viewer could otherwise promote them and unlock both. A workspace an instance admin makes gets its rows when it is made: the installer writes them for the owner's workspace, and a trigger on `instance_admins` writes them for the workspaces the new instance admin made (the `workspace.created` entry of the workspace's audit log names them, and they still hold an owner seat). `0069` wrote the same rows for workspaces that qualified then. Settings > Instance still shows where an instance admin is an owner, for information, with the switch next to it. An instance admin whose role someone else changes in any workspace gets an email about it (`seat_role_changed`).
- **"Strictly necessary" code.** An entry marked necessary runs without the reader's agreement. When its code matches a known tracking tool (`KNOWN_TRACKERS` in `packages/domain/src/p8-site-code.ts`: Google Analytics and Ads, Tag Manager, Meta, TikTok, LinkedIn, X, Pinterest, Snap, Hotjar, Microsoft Clarity and Advertising, Mixpanel, Segment, Amplitude, Heap, FullStory, Yandex), the dashboard asks the owner to confirm, the API refuses the save without `necessaryConfirmed`, and the audit entry lists each confirmed entry and the tools it matched. Swarm never moves it to another category itself; the list is short on purpose, so a tool missing from it simply asks nothing.
- **Media is public by design.** Every upload is served at `/media/<key>` without credentials, because every use needs that: images in emails (mail clients fetch them anonymously), site pages, OG cards fetched by link-preview crawlers, and attachment links in Dispatches. The key carries a 128-bit random id, so it can't be guessed or listed, and deleting the file revokes it. There are no private signed URLs. The one kind of media only some people may get is a PDF sold as a Good: once a product uses it, its `/media/` address answers 404 (whoever learns the key, and after a refund), and buyers get it only through the order-checked library download. Copies fetched or cached before that are out of reach. Otherwise nothing in the product stores media that only some readers may see (gated text is cut on the server; an image inside the gated part is unlisted, not secret). Media is served on the media host and on the owning Channel's own site only, never under another publication's domain. Variants (`?w=`, `?og=`, `?icon=`) come from the Images binding in a fixed set: the listed widths and icon sizes, OG crops with the focal point on a 10% grid, and a card in the owning Channel's current accent whatever colour is asked for. They are cached under the media origin, not the request's host, so the cache can't be filled with arbitrary variants.
- **Redirects** go only to same-site paths or https URLs; targets with control characters, whitespace or backslashes are refused, and `/_swarm` can't be redirected.
- **Bot Rules** block known AI crawlers by User-Agent and by Cloudflare's verified AI category, and write `robots.txt`.
- **Analytics** are cookieless and first-party. IPs and user agents are never stored; unique visitors are counted with a hash salted by a random key that changes daily, and the hashes are deleted after a day. Section analytics on themed home pages count, per section and day, the views that reached a section (a lazy same-origin image) and the signups through its form, with nothing about the reader (`site_section_daily`, kept as long as the Channel like `site_page_views_daily`).
- **Custom domains** are Cloudflare for SaaS hostnames with HTTP DCV, served only once active; adding, removing and making a hostname primary need the admin role and are audited.
- **Domain claims.** A sending, link or web domain is held by proof, not by who added it first. Once it has verified (or been active), it stays its Channel's (`proven_at`, migration 0065; a service change or a certificate renewal doesn't undo it). Until then another Channel can take it over only by publishing `_swarm-claim.<name>` = `swarm-claim=<token>`, a token bound to that Channel and name that the 409 names, however long ago the claim was added. There is no free takeover once the re-check window (a week for sending and link domains, two weeks for web hostnames) ends: a link or web domain verifies from a CNAME that is the same for every Channel, so a newcomer without proof would inherit the earlier owner's DNS. The same proof is asked for when no claim is in the way but the name's DNS already points at the platform: an earlier owner who removed the domain but not its record would otherwise hand it to whoever adds it next, because the hostname service activates it at once. Pointing at the platform means a CNAME chain with any hop at the track host or `SITE_FALLBACK_ORIGIN` (up to 8 hops, followed as Cloudflare follows them; a loop points nowhere, a longer chain counts as pointing here), or, for a name with no CNAME at all or the name a chain ends at, exactly one of those targets' A records, as from a flattened CNAME or an ALIAS at a bare domain (any overlap alone doesn't count, because Cloudflare's anycast addresses are shared). Link domains and web hostnames are checked against both targets, because both are custom hostnames in the same zone and a record left for one activates a name added as the other. Its 409 says the name already points at Swarm rather than that another Channel added it. A first-time owner adds the domain before publishing the CNAME, so they aren't asked. A lookup that fails refuses the add (503) rather than wave the name through. Known limit: a leftover record proxied from another Cloudflare zone (orange to orange) answers with no CNAME and that zone's own addresses, so exact A matching can't see that it reaches the platform. Removing a domain or a web hostname deletes its custom hostname at Cloudflare too, so nothing is left there to serve. The real owner can always publish the TXT record. The claim that gives way is deleted with its copy at the mail or hostname service, and audited in its own workspace (`sending_domain.released`, `web_domain.released`). Each name has one row, because the services hold one copy of a name and `sending_domains` can't be rebuilt without its cascading children.

## Payments (Phase 5)

- **No card data.** Readers pay on Stripe Checkout and manage payment methods in the Stripe Billing Portal, both on the Channel's own connected account. Swarm stores Stripe ids, amounts and statuses, never card details.
- **Connect.** Standard accounts over OAuth with the `read_write` scope. The OAuth state is a token signed with `AUTH_KEYS` (purpose `stripe-connect`, 30 minutes) naming the Channel and the operator who started the flow. The callback accepts it only from that operator's own session, re-checks that they still have the admin role on the Channel, and refuses a Stripe account already connected to another Channel. A refused account has the platform removed again (OAuth deauthorize), unless a Channel is connected to it through Connect. Connecting, changing tax or the grace period and disconnecting need the admin role and are audited; viewers can read the status. A Channel the operator can't see answers 404. The platform never sets an application fee.
- **Webhook.** `POST /api/v1/stripe/webhook` reads the raw body and checks `Stripe-Signature`: every `v1` signature against every secret in `STRIPE_WEBHOOK_SECRETS`, in constant time, within 300 seconds either way. A missing header, a wrong or stale signature or an empty secret list is a 400; there is no unsigned or "dev" mode, and an empty secret fails env validation when `PAYMENTS=stripe`. The endpoint skips the CSRF check and session loading (it carries no cookie); its signature is its only credential.
- **PayPal webhook.** `POST /api/v1/paypal/webhook/<channelId>` is answered by PayPal's own signature check on the Channel's credentials, so before anything costs a call it checks for free: the five signature headers, a transmission time within four days, a certificate URL on an https PayPal host, and a well-formed event (a type Swarm doesn't handle is acknowledged unchecked, since it changes nothing). Each Channel may then ask PayPal for 30 checks a minute (`PAYPAL_VERIFICATIONS_PER_MINUTE`, counted in `usage_windows`); past that, and when PayPal can't be reached, throttles or takes longer than 10 seconds, the route answers 503 so PayPal delivers again, and only PayPal's own refusal answers 400. Access tokens are reused until shortly before they expire.
- **PayPal reconciliation.** Access doesn't rest on every PayPal webhook arriving and finishing. The 5-minute lifecycle job asks PayPal, for a random sample of Channels and at most 4 reads per Channel (`PAYPAL_RECONCILE_READS_PER_CHANNEL`), about checkouts it never reported as activated (the PayPal subscription id is kept on the checkout row) and about a random share of running subscriptions. What PayPal says goes through the same handler as a webhook event, once (`RECONCILE-<id>-<status>` in `paypal_events`): a missed activation grants access late rather than never, and a missed cancellation, expiry or suspension ends or suspends it; a read of a known subscription never re-activates it. The Channel's PayPal settings show how many events never finished. This mapping of PayPal's states has not been run against PayPal.
- **Idempotency.** Every event id is claimed in `stripe_events` before any work, keyed by the account the event came through (`paypal_events` likewise by the Channel whose webhook verified it), so one tenant's delivery can never take over, settle or suppress another scope's claim; a duplicate delivery in the same scope does nothing. A failed event keeps its error and is reprocessed when the provider retries, and so is one whose run died after claiming it (still `received` after 5 minutes, on Stripe and PayPal alike); a retried event that already succeeded is skipped.
- **Tenancy.** An event's `account` must belong to a connected Channel, and every row it reads or writes is scoped to that Channel: an account can't reach another Channel's checkout sessions, subscriptions, customers or account flags. Platform events without an account are ignored, and so is an event whose `livemode` differs from the connected account's (a test-mode event never changes a live account).
- **Checkout references.** The site signs a token (purpose `checkout-ref`, `CHECKOUT_SIGNING_KEYS`, Ed25519; the api checks it with the public key) holding only the random reference of a `checkout_sessions` row written before the session was created, and a mark when the row's Member made the checkout signed in. It travels in the session's metadata (`swarm_ref`), since an Ed25519 token is longer than the 200 characters Stripe allows in `client_reference_id`, which holds the bare reference (a v1 token from before the cutover is read there). The webhook trusts that row (level, price, intent, Gift Pass) and never anything else the session says, which the owner of a connected account could set to anything. An empty, unsigned or foreign reference is ignored. A checkout made with a typed email that matches a Member is credited to that Member, but its new Stripe customer is linked (and so reused by the billing portal and later checkouts) only to a Member that checkout created, or to the Member who made it signed in.
- **Out-of-order events.** Each subscription row remembers the Stripe time of the state it holds; older events don't overwrite it, and a deleted subscription is never revived. Renewals and recoveries re-read the subscription from Stripe.
- **Revocation.** Access ends at the period end when a subscription is canceled, immediately on a full refund or a dispute (and the subscription is canceled on Stripe so it stops charging), and after the grace period (`grace_days`, 7 by default) when a payment fails. Comp and Gift Pass grants end at their end date. Revocations from webhooks are audited with the Stripe event id.
- **Buyers.** Paying does not confirm an address, because anyone can type anyone's address at checkout (and the address a provider reports is the one the payer entered). A checkout never activates, confirms or records consent for an existing Member: a pending Member stays pending until their address confirms, and the purchase is held for them meanwhile. A buyer new to the Channel becomes a pending Member with no consent or confirmation time, a consent record with source `checkout`, and the usual confirmation email (it is sent after the purchase is recorded); the thank-you page tells them to confirm. Only a confirmed address can sign in, so a purchase is usable only by whoever proves the address: a reader who was signed in when they bought, or someone who confirms. Someone who unsubscribed, bounced or complained (or whose address is suppressed) keeps that email status, so paying never re-subscribes a suppressed address to Broadcasts, but still gets what they paid for. Buying a Gift Pass or a tip signs nobody up. Records made before this change (migration `0095`) may say a checkout gave consent: a buyer it added was made active with `consent_at` and `confirmed_at` set by the checkout, and has no consent record with source `checkout` (source `checkout` is only written since). Nothing corrects them, since no deployed install held real data then; an admin who has some can find them as subscribers whose source is a checkout (`members.source_json` kind `checkout`) with no `checkout` entry in their consent history, and ask them to confirm.
- **Gift Passes.** The claim link carries 256 random bits; only its SHA-256 is stored. It is mailed to the recipient (or the buyer), expires after 90 days unclaimed, and stops working when the payment is refunded.
- **Trials** are card-required and limited to one per email per Channel (`trial_claims`).
- **Who a signed-in purchase is for.** Gift claims never start a session (see below), so a claim link can't plant one; a session can still end up in a browser its owner doesn't control in other ways (a shared computer, a forwarded sign-in link opened before its owner), so a session alone never credits a purchase to its Member or reuses their saved Stripe customer. No session carries a "started from a gift claim" mark, since none can be. Every checkout form shown to a signed-in reader (plans, gifts, tips, the join plan step, goods) names the account ("Buying as …") with a sign-out button to buy as someone else, and carries the account's id; only a checkout posted with that id matching the session is the reader's own. Anything else is treated like a signed-out checkout. The plans page is `private, no-store` for a signed-in reader, since it names them.
- **Checkout** (`POST /_swarm/checkout` on the site) refuses cross-site posts, is rate limited (`CHECKOUT_LIMITER`, 10 a minute per IP) and needs Turnstile. The level and price must be the Channel's own, active and sellable; archived levels and scheduled prices are never sold. Success and cancel URLs are built with the URL API on the Channel's origin.
- **Gates by level.** A paid reader's edge cache key carries their level, so a page rendered for one level is never served to another. Anything that depends on one reader (metered reads, the meter-spent Gate, soft-Gate pass-throughs, gift links) is `private, no-store`. An anonymous visitor's meter lives only in their meter cookie (`__Host-swarm_meter`): a signed list of the posts read this period on this publication, with no identifier, HttpOnly and SameSite=Lax, set only when a free read is used and lasting one period at most. Nothing about anonymous visitors is stored on the server, so a client can't grow the database through the meter and no reading history outlives the period. A signed-in Member's meter is rows keyed by their Member id, kept for the current and last period (`METER_READS_KEEP_MS`, 62 days) and deleted with the Member. The anonymous meter is a speed bump: clearing the cookie resets it. Bots and prefetches never use a meter.
- **Gift claims and gift articles.** A Gift Pass is claimed in one conditional update, so it can't be claimed twice. Claiming proves only the address the claim link was mailed to (the recipient, or the buyer when there is none), and only there does claiming count as consent. Claiming never signs the browser in, whatever address is typed: a buyer can name their own address and send the link to someone else, and a session for the buyer's Member would make that person read, and check out, as the buyer. The gift lands on the Member, who signs in with the usual emailed link (proof of the mailbox), and a browser already signed in as another reader stays signed in as them. Any other typed address gets the gift on its Member; if it is new to the Channel, the Member is created pending with the usual confirmation email. So a gift link can't plant a session in anyone's account, existing or future. Gift article links are random tokens stored as hashes, last 30 days and are capped at 5 per Member per month inside the insert. A link opens its post at most 50 times (`GIFT_ARTICLE_MAX_READS`, counted in the same statement as the cap), and stops when the Member who shared it can no longer read the post themselves (a cancellation, refund or lapse), when they stop it (`POST /_swarm/gift-article/revoke`, offered on the page that shows the link), or when the publisher stops every link to a post (`POST /api/v1/dispatches/{id}/gift-links/revoke`, editor role, audited). The publisher sees each link's reads at `GET /api/v1/dispatches/{id}/gift-links`.
- **Member Center billing** acts only on the subscription of the Member the signed link names; a form can only pick that Member's own price choices.
- **Mail apart from membership.** "Stop emails, keep my membership" (`members.emails_off_at`, migration `0115`) is a mail choice, not a status: posts and automation emails leave the Member out (the snapshot, the claim just before the provider, Flow email steps, audience counts and the inactive-reader cleanup all read it), while mail that belongs to the service (receipts, sign-in links, billing notices, confirmations) still goes, and the status, reader sessions and paid entitlement are untouched. Only the Member changes it, from either kind of Member Center link.
- **Two kinds of Member Center link.** The footer link in every email travels with forwarded mail, mail-gateway logs and shared inboxes, so it opens a summary only: a masked address, the plan and its renewal, no names or profile values (encrypted ones included) and no invoices. From it a Member can pause, resume, pick Rosters and the digest, stop emails and keep their membership (or turn emails back on), unsubscribe (rejoining undoes it), cancel at period end and keep the membership. Everything else needs a Member Center link emailed on request at `/m` (claim `e`) and opened within an hour: a level change (it charges the saved card), opening the Billing Portal, canceling a PayPal subscription (it can't be undone), seeing or changing the profile, seeing invoices, turning tracking off (it deletes the recorded opens and clicks) and turning off older links. From a footer link those actions only email the Member a fresh one. The Billing Portal's return address is `/m/back`, which carries no token, so no Member Center link is handed to Stripe. A billing, profile, unsubscribe, emails or tracking change made through either link is mailed to the address (category `member_change`, at most six an hour per Member) with a fresh link to look or put it back; a PayPal cancellation and deleted tracking history can't be put back, and the notice says so. A Member can turn off every older link at once (`members.member_links_after`): links issued before the one in use then stop working.

## Growth (Phase 6): Ask, Signup Journeys and Smart Prompts

- Poll links are per recipient and purpose-scoped (`ask`, `{m, o}`, 90 days). A Member Center, confirm or survey-page token is refused at `/a/<token>`, and a poll token is refused everywhere else. The GET only shows a confirm page; the answer is recorded on the POST, so link scanners record nothing. One answer per Member per question (a database UNIQUE); closed and draft Asks refuse answers.
- The survey page records answers only for a signed-in reader of the Channel or a survey-page link for that one Ask. Posts must be same-site and are rate limited.
- Ask answers copy only into unencrypted fields of the Ask's Channel, checked when the question is saved and again when the answer is written.
- Signup Journey tokens carry the address sealed with FIELD_KEYS, never in clear. Answers are written only to a Member created by that sign-up, so typing someone else's address into a form can't change their profile. The variant is the same for a known and an unknown address.
- Smart Prompt scripts are inline, first party and nonce'd under the site CSP; nothing is loaded from elsewhere. The dismissal cookie holds prompt ids and cooldown ends only (HttpOnly, SameSite=Lax, `__Host-` over https); dismissal posts must be same-site and return paths are same-site paths.

## Deliverability Center (Phase 7)

- **DMARC aggregate-report parsing.** Reports are untrusted mail from anyone who can send to `dmarc+<id>@<DMARC_MAIL_DOMAIN>`. The message is read up to 10 MB (larger ones are dropped unread), MIME nesting stops at 5 levels and 50 parts, the attachment at 5 MB and the decompressed XML at 25 MB, counted while inflating so a zip bomb or a lying size header stops at the limit. The zip reader takes at most 5 entries and refuses ZIP64 and encryption. The XML reader is hand-written and bounded (depth 32, 400,000 elements); a `DOCTYPE` is refused, so there are no DTDs, external entities or entity expansion, and only the five predefined entities and character references are decoded.
- **Which domain a report is for** comes from the address it was sent to (`dmarc+<sendingDomainId>@`), and the report's own `policy_published/domain` must match that domain; anything else is dropped. A report can't write to another domain or workspace.
- **Dropped, not rejected.** Bad input is logged and accepted, so reporters don't retry forever and the response reveals nothing. Raw files are kept in the private R2 bucket `REPORTS`, keyed by domain, day and content hash; reports are unique per domain, reporter and report id, and at most 100 are stored per sending domain in any 24 hours.
- **Dedicated sending** changes (own configuration set, dedicated IP pool) are admin and up, plan-checked (`plan_required` on free; dedicated IPs from Pro), audited, and idempotent. The dev provider that fakes them rides on `MAIL_ADAPTER=dev`, which is refused outside development and test.

## Privacy Center (Phase 7)

- **Requests from Members** are POSTs from the Member Center page, so they need its signed link (purpose `member`) and the page's origin, and share its rate limit. That link is in every email footer and works for 30 days, so it proves only that someone holds an email, which may have been forwarded. An export is still safe on it (the file's link goes to the address). Deleting is not: the page's confirmation only mails the address a single-use link (purpose `dsr-confirm`, `CAPTURE_KEYS`, 24 hours, one row in `dsr_confirmations` used atomically, whose id is 52 random bits and which also needs a 128-bit nonce that only the emailed link carries and the row keeps only as its SHA-256, so neither the signing key nor a read of the database is enough to confirm someone else's erasure; requests from the public page (`dsr-address-confirm`, which names its workspace) work the same way); its page changes nothing, and only that page's same-origin POST files the erasure. An address Swarm can't mail can't confirm that way: its erasure always waits as `pending` for an admin to approve, whatever link opened the page. A forwarded footer link shows the address to whoever holds it, and nothing a link carries proves who holds it: a link emailed on request a moment ago can be forged by anyone holding the member signing key, so it counts for no more (the exception that let one run without review is gone). A Member's request confirmed from their inbox still runs a pending one filed from a forwarded link rather than being turned away by it. The pending request has source `member_center_unverified`, so the Privacy Center warns the admin that the link may have been forwarded. A request covers the address across the workspace; the address is sealed by the vault on the request (bound to it) while it is open and cleared afterwards, leaving only its keyed marker.
- **Export links** (purpose `dsr-export`, 7 days, `DSR_EXPORT_SIGNING_KEYS`: jobs signs, capture checks with the public key, and the link's workspace must be the request's) open a page; only its same-origin POST sends the file, with `Cache-Control: private, no-store` and `Content-Disposition: attachment`. Files are deleted when the link expires, and when the address is erased.
- **Operator requests** need the admin role in the workspace and are audited without the address. Approving an erasure needs the literal confirmation `erase`.
- **Erasure** is a hard delete plus scrubbing of every table that can hold the address or the Member id, checked by a test that greps every column of every table; the address stays suppressed as a hash and every path that adds a Member refuses it.
- **Export destinations** hold the operator's access keys sealed with `FIELD_KEYS` together with their workspace and destination, so a copied value opens nowhere else (older values open once and are sealed again); the API never returns them and audit entries never include them. Endpoints must be public https hosts (the same check as Flow webhooks), and requests are SigV4-signed with the payload hash. What a destination sends is its `scope` (`0111_export_destination_scope.sql`): by default subscribed (active) Members only and no profile field values; anyone else changed since the last run is written as a reduced line (id, status and dates, `reduced: true`) so the copy learns of a departure, and events of people who are not subscribed are skipped. An admin picks profile fields one by one, or all of them (which sends encrypted fields in clear), and can include everyone for a full backup. Sending more people or fields than before counts as repointing (a fresh factor and a notice to the other owners and admins); narrowing does not. Destinations that existed before scopes keep sending everyone with every field (`legacyScope`), and the dashboard says so and offers to narrow them.

## Open Operator (Phase 8): MCP and agent actions

- **Same credentials, same checks.** `/mcp` accepts only `/v2` keys and OAuth access tokens (never the session cookie). Each tool is a `/v2` route run in-process through the router, so its scope, Channel and validation checks are the route's own; the in-process request carries the resolved principal in a `WeakMap` keyed by the `Request` object, which nothing outside the worker can construct. A tool outside the credential's scopes is `403` with an `insufficient_scope` challenge.
- **Origin.** Requests with an `Origin` other than `APP_ORIGIN` are refused (DNS rebinding); no CORS headers are sent.
- **Agent audit log** (all plans): every tool call in `agent_actions`, hash-chained per workspace like `audit_events`, with arguments stored only as a masked summary (personal and secret fields redacted, free text reduced to its length, addresses replaced). Verified on demand in the dashboard, a bounded page of at most 10,000 rows per request (the dashboard follows `nextCursor` to the end; the audit log's `GET …/audit/verify` works the same way); retention `max(plan audit retention, 90 days)` behind a verified anchor.
- **Approvals**: destructive calls through `/mcp` wait for a person by default, with or without Copilot (a direct `/v2` request is not held). Approving needs the admin role, claims the row in one conditional update (exactly once), and re-checks the flags, the credential (unrevoked, unexpired, grant live) and its scope and Channel before running the stored request with an Idempotency-Key. Decisions are audited. Stored requests are cleared once decided, at expiry (daily) and by erasure.
- **Audience-bound tokens.** Every OAuth grant is bound to one RFC 8707 resource, `/v2` (the default) or `/mcp`. `/mcp` accepts only `/mcp` tokens and `/v2` only `/v2` tokens; a token for the other answers `401` ([oauth.md](oauth.md#resource-indicators-rfc-8707)). API keys work on both.
- **Client ID Metadata Documents.** Unregistered MCP clients name themselves with an https URL. The document is fetched only on the consent page for a signed-in operator (never by the unauthenticated `/oauth/authorize`), through `outboundUrlProblem`, with no redirects, 5 KB and 5 seconds at most, cached by URL, at most 20 new fetches per operator per hour. Public clients only (PKCE as always), no secret in the document, the document's `client_id` must equal its URL, redirect URIs https or loopback http and matched exactly (any port on loopback). The consent page marks such clients "Unverified app" with the document's host, and warns about loopback redirects.

## Account security (Phase 7)

Routes: `workers/api/src/routes/security.ts` and `sso.ts`; the session rule in `lib/session.ts`, enforcement in `lib/access.ts`; constants in `packages/domain/src/p7-security.ts`; tables in `0012_platform.sql` and `0017_security.sql`.

### Second factor

- **Who must have one.** Owners and admins, everywhere. A workspace owner can set `require_2fa = 'all'` (audited as `workspace.require_2fa_changed`) to cover every seat. An operator with seats in several workspaces is held to the strictest. Every new operator owns their first workspace, so in practice every account needs a second factor once its grace period ends; teammates who only hold non-admin seats (for example people provisioned through SSO) do not, unless a workspace requires it.
- **Grace period.** The first time a second factor is required of an operator who has none, `operators.mfa_required_since` is set (and it is cleared when nothing requires one any more). For `MFA_GRACE_DAYS` (14) they work normally and the dashboard shows when to add one. After that, every session of theirs that has not proved a second factor is in the `enroll` state: it can only read its own status and add a passkey or authenticator app. The column is bookkeeping, like `last_seen_at`: it is written when a session is loaded or created and changes no permission by itself. This is also why existing sessions and tests that sign in with QuickPass alone keep working: a new owner is inside their grace period.
- **Pending sessions.** A first factor (QuickPass, Google, or SSO without an MFA claim) for an operator who has a second factor, or whose grace period is over, creates a session with `mfa_pending = 1`. Adding the first factor also marks every other session that never verified as pending, so an old session or a lost laptop can't skip the new factor. The state (`ok`, `verify`, `enroll`) is worked out on every request from the cached session facts, so a grace period that ends while an entry is cached takes effect at once. It fails closed: a session that has not proved a second factor is `verify` whenever the operator has one, whether or not its row was marked pending (a sign-in that races the first factor being added is not).
- **What a pending session can do.** `requireAuth` answers `401 mfa_required` to everything except the second-factor steps (`/api/v1/auth/second-factor/*`), `GET /api/v1/auth/session` (which reports `secondFactor.state` and the `methods` available, and lists no workspaces) and sign-out. An `enroll` session can also read `GET /api/v1/security` and add a passkey or TOTP. A `verify` session can't add a factor (that would let a first factor alone replace the second) and can't sign out everywhere.
- **Verifying** flips the session (`mfa_pending = 0`, `mfa_method`, `mfa_verified_at`) and rotates its token: the cookie is replaced, the old token stops working and its cache entry is deleted.
- **Attempt limits.** Failed checks are recorded in `mfa_attempts`: 5 per session per 15 minutes and 10 per operator per hour, then `429 rate_limited`, whatever the method.
- **Step-up.** Adding a factor when one exists, removing a factor and creating new recovery codes need a factor of the operator's own (passkey, TOTP or recovery code) proved on this session within `MFA_STEP_UP_MINUTES` (10). An identity provider's MFA claim lets a session sign in but never counts here, and an SSO session with that claim can't sign out everywhere until it proves an operator-held factor. Otherwise the API answers 403 with the detail `secondFactor: step_up_required`, and the dashboard asks for a check and retries.
- **Account change mail.** Adding or removing a passkey or the authenticator app, creating new recovery codes, signing out everywhere and undoing a first factor each email the operator at the account's address (`account_security_changed`), outside any session. A mailbox holder can read it too; the mail tells the real person, it does not stop someone who controls the mailbox.
- **Undoing a first factor.** Someone who gets into the mailbox for a moment could sign in and add the account's first factor, which then holds the real person's other sessions behind it. So the mail about a first factor carries a "This wasn't me" link (`/sign-in/undo-factor#token=…`, in the fragment so it stays out of logs), valid `FIRST_FACTOR_UNDO_DAYS` (7) and usable once; only its SHA-256 is stored (`factor_undo_tokens`, `0114_first_factor_undo.sql`). Opening it changes nothing; confirming on the page (`POST /api/v1/auth/undo-first-factor`, no session needed) removes every passkey and authenticator app added since that factor, and the recovery codes once none is left, signs out every session, and sets `operators.email_signin_required_at`: Google and SSO sign-ins are refused (`email_signin_required`) until a QuickPass sign-in clears it. It is recorded as `operator.first_factor_undone` (account activity, and the event, without detail, in each workspace) and the person is emailed. Someone who keeps access to the mailbox can use the link too, or sign in again; the link gives the real person a way back, it does not lock a mailbox holder out.
- **The last factor.** Removing the only passkey or authenticator app is refused (409) while a second factor is required. When the last factor goes, the recovery codes go with it.

### Passkeys

- `@simplewebauthn/server` verifies registrations and assertions inside the worker (WebCrypto only, no Node built-ins). The relying party ID is the hostname of `APP_ORIGIN` and the only accepted origin is `APP_ORIGIN`.
- Challenges are random, stored in `webauthn_challenges` for 5 minutes and spent atomically by the verifier, so a response can be used once, even when verification then fails.
- Attestation is `none` (no device attestation is collected). User verification is preferred, not required.
- The signature counter must move forward (both zero is allowed for authenticators that keep no counter); the update is conditional, so two racing assertions can't both pass. A counter that does not advance is refused and logged.
- An assertion is only checked against the signed-in operator's own credentials.
- Passkeys are a second factor only. Passwordless sign-in with a passkey as the first factor is not offered: the first factor stays an address the operator controls (QuickPass, Google or SSO), which keeps account recovery and the new-device email meaningful.

### TOTP and recovery codes

- RFC 6238 with HMAC-SHA1, 6 digits, 30 seconds, implemented with WebCrypto. The secret (160 bits) is sealed with `FIELD_KEYS` and only shown while setting up. The QR code is drawn in the browser from the `otpauth://` URI; no third-party service sees it.
- Codes one step either side of now are accepted, and `last_step` only moves forward (a conditional update), so a code, or an older one, is never accepted twice.
- Ten recovery codes (60 bits each, `xxxx-xxxx-xxxx`) are issued with the first factor and shown once. Only `sha256(operator id : code)` is stored. Each works once (spent atomically); using one is audited (`operator.recovery_code_used`) and emails the operator with the number left. Creating new codes replaces all of them.

### Sessions

- **Whose link it is.** Anyone can ask for a QuickPass link to their own address and send it to someone else (login CSRF), so the continue page names the address it signs in as before the click (`POST /api/v1/auth/quickpass/peek`, which spends nothing), and says so when the browser is signed in as another operator. Consume then needs `confirmEmail`, the address the page showed, unless the request carries `__Host-swarm_quickpass` (HttpOnly, SameSite=Strict, 10 minutes), which `POST /api/v1/auth/quickpass` sets in the browser that asked for the link. Its value is derived from the token, and every 202 sets one, so it says nothing about whether the address has an account. A link opened on another device still works after the confirmation. When continuing changes who is signed in, the page ignores `return` and goes home, so the sender does not pick the page.
- **Signing in again** in a browser that still holds a session cookie (QuickPass, Google or SSO, as the same operator or another) revokes the session behind the old cookie, so a copy of that token stops working when the browser's cookie is replaced.
- **Sign out everywhere** revokes every session of the operator (by default all but this one) and deletes each cached copy, so they stop working on the next request rather than after the 5-minute cache.
- **Revocation wins over the cache.** The session cache (5 minutes in KV) holds only derived facts. Every request also reads the session row, so a revoked session is refused on its next request even where a cached copy survives, including one written back by a request that read the row just before the revocation. The extra cost is one indexed D1 read per request.
- **Account activity.** Sign-ins, factors added or removed, recovery codes created or used and signing out everywhere are recorded for the operator in `account_events` (`0110_account_events.sql`) with the network prefix (`/24` or `/48`) and browser, and listed under Settings → Security → Account activity (`activity` on `GET /api/v1/security`), which only the operator can read. They are deleted after `ACCOUNT_EVENT_DAYS` (400). Each workspace the operator has a seat in gets a reduced copy in its audit log (`lib/account-events.ts`): the action, the method (`quickpass`, `google`, `sso`, `passkey`, `totp`, `recovery`) and the time, with no network prefix, browser or other detail, so an operator who works for several clients does not tell each client where they sign in from. The copy is a normal hash-chained entry. Entries written before this change keep the network prefix they recorded; the chain is not rewritten, and they go with the plan's audit retention.
- **New-device email.** A sign-in from a browser family and network (`/24` or `/48`) not seen in the operator's sessions in the last 90 days emails them, through the QuickPass mail path. The first sign-in ever sends nothing. The mail's "This was not me" button only opens Settings → Devices; nothing changes on a GET.

### SSO (Pro and up, off by default)

OIDC is built but off by default, and it has not been tested with a real identity provider: only with the fake one in `workers/api/tests/sso.test.ts`. The `sso` flag is read at platform scope, since sign-in happens before any workspace is known, so a workspace or Channel override does nothing. While it is off, every SSO route answers `404 feature_disabled` (sign-in start and callback, connections, domains and domain verification), the dashboard offers nothing, and connections already stored stay in the database without effect. Turning it on: [self-hosting.md](self-hosting.md#single-sign-on).

- **OIDC only for now.** Authorization code with PKCE (S256), a random `state` bound to the browser in a signed, 10-minute `__Host-` cookie, and a `nonce`. The ID token is verified against the issuer's JWKS (RS256 or ES256, cached an hour per connection, issuer and JWKS URL, and refetched once on an unknown key id): issuer equal to the configured one, audience (and `azp` when there are several), expiry, not-before. The discovery document's `issuer` must match exactly and its authorization endpoint must be https outside development. The issuer (when saved and on every fetch), the token endpoint and the JWKS URL go through `outboundUrlProblem`, and redirects from them are not followed (a 3xx is a failure). The client authenticates with `client_secret_basic` (or `client_secret_post` when that is all the provider offers); the secret is sealed with `FIELD_KEYS` and never returned.
- **Domain capture.** A connection claims domains; a claim captures sign-in only after a TXT record `_swarm-sso.<domain>` = `swarm-sso=<token>` is verified through the DNS resolver. A domain can be verified for one connection on the whole platform (a unique index); unverified claims block nobody. A proof vouches for the identity provider the connection had when it was made: changing the issuer or client ID clears every domain's verification, gives it a new token (so the old TXT record proves nothing) and puts the connection back to draft. Only owners can change the provider once a domain is verified or anyone has signed in through the connection, since it can sign in every captured address, the owner's included; admins can still change the client secret. The same rule holds when the route is deleting the connection and creating another: domains a workspace releases (deleting the connection, or removing a proven domain) are recorded in `sso_released_domains` with the provider they vouched for, owners are emailed, and for `SSO_RELEASED_DOMAIN_DAYS` (30) proving one again for a different provider needs an owner (403 for admins). Setting the same provider up again, or a domain the workspace never proved, stays an admin task. Deleting, disabling and ending enforcement stay admin actions.
- **Proof is re-checked.** A verified domain's TXT record is looked up again at sign-in once its last check is older than `SSO_DOMAIN_RECHECK_HOURS` (24), when another workspace tries to verify the same domain, and every day by the jobs worker for every verified domain, whether or not anyone signs in (`packages/engine/src/sso-domains.ts`, the five-minute cron, `SSO_RECHECK_BATCH` (25) domains per run, through the jobs worker's own `DNS_RESOLVER`). When it is missing (or the lookup fails) the proof is marked failing (`sso.domain_proof_failing`, and the workspace's owners and admins are emailed once) but keeps working; once it has failed for `SSO_DOMAIN_LAPSE_DAYS` (7) it lapses (`sso.domain_lapsed`): the domain stops capturing sign-in, and a workspace that proves it now can verify it. A record seen again clears the failure.
- **What an IdP may assert.** `email_verified` must be true, and the address must be on a domain the connection verified. An identity provider can therefore never sign anyone in as an address outside its own proven domains.
- **Whom an IdP may sign in.** Only an operator who holds a seat in the connection's own workspace, or someone new (no account yet, or an account with no seat anywhere) when the connection gives seats just in time. An operator on a captured domain who is seated only in other workspaces is refused (`sso_no_seat`): the sign-in is audited to the connection's workspace (`sso.sign_in_refused`, with the address) and the operator is emailed (`sso_sign_in_refused`). To use SSO they are invited to the workspace first, and accepting needs a sign-in of their own. A provider therefore can't take over an account seated elsewhere.
- **How far an SSO session reaches.** Until the session proves a factor of the operator's own (passkey, TOTP or recovery code), it reaches only the connection's workspace; any other workspace answers 403 with the details `sso: sso_other_workspace` and `secondFactor: step_up_required`. Proving the factor, or signing in with QuickPass or Google, lifts the limit. Every path that grants workspace authority applies this and the enforced-SSO rule: `requireWorkspace`, `requireChannel`, the route policy (`lib/policy.ts`) and the Stripe Connect callback.
- **When trust in the provider ends.** Deleting, repointing or disabling a connection revokes every session signed in through it. Such a session also reads as signed out while the platform `sso` flag is off, and `SSO_SESSION_MAX_HOURS` (12) after its sign-in however active it is, so the operator signs in again.
- **Linking and just-in-time seats.** An identity is `(sso, connection, sub)`. A `sub` is unique only at the provider that issued it, so changing the issuer or client ID deletes every identity linked through the connection, and a link counts only while the domain of the address it was made with is still verified for the connection (otherwise it is dropped and the sign-in matches by address). The first sign-in links an existing operator with that address who holds a seat in the workspace, or creates one (without a personal workspace) when the connection has a `jit_role`; a seat with that role is added for a new operator or one with no seat anywhere (`seat.provisioned`, audited). Only owners can set `jit_role = admin`. Without JIT, a new address is not signed in. JIT does not need an invite, even on an invite-only Swarm: `0032_instance.sql` documents SSO as a separate admission path.
- **Enforced connections.** With `enforced`, a session of a person whose address is on a domain the connection captured, and that did not come through the connection, can't enter its workspace (403 with the detail `sso: sso_required`). Teammates on other domains are not covered: they can't sign in through the provider at all. Owners are exempt, so a broken identity provider can't lock a workspace out. Changing `enforced` or the connection's status drops the cached session facts of the captured people, so it applies on their next request. Standing credentials (API keys and OAuth grants) are not sessions and are not covered by enforcement: they follow their own lifecycle (see "Standing feeds"), and admins review them under Settings → Developers. It applies only while the `sso` flag is on: with the flag off nobody can sign in through the connection, so enforcing it would lock its people out.
- **Starting a sign-in.** Only the dashboard can start one. The state cookie is the callback's only tie to the browser, so a start any site could trigger would let it sign a visitor into a connection it runs (login CSRF), ending the visitor's own session. The dashboard's "Continue with SSO" submits a hidden form to `POST /api/v1/auth/sso/start` (form-encoded `email` and `return`), which needs `Origin` equal to `APP_ORIGIN` before it sets the state cookie: browsers send Origin on every form post, including those (Safari before 16.4, Firefox before 90, some embedded webviews) that send no `Sec-Fetch-Site`. Its success answer is a small no-store page that goes on to the identity provider (meta refresh and a link) rather than a redirect, because browsers apply the dashboard's `form-action 'self'` to redirects after a form post. This one route skips the general CSRF middleware (`lib/csrf.ts`), which would refuse a form-encoded body, and checks Origin itself, more strictly, so a refusal is the same redirect to sign-in with `sso_start` as the GET's. `GET /api/v1/auth/sso/start` stays for existing links: it needs `Origin` equal to `APP_ORIGIN`, or no Origin and `Sec-Fetch-Site: same-origin`.
- **SSO and the second factor.** An SSO sign-in counts as the second factor for sign-in only when the ID token asserts MFA: `amr` contains `mfa` (RFC 8176) or `acr` is the OpenID PAPE multi-factor policy. Otherwise it is a first factor like any other. The claim never stands in for the operator's own factor for account changes, standing feeds or other workspaces (above).
- **Plan.** Creating or activating a connection needs `PLAN_LIMITS[plan].sso` (`plan_required` otherwise); a workspace that drops below Pro stops capturing sign-ins.

### Instance admins

`instance_admins` can change install-wide settings (sign-up, mail, sending limits, platform features, website code and DeBounce grants). That needs at least what platform staff need (`lib/instance-admin.ts`): a factor of the operator's own proved on this session (403 `secondFactor: factor_required` without one, `step_up_required` for an SSO-asserted or unproved session), whatever seats they hold, with no grace period; a second factor is also required of every instance admin in the session facts. A change (any PUT under `/api/v1/instance`) needs that proof within `MFA_STEP_UP_MINUTES`, is logged (`instance setting changed`) and is emailed to every other instance admin (`instance_setting_changed`). Each change is also written to the install's own audit log, `instance_audit_events` (`0113_instance_assurance.sql`, `packages/db/src/instance-audit.ts`): one hash chain for the whole install, built like the workspace chain, with who made the change, the path and what it asked for (values of fields named like secrets are not recorded). Instance admins read it, newest first a page at a time (`cursor`, `nextCursor`), with a check of the whole chain from its first event, at `GET /api/v1/instance/audit`, and in the dashboard under **Settings → Instance → Instance audit log** (when, who, which setting and the fields it changed, and whether the chain is intact); an edited or deleted past entry shows as `ok: false` with the first broken `seq`. A chain has no anchor outside the database, so deleting the newest entries is not detected. Workspace-level grant changes keep their workspace audit entries too. Recovery when the only instance admin loses their factor is the command line: [self-hosting.md](self-hosting.md).

### Standing feeds

API keys, webhook endpoints and export destinations keep sending a workspace's data after the session that set them up has gone, so they follow the authority behind them rather than any session (`packages/engine/src/feed-authority.ts`, `migrations/0086_feed_authority.sql`).

- **Setting one up.** Creating an API key, a webhook endpoint or an export destination, and repointing one (a key's scopes or publications, an endpoint's URL or publication, a destination's endpoint, region, bucket, prefix or keys, or a scope that sends more people or fields), needs a factor of the operator's own (passkey, TOTP or recovery code) proved on this session within `MFA_STEP_UP_MINUTES` (10): 403 `secondFactor: step_up_required` otherwise, and `secondFactor: factor_required` for an operator with no factor at all, who can't set one up. An identity provider's MFA claim does not count. The dashboard asks for the check and retries. Every other owner and admin of the workspace is emailed (`standing_feed_changed`) with what was set up and where it points (the URL, the bucket, the key's scopes); the audit entry of a repoint records the new target.
- **Whose authority.** Each endpoint and destination records who confirmed it (`confirmed_by`: whoever created, repointed or adopted it), and a key the admin who stands behind it (`created_by`: its creator, or whoever last changed it). It works only while that operator holds an owner or admin seat in the workspace, its publication is not deleted and the plan includes it. Otherwise it is suspended, not deleted: export runs skip it, webhook fan-out gives it no deliveries and a delivery already queued is canceled, and the key is refused (401). The API shows `suspendedReason` (endpoints and destinations) or `status: suspended` (keys), and the dashboard says why. An admin keeps it by confirming it (`POST …/confirm`, or changing the key), with the same fresh check, and then stands behind it; or removes it. Events that happen while an endpoint is suspended are not sent to it later. While a destination is suspended, the `member.deleted` markers it has not written are kept (they hold a Member id and a time only).
- **Through /v2.** An API key or OAuth grant can only propose a webhook endpoint: it is stored with `proposed_via` and `proposed_by_id`, receives nothing (`suspendedReason: unconfirmed`) until an admin confirms it in the dashboard, and stops for good if that key or grant is revoked. Changing its URL or publication through /v2 makes it a proposal again. The owners and admins are emailed when one is proposed.
- **When an admin's authority ends.** Demoting an admin below admin, or removing them, withdraws the invites they sent that are still pending (`invite.revoked`, `reason: inviter_demoted` or `inviter_removed`), and an invite is accepted only while whoever sent it could still send it. The remaining owners and admins are emailed which keys and feeds are now suspended (`standing_feed_suspended`). Removing a seat still revokes that teammate's keys and grants outright (Teammates leaving).
- **Pausing everything at once.** For an incident, Settings → Security → **Pause all outbound feeds** (`POST /api/v1/workspaces/{workspaceId}/security/pause-feeds`, `routes/pauseFeeds.ts`) sets every export destination and webhook endpoint of the workspace that is not already paused or turned off to `paused`, and answers with each one and where it pointed. Ticking **Also revoke every API key** or **Also disconnect every app** (`revokeApiKeys`, `revokeApps`) revokes those as well. It needs an owner or admin with a factor of their own proved within `MFA_STEP_UP_MINUTES`, writes `feeds.paused_all` plus one entry per feed, key and grant (`reason: feeds_paused_all`), and emails every owner and admin, the actor included, with the list. Nothing resumes by itself: an admin resumes each feed on its own page, after checking where it points. Signing out sessions alone does not stop feeds, by design. Flow webhook steps and bulk exports already running are not covered: pause the Flow or cancel the export.
- **Member exports.** A bulk export (`export_jobs`) checks before each chunk, the last one included, that whoever asked for it still has the admin role on the Channel and that the Channel is not deleted. Otherwise it stops as `failed` with the reason (`export.stopped` in the audit log) and the parts written so far are deleted, so no file is published. An admin can cancel an export that has not finished (`POST /api/v1/exports/{id}/cancel`, `export.canceled`). Finished files are deleted after `EXPORT_TTL_HOURS` (72).
- **Background job messages.** Queue messages are not signed, so consumers take tenancy from stored rows: imports, exports, bulk jobs, Segment refreshes, Flow steps and events, list checks and webhook deliveries each name a row and read workspace and Channel from it. The one message that names a workspace and Channel itself, `email_check`, is refused unless the Channel is a live Channel of that workspace, and only that Channel's Members named by id are checked (`email_check refused` in the jobs log); addresses in a message are ignored. "Check again", which skips the workspace's settings and a result that still counts, is a stored `email_check_requests` row (`0112_email_check_requests.sql`) written by the api for an editor and used once; a `force` flag on a message is not read. A Flow step message for an attempt the run has not reached is ignored, so a forged one can't run a node a second time. Not yet guarded: two copies of an `email_check_run` message for the same running list check can work it at the same time and spend more DeBounce credits on that workspace's own list.
- **What the public workers can queue** (S04-P1-TR-public-worker-queue-narrowing). Capture and events answer the internet, so they have no binding to the jobs queue. Their only queue is `swarm-<env>-public` (`PUBLIC_QUEUE`), and on it the jobs worker accepts two messages: `channel_changed` (a signup, confirmation, Member Center change or bounce changed a Member of this Channel), which names nothing but the Channel, and `email_check` for exactly one Member with the signup rules (`confirmed: true`) and no stored request. The jobs worker derives the rest from stored rows: it marks the Channel's Circles pending and queues their refreshes on the jobs queue itself, and an email check still requires the Channel to be a live Channel of the workspace and the Member to have confirmed. Every batch is read by the queue it came from, never by a body, and every body is parsed against that queue's types and shapes; anything else (a job type, a delivery, an extra field, an id that isn't an id) is logged as `message refused` and acked, never run. A batch from a queue the worker does not know is retried, not run. `pnpm swarm doctor` reports a public Worker bound to any other queue. What a forged message on the public queue can still do: queue a Circle re-evaluation for any Channel (cheap, coalesced while one is pending) and an email check of a confirmed Member under that workspace's own signup rules. The other queues: the api and jobs workers produce on the jobs and webhooks queues, so a `flow_step` attempt or a job id there is only as trusted as those two workers. Public workers still write D1 rows that crons and the jobs worker pick up (`member_events`, `dsr_requests`, `flow_runs` and others); the queue split does not narrow that, and the shared database is the larger grant (see the table below).
- **Existing feeds.** Endpoints and destinations created from the dashboard before this rule are confirmed by their creator as of their creation. Those with no recorded creator (created through /v2, or whose creator's account is gone) wait for an admin to confirm them.

### SAML and SCIM: not scheduled

Ticket **SEC-SAML-1**. SAML and SCIM are not scheduled until there is an identity provider to test with. SAML 2.0 connections are refused by the API (`501 not_implemented`, "use OpenID Connect"). Evaluation on 2026-10-28: `samlify` 2.13.1 (the newest release at least 14 days old) round-trips a signed login response in the workerd test pool and rejects a tampered one, so it works. It was not adopted because:

- it needs `nodejs_compat` on the whole API worker (the bundle imports `crypto`, `fs`, `stream`, `zlib`, `buffer`), which the API does not enable today;
- it adds about 1.1 MB (190 KB gzipped) to the API bundle, a 57% increase;
- XML signature libraries have a history of signature-wrapping flaws (`samlify` and `xml-crypto` both had critical advisories in 2025), and we want that code isolated from the session and tenancy code.

Plan for the ticket: a separate `sso-saml` worker with `nodejs_compat`, reached only through a service binding, that takes the SAMLResponse and returns verified claims to the API; SP-initiated with signed assertions required, audience, recipient, `InResponseTo` and `NotOnOrAfter` checks, and assertion-id replay protection in D1. Until then, every major identity provider also speaks OIDC.

## Copilot (Phase 8)

- **Keys never reach the browser.** The dashboard calls Swarm's API; the platform key (`ANTHROPIC_API_KEY`) and a workspace's own key are used only inside the API worker, for one request.
- **A workspace's own key** is checked with the provider before it is saved, sealed with `FIELD_KEYS` together with its workspace id (a copied value doesn't open in another workspace), shown only as its last four characters, removable, and never returned, logged or written to audit metadata. The log redactor also strips anything shaped like `sk-ant-…`. A saved key that can't be opened stops Copilot with `unavailable` instead of falling back to the platform key.
- **Untrusted content.** Dispatch text goes to the model inside `<dispatch_content>` tags after an instruction that it is data, with tag look-alikes defused. The model has no tools and its output is only shown to the operator, inserted as text (never parsed as HTML), and applied only on a click.
- **No content kept.** `copilot_requests` stores feature, key source, model, status, tokens, latency and who asked; never prompts or results. Provider failures log the request id, error class and HTTP status only.
- **Abuse limits.** Per-operator requests per minute and a per-workspace monthly allowance on the platform key (`COPILOT_PLAN_LIMITS`); a per-operator minute limit with a workspace key; 24,000 characters per request.
- **Training and retention.** No request-level opt-out exists on the Anthropic Messages API; the platform organisation must have zero data retention (a deployment check). Details: [copilot.md](copilot.md).

## Link Hub (Phase 8)

- **No open redirect.** `/_swarm/hub/<linkId>` reads the target from `hub_links` by id within the Channel resolved from the Host header; nothing in the request names a target, and another Channel's link id is a 404. Targets are absolute `http`/`https` URLs without credentials, checked when saved, by a table `CHECK`, and again before each redirect.
- **Cookieless counting.** Clicks are daily counters per link, source and country; no cookie, IP, User-Agent or visitor hash is stored. Bots and prefetches are not counted, and counting runs after the response.
- **The page** is server-rendered with the site CSP and no script; the redirect answers `no-store` and is never cached. Details: [link-hub.md](link-hub.md).

## App Directory (Phase 8)

- **Platform staff** are rows in `platform_staff`, written only with SQL (no route). Staff routes also need a session that proved a passkey, authenticator app or recovery code; QuickPass alone, SSO and the second-factor grace period are not enough. Everyone else gets `404` from them. Decisions are audited in the owning workspace with the staff operator as actor.
- **Install never handles a PKCE verifier.** The Install button opens the app's own `installUrl`; the app makes its authorization request and the existing consent page (admin only) decides. An installed app is an ordinary OAuth grant, revoked the usual way.
- **Listings** are owned by the app's workspace (admin only, cross-tenant `404`); images must be public images in that workspace's Media; URLs pass the redirect-URI checks (https, no credentials or fragment). Any edit takes an approved listing out of the directory until it is approved again, so what is public is what staff saw. A revoked app's listing disappears at once.
- **Manifests** are validated strictly (unknown keys and versions refused) and only describe an app: they cannot change its client type, redirect URIs or scopes. Swarm never fetches images or anything else from a manifest.
- **Community recipes** are sanitised by an allowlist before they are stored: no ids of the Channel, no Circle conditions or field values, no webhook addresses (the Flow's webhook secret is never read), no `mailto:` links, link query strings or fragments, no images, polls, Gates, Smart Blocks or raw HTML, and email addresses redacted. Staff review the full text as a second check. Recipes are shown without the submitting workspace.
- **Public endpoint** (`/api/v1/public/apps`): read-only, approved listings only, 60 requests a minute per client network, `Cache-Control: public, max-age=300`, `Access-Control-Allow-Origin: *` without credentials; it never returns client ids, workspace names or review notes.

## Decisions on reported gaps (Nov 2026)

### Tracked links on the install's link domain

`/c/<token>` on `link.<install domain>` (or a publication's own link domain) redirects to a target a publication wrote, so on a shared install a workspace could use the install's link domain to point at a page the owner would not want their name on. What is in place:

- The token is HMAC-signed (`TRACK_KEYS`) and names a Delivery and a link target; the target must belong to that Delivery's Broadcast (`linkFor`). A bad, foreign or forged token never redirects, and no URL is ever read from the request, so it is not an open redirect.
- Targets come only from rendered email (`safeUrl`: http or https, at most 2048 characters), and the database refuses anything else (`link_targets.url` CHECK in `0003_dispatch_send.sql`), so a redirect can never lead to a `javascript:` or `data:` address.
- The redirect sends `Referrer-Policy: no-referrer` and `Cache-Control: no-store`.

A publication's verified link domain only redirects for that publication's own emails: a click token of another workspace presented on it gets the "link does not work" page (`linkHostServes`), so a branded domain can't be lent to someone else's target. The install's shared link host serves every Delivery.

Not done: a workspace can still send a tracked link to a site of its choice, and once one Delivery exists anyone holding that link can follow it. Stopping that needs either a check of every target against a reputation service or a warning page before every click; the first adds a third party that sees every link, the second breaks normal newsletters. Neither is a cheap, sound fix, so on an install with workspaces you don't know, the advice is: keep sign-up invite-only, give each publication its own branded link domain (Sending & delivery), and remove a workspace that abuses it. An instance-level way to stop one workspace's links is a candidate for later.

### One key for every value sealed with `FIELD_KEYS`

`encrypt`/`decrypt` in `packages/engine/src/fields.ts` derive one AES-256-GCM key per `FIELD_KEYS` secret with a single HKDF context (`swarm:member-fields:v1`) and use it for every purpose: profile fields, the address in join and Signup Journey tokens, Privacy Center request addresses, Flow webhook secrets, Event Webhook secrets, TOTP secrets, SSO client secrets, Copilot, Shorthop and export destination keys. The additional data binds only the key id.

Decision: **leave it as is for now, documented.** The reasons:

1. **What separation would buy.** Per-purpose keys stop a value sealed for one purpose from being opened as another. That matters only where an attacker can hand `decrypt` a value of their choosing. Every `decrypt` reads either a database column the server wrote or a claim inside a token whose HMAC is bound to its own purpose (`join`, the journey token), so the attacker cannot substitute one sealed value for another without write access to D1 or the token keys, which already gives everything away. Where a sealed value could be copied between rows of the same column, the plaintext binds its owner (Copilot, Shorthop and export keys seal `{ w: workspaceId, … }`).
2. **A safe change does not buy it yet.** Existing data cannot be read with a new key, so a versioned format (for example `p2.<purpose>.<kid>.<iv>.<body>`) must keep opening the current format. As long as that fallback exists, an attacker able to substitute values can still use the old format, so separation only starts protecting once every stored value has been re-sealed and the fallback removed. That needs a background re-seal across a dozen tables, which is not small.
3. **Scope.** Doing it properly touches every call site, including `export-sync.ts` and `copilot.ts`, which are being changed for export credential binding at the same time.

What would change the decision: a `decrypt` that accepts a sealed value from a request without a purpose-bound signature, or a feature that copies sealed values between columns. The plan, when it is done: add a `purpose` argument and the `p2.` format with a per-purpose HKDF `info` (`swarm:sealed:<purpose>:v1`) and the purpose in the additional data; open legacy values through the old key; re-seal each table in a jobs batch; then drop the fallback in a later release.

Status (with [the vault](#the-vault)): the row-bound format exists. `sealV3`/`openV3` (`fields.ts`) write `fv3.<purpose>.<kid>.<iv>.<ct>` with a per-purpose HKDF `info` (`swarm:sealed:<purpose>:v3`) and additional data `fv3|<purpose>|<kid>|<row binding>`, where the binding names the row's workspace, Channel, Member and field (or request, endpoint, Flow, operator, connection, destination). Only the vault writes it, and only once `VAULT_WRITE_FORMAT` is `v3`; its cron then seals every stored value again for its own row, and `VAULT_LEGACY_OPEN=off` ends the fallback once nothing is left in the old formats.

### Per-link keys

One `MEMBER_KEYS` value used to sign every link family (confirm, leave, Member Center, asks, data downloads, goods, checkout references, sponsor reports, previews, form stamps, signup tokens, the bot check, erasure confirmations) for every tenant, and five workers held it, so the keyring of any one of them could forge all of them. Each family now has its own keyring (`packages/tokens/src/families.ts`), and the installer's key registry (`packages/installer/src/keys.ts`, `KEY_REGISTRY`) gives a worker only the keyrings it signs or checks:

- **Ed25519 where one worker signs and another only checks**: Member Center links (send, jobs; checked by capture), asks (send → capture), ask pages (capture → site), data downloads (jobs → capture), goods links (→ site), checkout references (site → api), sponsor reports and previews (api → site). The checking worker holds only the public keys (`*_VERIFY_KEYS`), so its secrets can't make one. A signature is 86 characters instead of 43.
- **HMAC where the signer checks too**, or where the code must fit an email address's local part: confirm and leave (`CONFIRM_KEYS`), capture's own tokens (`CAPTURE_KEYS`), form stamps, signup tokens, reader sessions, the api's own state (`AUTH_KEYS`), tracking, unsubscribe codes, and bounce codes, which get their own `BOUNCE_KEYS` so track and the api, which hold `UNSUBSCRIBE_KEYS`, can't make a bounce that suppresses an address workspace-wide.
- **The v2 format** `v2.<purpose>.<kid>.<payload>.<sig>` takes its algorithm and keyring from the purpose, never from the token, so neither can be swapped, and a token's lifetime may not exceed its family's even from a key holder. Families that name a tenant (`c` for a Channel, `w` for a workspace) carry it, for the checking worker to compare with the row it loads.
- **Links from before** (v1, `MEMBER_KEYS`) keep working for their family's own lifetime, at most 90 days (sponsor reports, a year as v1, are cut to 90 days: once the cutover has happened, the jobs worker emails the sponsor of every booking still running or ended within 90 days before it a new link, once, and an admin can send one from the booking at any time), and only if issued before the cutover the installer records (`LINK_LEGACY_CUTOFF`). A holder of the old key could backdate one, but none verifies after cutover plus that window, and each worker loses `MEMBER_KEYS` when its window ends (docs/self-hosting.md "Per-link keys"). A worker that is missing a key, or whose link mode is missing or unclear, refuses to start.
- **Rotation** (`pnpm swarm rotate-keys`) reads the same registry: the new key, or for Ed25519 its public key, reaches every worker that checks before any worker signs with it.

Every family signs and checks with its own keyring (`LINK_V2_SIGNING_READY` is true), and the installer's second pass switches an install over. Who signs and who checks each family:

### What one internet-facing worker holds

Tenant separation is enforced by the queries inside each worker; there is no second boundary at the binding layer. A worker that ran attacker code would hold everything below for every tenant of the install. ### The vault

The vault Worker (`workers/vault`, docs/architecture.md "The vault") is the one place sealed values and service secrets are opened, and where Member Center, goods and signup links are signed for the workers that face the internet.

- **No public surface.** No route, no `workers.dev` name, no preview URL; `fetch` answers 404. api, capture, site and jobs reach it through a service binding pinned to their own named entrypoint (`ApiVault`, `CaptureVault`, `SiteVault`, `JobsVault`). The pinning is fixed at deploy time, so a compromised capture can call only `CaptureVault`'s methods; there is no shared secret to steal. `pnpm swarm doctor` flags a binding through another entrypoint, or from a Worker that should have none.
- **It reads ciphertext from D1 itself** and never opens a value a caller hands it, except tokens it verifies with its own keys (join and journey tokens under `SIGNUP_KEYS`, Member Center links under `MEMBER_SIGNING_KEYS`).
- **It decides who may open what**, from D1 or from a credential or token it verifies itself, never from a caller's claim: a session, API key or OAuth token the api passes through (resolved with the api's own lookups, `@swarm/db` `credentials.ts`: a session still waiting for its second factor, a revoked or expired key, a key whose admin was demoted, one limited to other Channels or without the scope are all refused); a Member Center link (and `member_links_after`; profile fields only within an hour of an emailed link); or a stored job whose row says it may act now (an export that is running and whose creator is still an admin of the Channel, an import or bulk edit that is running, a Flow run at that step, a data request being processed, a pending webhook delivery, a confirmed export destination, a payment event recorded in the last hour). Every Member named must be in the Channel reached. The check is coarse by design; route policy (holds, approvals, step-up) stays in the api, so the vault is a second boundary, not the only one.
- **Values are bound to their row** once written as v3 ([above](#one-key-for-every-value-sealed-with-field_keys)), so a ciphertext copied into a row the attacker may open, of another Member or tenant, does not open there.
- **Service secrets don't leave it.** Provider credentials (a Channel's own Stripe key or the platform key on its connected account, PayPal, Shorthop, the Copilot key, export destination keys, DeBounce) are attached to outbound requests only for a fixed allowlist of (entrypoint, credential, principal, method, path) on the credential's own host (`packages/vault/src/core/proxy.ts`), and only the Copilot calls on it may stream their answer back (`providerStream`, for the api; the same checks, an 8 MB and two-minute cap); a caller's own `authorization` or `stripe-account` header is refused, redirects are not followed, and capture's billing calls must name the link Member's own subscription or customer. Webhook, Flow, Stripe-webhook, TOTP and SSO secrets are used inside it to sign or verify. A new webhook secret or TOTP enrolment is returned once, to show the operator.
- **Links from evidence.** Capture asks for a Member Center link after a confirmation in the last 10 minutes, for the Members of an address that asked (3 an hour per address, 200 an hour per Channel, mailed only), or for a fresh emailed link from a valid one (5 an hour per Member); site for the goods library of an address with a paid order (3 a day) or the links of an order paid in the last day; the api for Members of a Channel it reaches with `sends:write` or as an editor, or after a payment event. Every mint is a `vault_mints` row.
- **Fail closed.** A caller gets `unavailable` after 5 seconds, on any transport error, or when the vault's env is missing a key or a var; it shows no encrypted field and answers 503 to a save that needs a seal, never a weaker path: the dashboard and /v2 show encrypted fields as null and flag the Member `encryptedUnavailable: true` (the dashboard says "Profile fields are temporarily unavailable" instead of showing them empty), the Member Center shows the page with a short note in their place (and no empty inputs a save could clear them with), a sign-up with an encrypted answer is refused with 503 before anything is stored, a provider call (Stripe, PayPal, Shorthop, Copilot, DeBounce) answers as unavailable, a Stripe webhook to a publication's own endpoint answers 500 so Stripe retries, and jobs' exports, imports, Flow steps, data requests and webhook deliveries are retried rather than done without it. A caller's `/healthz` is 503 while the vault does not answer through its binding.
- **Records.** One log line per call (operation, entrypoint, principal kind, tenant, count, decision, time; never a value or credential). Refusals, rate-limit hits and bulk opens are also kept in `vault_audit` for 90 days; a bulk open is also written to the workspace's own audit log, once per job (`vault.export_open`, `vault.dsr_open`, `vault.destination_open`), so the publisher sees it.
- **Erasure markers.** The `FIELD_KEYS`-keyed HMAC that hides erased addresses is computed by the vault for callers, rate-limited per caller and workspace, so it does not become a cheap oracle for testing addresses (jobs' imports and bulk deletes ask for up to 500 at once, against a larger limit). The vault's cron also rewrites markers of older forms.
- **The vault alone holds `FIELD_KEYS`.** api, capture, site and jobs don't have it: their env schemas refuse it on a deployed worker and need `VAULT`, a lint rule (`eslint.config.js`) lets only `packages/vault` and `workers/vault` import the sealing primitives, and `pnpm swarm update` removes the secret from them once they are healthy (for jobs, which has no public host: once its cron has recorded a successful vault ping since the deploy). Each caller hands the vault what proves the request: the api the request's own session cookie, API key (with its IP) or OAuth token, also for Copilot and MCP tools, which run as in-process /v2 requests with their caller's credential; capture the Member Center link, the confirmation just made, or the address typed; site the reader's session or the order; jobs the stored row (export, import, bulk edit, Flow run at its step, data request, delivery, destination, cron task).
- **No ciphertext comparisons or copies outside it.** A value is sealed for its own row, so an import updating an existing Member, a bulk edit (one seal per Member, never one ciphertext for a chunk) or a Flow step asks the vault to seal it for that Member. `field_changed` is decided on plaintext by the vault: it hands back the stored ciphertext itself for an unchanged value (to an anonymous sign-up never), so the caller's write compares strings it was given, not values it can't read.

Residual: the database is shared. A compromised public worker still reads and writes every tenant's plain rows, and the vault's evidence checks rest on rows it could write (a confirm request, a paid order). What it no longer gets is the means to open sealed values, a lasting signing key for the high-value links, or provider credentials; mail credentials stay in the five mail workers.
