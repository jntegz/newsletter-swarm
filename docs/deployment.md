# Deployment

This is the operator reference: every binding, variable and secret, and how to set each one up by hand. Update it in the same change that adds one.

To install Swarm on your own Cloudflare account, use the installer instead: `pnpm swarm` does everything in this file (resources, keys, mail, DNS, configs, migrations, deploys and the owner account). See [self-hosting.md](self-hosting.md). The installer never edits the committed `wrangler.jsonc` files; it renders `workers/<worker>/wrangler.<env>.generated.jsonc` from them and deploys with those.

Every worker has three environments in its `wrangler.jsonc`:

- the default block, for local development;
- `staging`;
- `production`.

The default block names each script `swarm-<worker>-local`, not its production name, so a `wrangler deploy` that names no environment cannot replace a production script with development settings; at most it makes a separate `-local` script, which has no route and no workers.dev hostname, and which most workers' `local` database ids keep from uploading at all. Always deploy with `--env staging` or `--env production` (the package scripts and the installer do).

Development-only routes and fakes need two things: `ENVIRONMENT` of `development` (or `test`) **and** a request on a local host name (`localhost`, a loopback address, or a name under `.localhost` or `.test`), which Cloudflare never routes to a deployed Worker. That covers the api's `/__dev/*` mailbox, the jobs worker's `/__dev/flows/advance` and the site's `/_swarm/checkout/dev/*` fake checkout (with `PAYMENTS=dev`).

The committed `staging` and `production` blocks hold placeholders (`unprovisioned`, hostnames under `swarm.example`, the account id `000000000000`) and no routes. Replace them, or let the installer render them. The template hostnames, site domains and the custom-hostname fallback are all under the reserved `.example` name, so a value left in place fails visibly instead of sending subscribers or tenants to someone else's domain. Older copies used `swarm.page`; it is still refused.

## Local development

```bash
pnpm install
for f in workers/*/.dev.vars.example; do cp "$f" "${f%.example}"; done   # then put random keys in them
pnpm db:migrate:local   # applies migrations/ to the shared local state in .wrangler/state
pnpm dev                # all workers, the dashboard (:5273) and the landing page (:5274)
```

All workers persist to the same `.wrangler/state` directory, so they share one local D1 database and one R2 store.

Locally, mail is not delivered. It lands in the dev mailbox at <http://localhost:5273/__dev/mail>. Sign-in uses Cloudflare's always-pass Turnstile test keys. Sending domains verify at once and every domain reports `p=quarantine` (`DNS_RESOLVER=dev`, `LINK_HOSTNAMES=dev`); none of the dev providers can be selected outside development. To send through Resend from a local run, set `MAIL_ADAPTER=resend`, `AWS_REGION` to the Resend region and `RESEND_API_KEY` in the sending workers' `.dev.vars`.

`TRACK_KEYS` must be the same in `send` and `track`, and `UNSUBSCRIBE_KEYS` in `api`, `send`, `track` and `events`, because one worker signs what another verifies. The same goes for every keyring in [Secrets](#secrets) held by more than one worker, and for an Ed25519 keyring's `*_VERIFY_KEYS`, which must be the public keys of its `*_SIGNING_KEYS`: the `.dev.vars.example` files already agree.

Local sign-up is open: with no `instance_settings` row, anyone can sign up (see [Instance settings](#instance-settings)).

## Provisioning an environment by hand

1. Sign in once: `pnpm --filter @swarm/api exec wrangler login`. Set `CLOUDFLARE_ACCOUNT_ID` if the login can see more than one account.
2. Create the resources and write their ids into the configs: `pnpm provision staging --dry-run` prints the plan, then `pnpm provision staging` (or `node scripts/provision.mjs staging`) does it.
   - The resource list is read from every `workers/*/wrangler.jsonc` block for that environment: D1 databases, KV namespaces (titled `swarm-<env>-<binding>`, for example `swarm-staging-cache`), R2 buckets, and queues including each consumer's dead-letter queue. A resource that exists is looked up, otherwise it is created; `database_id` and the KV `id` are then written into every worker that binds them. Re-running it changes nothing.
   - `--location <hint>` (`weur`, `enam`, …) sets where the D1 database and R2 buckets are created; see [data-residency.md](data-residency.md).
   - Turnstile widgets are not managed by wrangler. Create one in the Cloudflare dashboard for the environment's app, forms and site hosts, pass its site key as `--turnstile-site-key <key>` (written to `TURNSTILE_SITE_KEY` in `api`, `capture` and `site`), and put its secret in with `wrangler secret put TURNSTILE_SECRET_KEY`.
   - Durable Objects are created by deploying `realtime` (step 6). Rate-limit namespaces need no creation: their `namespace_id` is chosen in the config and must be unique per environment (`100x` local, `101x` staging, `102x` production for `api`; `41x1`–`41x3` for `site`).
   - `pnpm check:provisioned staging` fails while any worker config still holds a template value for that environment (`unprovisioned`, a `swarm.example` or `swarm.page` hostname, the account id `000000000000`), or when staging and production share a rate-limit namespace id. Provisioning writes only the resource ids and the Turnstile key, so replace the hostnames, site domains (`PLATFORM_SITE_DOMAIN`, `SITE_FALLBACK_ORIGIN`) and the SNS topic ARN yourself first. The list of template values is the installer's own (`packages/installer/src/config/placeholders.json`), so the manual path refuses what `pnpm swarm` refuses. Run it before every deploy.
3. Add a route for each worker's hostname (see [Routes](#routes)).
4. Apply migrations: `pnpm db:migrate:staging`. This includes `0032_instance.sql`; see [Instance settings](#instance-settings) to make the instance invite-only.
5. Set the secrets listed below.
6. Build the dashboard, then deploy each worker:

   ```bash
   pnpm --filter @swarm/dashboard build
   pnpm --filter @swarm/realtime deploy:staging
   pnpm --filter @swarm/vault-worker deploy:staging
   pnpm --filter "./workers/*" deploy:staging
   ```

   Deploy `realtime` first on a new environment: `api`, `send` and `capture` bind to its Durable Objects (`SendMonitor`, `RateLimiter`, `ApiRateLimiter`) by script name, and those bindings can't be created before the classes exist. Then `vault`: `api`, `capture`, `site` and `jobs` bind to its named entrypoints, and an upload with a service binding to a script that does not exist fails.

The API worker serves the dashboard build from `apps/dashboard/dist` in staging and production. `/api/*`, `/v2/*`, `/healthz`, `/.well-known/*` and the OAuth endpoints `/oauth/authorize`, `/oauth/token` and `/oauth/revoke` run the worker first (`run_worker_first`); `/oauth/consent` is a dashboard page. The dashboard's security headers (CSP, HSTS, framing) come from `apps/dashboard/public/_headers`, which Vite copies into `dist` and Workers static assets applies; a path that runs the worker first gets the worker's headers instead. Website → Design shows a live preview from the publication's website and draws uploaded fonts from the media origin, so the dashboard has to be allowed to frame your sites and load fonts from them: `pnpm swarm` adds `https://<your domain> https://*.<your domain>` to the `frame-src` and `font-src` directives when it uploads these headers. If you deploy with wrangler yourself, add the same two sources to both directives in your copy of `_headers`, or the preview pane stays blank and uploaded fonts show in a fallback face in the dashboard (the websites themselves are not affected).

### Routes

The committed configs have no routes in `staging` and `production`. The installer gives every hostname a zone route (`<host>/*`) and a proxied `AAAA 100::` record; a Worker route wins over a Custom Domain on the same hostname, and the most specific pattern wins over `*.<zone>/*`.

| Worker    | Hostname (installer default, production)                  |
| --------- | --------------------------------------------------------- |
| `api`     | `app.<zone>` (`APP_ORIGIN`)                               |
| `capture` | `forms.<zone>` (`CAPTURE_ORIGIN`)                         |
| `track`   | `link.<zone>` (`TRACK_ORIGIN`)                            |
| `events`  | `events.<zone>`                                           |
| `site`    | `media.<zone>` (`MEDIA_ORIGIN`) and `*.<zone>` (websites) |

With custom domains on, the `site` worker gets `*/*` on the SaaS zone instead of `*.<zone>/*`. `send`, `jobs`, `realtime` and `vault` have no routes. Staging hostnames get a `staging-` prefix (`staging-app.<zone>`) and no website wildcard.

### Public surface

Each worker answers only where this table says. Cloudflare can also give a Worker a default `<script>.<account>.workers.dev` hostname and preview URLs; every Swarm worker config sets `"workers_dev": false` and `"preview_urls": false`, at the top and again in `staging` and `production`, so nothing depends on the account's default. `wrangler deploy` applies them, and the browser setup page turns the same settings off through the API after each upload (`POST /accounts/<id>/workers/scripts/<script>/subdomain`).

| Worker                              | Answers on                                                                                                                                | Default hostname / previews  |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------- |
| `api`, `capture`, `track`, `events` | its routed hostname above                                                                                                                 | off                          |
| `site`                              | `media.<zone>`, publication hostnames under the zone, verified custom hostnames                                                           | off                          |
| `send`, `jobs`, `realtime`          | nothing from the internet: queues, crons, Durable Object and service bindings                                                             | off                          |
| `vault`                             | nothing: only the `VAULT` service bindings of `api`, `capture`, `site` and `jobs`, each pinned to its own entrypoint; `fetch` answers 404 | off                          |
| `swarm-setup` (apps/setup)          | its workers.dev address only, while you install; delete it afterwards                                                                     | workers.dev on, previews off |

No zone-level rule (WAF, firewall, Access) is assumed by the code. If you add one, it covers only the routed hostnames; keep the default hostnames off so it cannot be walked around. The `site` worker resolves the publication from the Host header, so it serves any hostname routed to it; it is not host allow-listed.

### Instance settings

Migration `0032_instance.sql` adds two tables:

- `instance_settings`: one row per setting. The only key is `signup`, `open` or `invite_only`. With no row, local development and tests are open, and a deployed instance (staging or production) fails closed: the first person to sign in gets an account and a workspace, and everyone after needs an invite.
- `instance_admins`: the operators who may change instance settings, in Settings > Instance or with `GET`/`PUT /api/v1/instance/settings`. `GET /api/v1/instance` is public and reports the sign-up mode.

With `invite_only`, an unknown address is let in only with a pending invite, and then without a workspace of its own; a sign-in link request for any other unknown address gets an "invite-only" email instead (the API still answers 202; at most three at once per address, then one every eight hours, counted in the realtime worker's `ApiRateLimiter`), and Google sign-in redirects to `/sign-in?error=invite_only`. SSO just-in-time provisioning, when the `sso` flag is on, is unchanged.

The installer sets `signup` to `invite_only` right after the migrations and before it deploys anything, then creates the owner and adds them to `instance_admins` (`ON CONFLICT DO NOTHING`, so a later change by the owner is kept; `update` does not write this row). By hand, sign in as the owner first: with no row, the first account is let in and every later address needs an invite. Then make the owner an instance admin and save the setting, so Settings > Instance shows it and the owner can change it:

```sql
INSERT INTO instance_admins (operator_id, created_at)
  SELECT id, strftime('%s', 'now') * 1000 FROM operators WHERE email = 'owner@example.com';
INSERT INTO instance_settings (key, value, updated_by, updated_at)
  SELECT 'signup', 'invite_only', id, strftime('%s', 'now') * 1000 FROM operators WHERE email = 'owner@example.com';
```

Run it with `wrangler d1 execute DB --remote --env <env> --command "…"` from `workers/api`.

Adding a row to `instance_admins` also allows the workspaces that person made (their first sign-in made one) to run website code on this Swarm's domain and use its DeBounce credits: a trigger writes `site_code_workspaces` and `email_check_workspaces` rows for them (`migrations/0069_review_fixes.sql`). Being an owner of anyone else's workspace allows nothing; allow those in Settings > Instance.

### Sending limits

Migration `0066_sending_limits.sql` adds `sending_limits` (at most one row: emails a second, an hour, a day and a month, each nullable, and who changed them) and three columns on `broadcasts` for a send waiting for a limit (`waiting_for`, `waiting_since`, `wait_detail`). Instance admins edit the limits in Settings > Instance or with `GET`/`PUT /api/v1/instance/sending-limits`; [self-hosting.md](self-hosting.md#sending-limits) explains them.

Every worker that sends mail binds the realtime worker's `SendPacer` as `SEND_PACER`: `api`, `send`, `jobs`, `capture` and `site` (the committed `wrangler.jsonc` files have it for each environment). Deploy `realtime` first, as the installer does. A worker deployed without the binding still sends, but its mail isn't counted. Nothing to set up: no row means no limits, and `MAIL_MAX_PER_SECOND`, where it was set on `send`, stays a ceiling on the per-second limit.

### Features

Every feature flag is off when `feature_flags` has no row for it (`packages/flags/src/registry.ts`), and no migration adds any. That is what local development, the tests and a manual deploy get. The installer is what turns features on: it adds one `scope = 'platform'` row per flag whose decision is `build`, on except for `FEATURES_OFF_AT_INSTALL` (Copilot, because it uses a paid AI service). It writes only missing rows, on every `pnpm swarm` and `pnpm swarm update`, so a stored choice stands. Off must stay a row with `enabled = 0`: delete the row and the next update turns the feature back on.

With no installer, to start from the same place, save this as `features.sql`:

```sql
INSERT OR IGNORE INTO feature_flags (id, key, scope, scope_id, enabled, updated_at)
  SELECT 'ff_' || lower(hex(randomblob(16))), value, 'platform', NULL, 1, strftime('%s', 'now') * 1000
  FROM json_each('[
    "signup_paths", "site_templates", "message_templates", "site_custom_code", "archive_import", "snippets", "post_archive", "content_calendar", "email_design",
    "raw_html_mode", "split_tests", "cohort_sampling", "best_time_send", "resend_unopens", "click_map", "landing_pages", "engagement_scores", "applications", "smart_blocks", "block_visibility", "signup_journeys",
    "smart_prompts", "nojs_subscribe", "site_homepage_layouts",
    "site_sections", "site_prev_next_nav", "site_drop_caps", "gated_seo_exposure", "author_pages",
    "founding_level", "paywall_coupon", "gift_passes", "gift_articles", "pledges",
    "pay_what_you_want", "referral_awards", "reader_survey_on_subscribe", "welcome_page",
    "post_series", "design_templates", "code_embeds", "custom_email_css", "rosters", "feed_sync",
    "link_hub", "open_operator_mcp", "app_directory", "email_verification"
  ]');
```

and run it from `workers/api` with `pnpm exec wrangler d1 execute DB --remote --env <env> --file features.sql`. It can be run again; it keeps what is there. Skip it to keep everything off and turn on only what you want.

To change a feature afterwards, an instance admin (see above) uses Settings > Instance > Features, or `GET /api/v1/instance/features` and `PUT /api/v1/instance/features/{key}` with `{ "enabled": false }`. Only `build` keys are accepted; others answer 400. The row keeps who changed it (`updated_by`, NULL when the installer or `pnpm swarm feature` wrote it) and when, and the api worker logs `instance feature changed`. By hand:

```sql
UPDATE feature_flags SET enabled = 0, updated_at = strftime('%s', 'now') * 1000
  WHERE key = 'split_tests' AND scope = 'platform';
```

A change reaches the workers within a minute: flags are cached in `CACHE` for 60 seconds per workspace and publication, and there is no way to clear them all at once. Website pages can take up to six minutes, because the site worker's edge cache keeps a rendered page for 300 seconds on top of that, and bumping `cache_version` right after a change would only store pages rendered from the old flags. The precedence is platform, then workspace, then publication, so a row at a narrower scope overrides the platform row. Nothing in Swarm writes those rows; the per-workspace or per-publication instructions elsewhere in this file mean adding them by hand.

## Mail

`MAIL_ADAPTER` picks the provider for every worker that sends: `api`, `send`, `jobs`, `capture` and `site`. Set the same value on all five.

| `MAIL_ADAPTER` | Where                     | Needs                                                                                                                                                                                              |
| -------------- | ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dev`          | development and test only | the `DEV_MAILBOX` bucket; refused anywhere else                                                                                                                                                    |
| `ses`          | staging, production       | `AWS_REGION` (the SES region), `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `SES_CONFIGURATION_SET`; on `api` also `SES_DIRECT_CONFIGURATION_SET`; on `api` and `send` also `SES_EVENT_TOPIC_ARN` |
| `resend`       | staging, production       | `RESEND_API_KEY`, and `AWS_REGION` set to the Resend region new domains are created in: `us-east-1`, `eu-west-1`, `sa-east-1` or `ap-northeast-1`                                                  |
| `mailgun`      | staging, production       | `MAILGUN_API_KEY` and `MAILGUN_REGION` (`us` or `eu`); `AWS_REGION` must still hold a valid region name                                                                                            |
| `postmark`     | staging, production       | `POSTMARK_SERVER_TOKEN` and `POSTMARK_ACCOUNT_TOKEN`; `AWS_REGION` must still hold a valid region name                                                                                             |
| `smtp`         | staging, production       | `SMTP_HOST`, `SMTP_PORT`, `SMTP_DKIM_SELECTOR`, `SMTP_USERNAME`, `SMTP_PASSWORD`; `AWS_REGION` must still hold a valid region name                                                                 |

The env schemas enforce these rules: a worker with a missing or wrong value answers every request with an env error that names the key, instead of failing sends later. Bounces, complaints and deliveries come back through the `events` worker in both cases: `POST /sns/ses` for SES, `POST /resend` for Resend.

To change service on a running install, use `pnpm swarm mail switch <service>` or the setup page rather than editing these by hand (see [Changing your email service](setup-guide.md#changing-your-email-service)). Editing them alone leaves each publication's sending domain registered with the old service, so it can't send. Migration: `0053_mail_service_change.sql`.

Settings → Instance shows the service in use, the records it wants for the domain of `MAIL_FROM`, and what DNS has for each (`GET /api/v1/instance/mail`, instance admins only). It calls the provider's API and DNS over HTTPS each time, with no new bindings or secrets.

### Amazon SES

Do this once per environment, in the SES region set as `AWS_REGION`:

1. **Configuration sets.** `swarm-<env>-broadcasts` (send worker), `swarm-<env>-transactional` (api, jobs, capture and site) and `swarm-<env>-direct` (api, the Direct Send API; var `SES_DIRECT_CONFIGURATION_SET`, required with `MAIL_ADAPTER=ses`, unused locally where the dev mailbox receives Direct Sends). Turn on reputation metrics on all three.
2. **SNS topic** `swarm-<env>-ses-events`. Set the topic's `SignatureVersion` attribute to `2`: SNS uses `1` unless told otherwise, and the `events` worker refuses that, so the subscription would never confirm and no bounce or complaint would arrive. Give each configuration set (including `-direct`) an event destination for _Bounce_, _Complaint_, _Delivery_ and _Reject_ that publishes to the topic.
3. **Subscribe the events worker** over HTTPS at `https://<events host>/sns/ses`. The worker confirms the subscription itself, but only for topics in `SNS_TOPIC_ARNS`, so set that var first. Without `SNS_TOPIC_ARNS` the route answers 404. Notifications more than an hour from now are refused, and each `MessageId` is applied once (a repeat answers 200 with `kind: replay`).
4. **IAM user** for the workers, allowed only `ses:SendEmail`, `ses:SendRawEmail`, `ses:GetAccount` (Settings shows the sandbox and sending limits, and says "unknown" without it), `ses:CreateEmailIdentity`, `ses:GetEmailIdentity`, `ses:DeleteEmailIdentity` and `ses:PutEmailIdentityMailFromAttributes`, plus, for dedicated sending (Phase 7, api and send), `ses:CreateConfigurationSet`, `ses:CreateConfigurationSetEventDestination`, `ses:PutConfigurationSetDeliveryOptions`, `ses:CreateDedicatedIpPool` and `ses:GetDedicatedIps`, and, for the account-level suppression list (jobs), `ses:PutSuppressedDestination`, `ses:DeleteSuppressedDestination` and `ses:ListSuppressedDestinations`. The topic's access policy must let SES publish (`sns:Publish` for the `ses.amazonaws.com` principal, conditioned on the account). Its keys are the `AWS_*` secrets below.
5. **Platform domains.** Verify `PLATFORM_MAIL_DOMAIN` and the domain of `MAIL_FROM` with Easy DKIM, a `bounce.` MAIL FROM subdomain and `_dmarc` at `p=quarantine` or stricter. Leave the SES sandbox before production.
6. **Dedicated sending (Phase 7).** Set `SES_EVENT_TOPIC_ARN` on `api` and `send` to the topic from step 2 (it must also be in `SNS_TOPIC_ARNS`): paid Channels' own configuration sets publish their events there. Dedicated IP pools are created by the platform with `ScalingMode: MANAGED`; AWS bills them per IP per month, and the account's dedicated IP quota may need raising first.

### Resend

1. **API key.** Create a key with _Full access_ (the workers create and verify domains, not only send). Set it as `RESEND_API_KEY` on `api`, `send`, `jobs`, `capture` and `site`, and `AWS_REGION` on the same five to the Resend region.
2. **Remove the SES settings.** Leave out `SES_CONFIGURATION_SET`, `SES_DIRECT_CONFIGURATION_SET`, `SES_EVENT_TOPIC_ARN` and the `AWS_*` secrets, and leave `SNS_TOPIC_ARNS` unset on `events`.
3. **Platform domain.** Add `PLATFORM_MAIL_DOMAIN` (and the domain of `MAIL_FROM`) in Resend with the custom return path `bounce` and open and click tracking off; Swarm tracks opens and clicks itself. Publish the records Resend gives (a `resend._domainkey` TXT, and MX and SPF TXT records on `bounce.<domain>`) and `_dmarc` at `p=quarantine` or stricter. Domains Channels add later are created the same way through the API.
4. **Webhook.** Add a webhook to `https://<events host>/resend` for `email.delivered`, `email.bounced`, `email.complained`, `email.suppressed` and `email.failed`. Its signing secret (`whsec_…`) is `RESEND_WEBHOOK_SECRET` on `events`. Requests are verified with the Svix signature scheme, and each `svix-id` is applied once (a repeat answers 200 with `kind: replay`); without the secret the route answers 404. Delivered, bounced, suppressed and complained events are applied like their SES equivalents; `email.failed` is logged.

What differs from SES:

- Sends use `POST /emails` with the Message-ID as the `Idempotency-Key`, so a retried request never mails twice. Swarm's tags travel as Resend tags and come back on webhooks.
- At most 8 requests are in flight per batch (SES gets 10). Resend's default API rate is 2 requests a second per team, so set your plan's limits under Settings > Instance > Sending limits ([self-hosting.md](self-hosting.md#sending-limits)). Rate limits and server errors are retried with a growing delay. A used-up daily quota makes the send wait for the next UTC day, and a monthly one pauses it until the next month or a resume. A key Resend refuses (401, 403) pauses the send until a person resumes it, with every unsent recipient still pending.
- Dedicated sending is SES-only: with Resend, the Deliverability dedicated-sending routes answer "Dedicated sending needs Amazon SES."

### Mailgun

**Preview.** Mailgun support is tested against a stand-in for its API only, not yet with a real account or a real send.

1. **API key.** Use the account's Private API key (Account Settings > API Keys). A domain sending key can only send, and the workers also add domains. Set it as `MAILGUN_API_KEY` on `api`, `send`, `jobs`, `capture` and `site`, and set `MAILGUN_REGION` to `us` or `eu` on the same workers. `AWS_REGION` must still hold a valid region name; Mailgun doesn't use it.
2. **Remove the SES settings,** as for Resend.
3. **Platform domain.** Add `PLATFORM_MAIL_DOMAIN` (and the domain of `MAIL_FROM`) in Mailgun, and publish its SPF and DKIM records. The tracking CNAME isn't needed, because Swarm turns Mailgun's tracking off on every message.
4. **Webhooks.** Point the domain's `delivered`, `permanent_fail`, `temporary_fail` and `complained` webhooks at `https://<events host>/mailgun`. Set the account's webhook signing key (Settings > API Security), which is not the API key, as `MAILGUN_WEBHOOK_SIGNING_KEY` on `events`.

What differs from Resend:

- Mailgun documents no idempotency key, so a retry after a server error can in rare cases mail twice. Rate limits and server errors are retried; a key Mailgun refuses stops the send.
- Mailgun's signature covers the timestamp and a token but not the event, so `events` accepts each token once (`mailgun_webhook_tokens`). Signatures are accepted for a day, because Mailgun retries for 8 hours and doesn't say whether a retry is signed afresh.
- Mailgun's docs show the webhook event both inside `event-data` and at the top level. `events` reads both, and always requires a valid signature.
- At most 8 requests are in flight per batch. Dedicated sending is SES-only.
- Custom variables, which carry Swarm's delivery ids, also appear to recipients in the `X-Mailgun-Variables` header. They hold ids only.

### Postmark

**Preview.** Postmark support is tested against a stand-in for its API only, not yet with a real account or a real send.

1. **Tokens.** Create a server, and set its server token as `POSTMARK_SERVER_TOKEN` and the Account API token as `POSTMARK_ACCOUNT_TOKEN` on `api`, `send`, `jobs`, `capture` and `site`. `AWS_REGION` must still hold a valid region name; Postmark doesn't use it.
2. **Remove the SES settings,** as for Resend.
3. **Stream for posts.** Create a broadcast stream on the server with the id `broadcasts`. Posts and automation emails go there, and all other mail goes to the default `outbound` stream. Choose custom unsubscribe handling if Postmark has approved your account for it.
4. **Platform domain.** Add `PLATFORM_MAIL_DOMAIN` (and the domain of `MAIL_FROM`) in Postmark, with `bounce.<domain>` as the return path, and publish its DKIM and return-path records.
5. **Webhooks.** On both streams, add a webhook to `https://<events host>/postmark` for deliveries, bounces and spam complaints, and on `broadcasts` also subscription changes. Postmark doesn't sign webhooks, so give each one HTTP Basic auth with a long random password, and set that password as `POSTMARK_WEBHOOK_SECRET` on `events`. Each bounce or complaint `ID` is applied once for 8 days (a repeat answers 200 with `kind: replay`).

What differs from Resend:

- Postmark documents no idempotency key, so a retry after a server error can in rare cases mail twice. Rate limits and server errors are retried. A refused token, or an account Postmark hasn't approved, stops the send.
- A reader who unsubscribes through Postmark's own link is unsubscribed in Swarm too, through the subscription change webhook.
- Postmark refuses to send to an address it has deactivated (error 406). Swarm records that one email as failed.
- Postmark's docs don't say what it does with Swarm's `List-Unsubscribe` headers on a broadcast stream, so check them on the first real send.
- At most 8 requests are in flight per batch. Dedicated sending is SES-only.

### Your own mail server

**Preview.** SMTP support is tested against a stand-in server only, not yet with a real send. Ports 465 and 587 were confirmed reachable from a Worker on 2026-11-04.

1. **Server.** Set `SMTP_HOST`, `SMTP_PORT` and `SMTP_DKIM_SELECTOR` on `api`, `send`, `jobs`, `capture` and `site` (and `SMTP_HOST`, with `SMTP_BOUNCE_DOMAINS` when needed, on `events` too, see Bounces), and `SMTP_USERNAME` and `SMTP_PASSWORD` as secrets. Port 465 uses TLS from the start, and any other port must offer STARTTLS, or Swarm refuses to send. Cloudflare blocks port 25, and Workers can't reach addresses Cloudflare proxies. `AWS_REGION` must still hold a valid region name.
2. **DNS.** Publish your server's DKIM record at `<selector>._domainkey.<domain>` and an SPF record that allows it. Swarm checks for them, and won't send from a domain until it finds the DKIM record. It can't check that your server actually signs.
3. **Bounces.** Posts go out with the return path `bounce+<code>@<UNSUBSCRIBE_MAIL_DOMAIN>`, where `<code>` is a bounce code signed with `UNSUBSCRIBE_KEYS` under its own label: the unsubscribe code in the email's links and `List-Unsubscribe` is not accepted there. A bounce counts only within 7 days of the email going out (the code is also in the delivered copy's `Return-Path` header), and each email counts at most once as a hard and once as a soft bounce. Route `bounce@<UNSUBSCRIBE_MAIL_DOMAIN>` to the `events` worker with Email Routing, and allow your server in SPF for that domain. A relay that replaces the return path sends bounces elsewhere, so report those as below.

   A mailed-in bounce isn't signed by anyone Swarm knows, and whoever has the raw delivered message has its return path, so a permanent failure (5.x.x) counts as hard, suppressing the reader workspace-wide at once, only when it authenticates as the server that would really send it. The `events` worker reads the `Authentication-Results` header Email Routing prepends (only the first one, and only with authserv-id `mx.cloudflare.net`). Email Routing echoes the envelope sender, which the sender chooses, inside that header, so it is read strictly: nothing in it is trusted when the envelope sender has a parenthesis, quote, `;`, `\`, comma, white space or control character, when the header is not in the order Email Routing writes it (its DKIM results first, then DMARC and SPF once each), when a result has a stray word or a value that is not a plain address, domain or token, or when a DKIM pass has a `header.d` that is not a bare domain (or a `header.i` outside it). The bounce must have an empty envelope sender (or a `MAILER-DAEMON@` or `postmaster@` one, which ordinary mailbox users can't send from) and a DKIM pass (`header.d`) or SPF pass (`smtp.mailfrom` or `smtp.helo`) whose organisational domain is one of: the domain of the reader's address; for the big mailbox providers, the domain their bounce servers use (`gmail.com` and `googlemail.com`: `google.com`; `outlook.com`, `hotmail.com` and `live.com`: `outlook.com` and `protection.outlook.com`; `yahoo.com`: `yahoodns.net`); or the domain of `SMTP_HOST` set on `events` (the installer sets it), for bounces your relay writes itself, which are most of them (a 5.1.1 for an address that no longer exists usually comes from the relay, not the reader's server). Gmail's relays sign their bounces as another domain, which is known too: `smtp.gmail.com` and `smtp-relay.gmail.com`: `google.com` and `googlemail.com`. Fastmail and Microsoft 365 are different: Fastmail signs every customer's mail as `messagingengine.com`, and every Microsoft 365 tenant's mail leaves from `protection.outlook.com`, so any of their customers could write a bounce that authenticates the same way. Those domains are never accepted for `SMTP_HOST`, even when it is `smtp.fastmail.com`, `smtp.office365.com` or `smtp-mail.outlook.com`; a bounce from `protection.outlook.com` still counts as hard for a reader at `outlook.com`, `hotmail.com` or `live.com`. With Microsoft 365, name your tenant in `SMTP_BOUNCE_DOMAINS` (for example `contoso.onmicrosoft.com`) if your relay's bounces are signed as it. If you accept that any Fastmail or Microsoft 365 customer could then suppress your readers, you can name `messagingengine.com` or `protection.outlook.com` there yourself. For any other relay whose bounces authenticate as a domain other than its host's, set `SMTP_BOUNCE_DOMAINS` on `events` to those domains, comma-separated (the installer asks, or reads `mail.smtp.bounceDomains`); each counts with its subdomains, as given rather than widened to its organisational domain, so a Microsoft 365 tenant can name `contoso.onmicrosoft.com` without accepting every tenant. A self-hosted relay such as Postfix sends bounces with an empty envelope sender and usually doesn't sign them, so they authenticate only by SPF on the HELO name: give the server a HELO name under your own domain (Postfix `smtp_helo_name`, by default `myhostname`) and publish an SPF record for that exact name allowing its address (for example `mx1.example.com TXT "v=spf1 a -all"`), or have it DKIM-sign the bounces it writes. Without either, its bounces count as soft, and a weekly newsletter rarely reaches 3 soft bounces in 7 days, so dead addresses stay on the list. A relay under a shared sending service (`sendgrid.net`, `amazonses.com` and the like) doesn't count, either as `SMTP_HOST` or in `SMTP_BOUNCE_DOMAINS`, since any of its customers passes for it. Any other permanent failure counts as soft, so it suppresses only through the usual rule of 3 soft bounces in 7 days. A reader whose mailbox is on a custom domain hosted by a big provider (Google Workspace, Microsoft 365) gets their bounce from that provider's domain, so it counts as soft too. Where bounces must take effect at once and be authenticated, send through a service with signed webhooks instead (SES, Resend or Postmark).

4. **Complaints.** Plain SMTP doesn't report them, so the Warm-up complaint pause can't work on its own. If your server learns of one, send it to `POST https://<events host>/smtp-feedback` as JSON: `{"type": "complaint", "messageId": "<the email's Message-ID>"}`. `type` can also be `hard_bounce` or `soft_bounce`, with an optional `detail`. Sign it like a Svix webhook with `SMTP_FEEDBACK_SECRET` (`whsec_…`, set on `events`), using the headers `svix-id`, `svix-timestamp` and `svix-signature`. Give each report its own `svix-id`: a repeated one is answered 200 with `kind: replay` and not applied.

What differs from the other services:

- One connection per email, with at most 4 at once. A refused login, or a server without STARTTLS, stops the send. 4xx answers and connection failures are retried, and other 5xx answers fail that one email.
- A connection lost right after the message was sent can in rare cases mail twice.
- Dedicated sending is SES-only.

### For both providers

1. **Email Routing** on `UNSUBSCRIBE_MAIL_DOMAIN`, to the `events` worker. It handles `unsub+<code>@`, the mailto half of List-Unsubscribe. On a zone of its own a catch-all rule works; on a subdomain of a zone you use for other mail, add the subdomain under Email Routing and a literal rule for `unsub@<domain>` with subaddressing on, so plus addresses reach it (the catch-all is zone-wide). The installer adds the literal rule.
2. **Link domain.** Route `TRACK_ORIGIN`'s host to the `track` worker. Channels' own link domains are Cloudflare for SaaS custom hostnames on the zone in `CF_ZONE_ID`, with the track host as the fallback origin. Check that a Channel's link domain really reaches the `track` worker: with custom web domains on, the `*/*` route below sends every custom hostname on the SaaS zone to the `site` worker, which answers 404 for a link domain. The `track` worker redirects on a Channel's verified link domain only for that Channel's own emails.
3. **DMARC reports (Phase 7).** `DMARC_MAIL_DOMAIN` (for example `dmarc.<domain>`) receives the aggregate reports that sending domains ask for with `rua=mailto:dmarc+<sendingDomainId>@<DMARC_MAIL_DOMAIN>` (docs/deliverability.md):
   - Turn on Email Routing for it and add a rule for `dmarc+*@<DMARC_MAIL_DOMAIN>` (a catch-all, or `dmarc@` with subaddressing on) to the `events` worker. The worker drops anything that isn't a `dmarc+<id>@` report.
   - Publish `*._report._dmarc.<DMARC_MAIL_DOMAIN>  TXT  "v=DMARC1"`. The report address is on another domain than the sending domains, and reporters check this record (RFC 7489 §7.1) before sending reports there; the wildcard authorises every sending domain at once.
   - Create the private R2 bucket `swarm-<env>-reports` and bind it to `events` as `REPORTS`.
   - Set the same `DMARC_MAIL_DOMAIN` on `api` (it writes the recommended record) and `events`.
4. **Dedicated sending (Phase 7).** Set `SES_EVENT_TOPIC_ARN` on `api` and `send` to the topic from step 2 (it must also be in `SNS_TOPIC_ARNS`): paid Channels' own configuration sets publish their events there. Dedicated IP pools are created by the platform with `ScalingMode: MANAGED`; AWS bills them per IP per month, and the account's dedicated IP quota may need raising first.
5. **Account-level suppression list.** Keep SES's account-level suppression list on for _Bounce_ only (the installer sets it; by hand, `aws sesv2 put-account-suppression-attributes --suppressed-reasons BOUNCE`). The setup key needs `ses:PutAccountSuppressionAttributes`; the workers' key does not. The jobs worker pushes Swarm's hard bounces to it and removes the hard bounces an operator removes. Complaints stay in the workspace that received them, because the list is shared by every workspace in the AWS account (docs/deliverability.md "Suppressions"). `ses:ListSuppressedDestinations` is no longer called; the policy may keep it.

The Phase 2 exit gate's load test (100k SES simulator Members on staging) is in [load-testing.md](load-testing.md).

## Custom web domains (Cloudflare for SaaS)

Channel websites are served at `<slug>.<PLATFORM_SITE_DOMAIN>` and on verified custom hostnames. Custom hostnames are Cloudflare for SaaS custom hostnames on the SaaS zone in `CF_ZONE_ID` (the same zone and token as link domains).

1. On the SaaS zone, set the **fallback origin** to `SITE_FALLBACK_ORIGIN` (for example `sites.<platform site domain>`, a proxied record routed to the `site` worker). Operators point a CNAME (or, at a bare domain, ALIAS/ANAME/CNAME flattening) at it.
2. Route `*/*` on the SaaS zone to the `site` worker, so every custom hostname reaches it. The site worker serves a hostname only once its row in `custom_hostnames` is `active`.
3. `api` creates hostnames with HTTP domain control validation and removes them; `jobs` re-checks pending ones every 5 minutes for two weeks (25 per run). Both need `CF_ZONE_ID` and `CF_API_TOKEN` when `WEB_HOSTNAMES=cloudflare`; the token needs _SSL and Certificates: Edit_ on the zone.
4. `WEB_HOSTNAMES=off` switches custom web domains off (the platform address keeps working); `dev` is a fake that activates a hostname on its first check and is refused outside development.

## Payments with a publication's own key

The simplest way to take payments needs no Stripe platform account and no command line. An instance owner turns on **Stripe with a restricted key** in Settings → Instance (flag `stripe_own_key`, off at install, and it works with `PAYMENTS=off`). A publication's owner then creates a restricted key (`rk_live_…` or `rk_test_…`) in Stripe and adds it under Settings → Payments.

- Only restricted keys are accepted. Full secret keys (`sk_…`) are refused.
- Only the owner role can add or remove a key.
- The key and the webhook signing secret are sealed by the vault for the publication's row, and only the key's last four characters are ever returned. Calls on the key go out through the vault's provider proxy, which attaches it; a publication's webhook is checked by the vault against its secret before anything else.
- Swarm checks the key with read calls, then creates a webhook endpoint at `<APP_ORIGIN>/api/v1/stripe/webhook/<channelId>`. Each event is checked only against that publication's secret, and the address decides whose event it is, never the body.
- Disconnecting deletes the endpoint and forgets the key and the secret. Revoke the key in Stripe as well.
- Turning the switch off stops new connections. Accounts already connected keep working, so subscriptions aren't cut off.

The permission list shown on the page comes from the calls Swarm makes. It has not been checked against a real Stripe account yet. If a permission is missing, Stripe's refusal is shown when the key is added or when the call is made.

## PayPal memberships

**This has never run against PayPal.** It's written from PayPal's API documentation and covered by tests with a stand-in, so treat it as unproven until someone runs it in sandbox mode.

An instance owner turns on **PayPal memberships** in Settings → Instance (flag `paypal_memberships`, off at install). A publication's owner creates a REST app in PayPal's developer dashboard and connects it under Settings → Payments.

- **What it covers:** monthly and yearly memberships at a fixed price: subscribe, renew, cancel, refunds and access. Coupons, tax, trials, pay what you want, plan changes, Gift Passes, lifetime prices and Products stay on Stripe.
- **Secrets:** the client secret is sealed by the vault for the publication's account, and only its last four characters are returned. Only the owner role can connect or disconnect.
- **Webhook:** Swarm creates it at `<APP_ORIGIN>/api/v1/paypal/webhook/<channelId>`. Each delivery is checked with PayPal's own signature check before anything is read.
- **Plans:** a PayPal plan is made the first time a reader chooses PayPal for a price. Changing a price later makes a new price row and a new plan; existing PayPal subscribers stay on their old price.
- **Receipts:** a payment sends the same **Payment receipt** as Stripe, once per sale, if the publication's owner has saved that message.
- **Canceling:** PayPal stops billing at once, so access runs to the end of the paid period and the daily job ends it. A full refund, or partial refunds that add up to the whole payment, or a reversal ends access immediately. A failed payment gives seven days' grace.
- **Refunds:** issue them in PayPal. Swarm hears about them by webhook.
- **Disconnecting** deletes the webhook and forgets the secret. Existing subscriptions keep charging in PayPal until they're canceled there, and Swarm no longer hears about them.

## Payments (Stripe Connect)

Membership levels are paid through each Channel's own Stripe account, connected with Connect Standard over OAuth. The platform never sets an application fee (0% take); every money call runs on the connected account with the `Stripe-Account` header, on the pinned API version `2025-09-30.clover`.

1. **Platform account.** In the Stripe Dashboard of the platform account, enable Connect with Standard accounts and OAuth. The secret key (`sk_live_…`, `sk_test_…` in staging) is `STRIPE_SECRET_KEY`. A restricted key is not enough: Connect OAuth, Checkout on connected accounts and subscription updates need the full secret key.
2. **OAuth.** Under Connect → Settings → OAuth, copy the client id (`ca_…`) into `STRIPE_CONNECT_CLIENT_ID` and add the redirect URI `<APP_ORIGIN>/api/v1/payments/connect/callback` (for example `https://app.swarm.example/api/v1/payments/connect/callback`). The scope requested is `read_write`.
3. **Webhook endpoint.** Add an endpoint that listens to events on **Connected accounts** (not "Your account") at `<APP_ORIGIN>/api/v1/stripe/webhook`, API version `2025-09-30.clover`, with these events:
   `checkout.session.completed`, `customer.subscription.created`, `customer.subscription.updated`, `customer.subscription.deleted`, `customer.subscription.trial_will_end`, `invoice.paid`, `invoice.payment_failed`, `charge.refunded`, `charge.dispute.created`, `account.updated`.
   Its signing secret (`whsec_…`) goes into `STRIPE_WEBHOOK_SECRETS`. To rotate, roll the secret in Stripe, set `STRIPE_WEBHOOK_SECRETS=<new>,<old>`, and drop the old one once Stripe stops signing with it (24 hours at most).
4. **Billing Portal.** Member Center's "Update payment method" opens a Stripe Billing Portal session on the connected account, so each account needs the portal configured (or Stripe's default configuration allowed).
5. **Stripe Tax** is optional per Channel (Settings → Payments); the connected account must have Stripe Tax set up for it to work.
6. Locally `PAYMENTS=dev` uses a fake that never calls Stripe: Connect returns straight to the callback and Checkout opens the site's dev checkout page. The fake is refused outside development and test. `PAYMENTS=off` turns Membership levels off for a deployment (the webhook then answers 404).

The webhook verifies every request against `STRIPE_WEBHOOK_SECRETS` whatever `PAYMENTS` is, so it answers 400 until a secret is set; there is no unsigned mode. It answers 500 when processing an event fails, so Stripe retries it (for up to three days); the event is kept in `stripe_events` with status `failed` and the error.

The `jobs` cron (every 5 minutes) runs the subscription lifecycle: grace periods that ran out, comp and Gift Pass grants that ended, unclaimed Gift Passes (90 days) and scheduled price changes. Price changes set to migrate existing Members update their subscriptions on Stripe, so `jobs` needs `STRIPE_SECRET_KEY` too. It also sends the Gift Pass reminders (a week before a claimed pass ends, a fortnight before an unclaimed one expires), whose links point at the Channel's site, so `jobs` has `PLATFORM_SITE_DOMAIN` and `SITE_SCHEME` with the same values as the api worker.

### Stripe lifecycle suite

`workers/api/tests/stripe-lifecycle.live.test.ts` runs the subscription lifecycle against real Stripe in test mode, on test clocks: trial → paid → payment failed → grace → downgrade → recovery, cancel at period end, a full refund, a scheduled price change that migrates a subscription, a coupon's effect on MRR, and a Gift Pass (paid, mailed, reminded, expired, refunded). It creates the level and coupon through our API (so on Stripe), acts on Stripe as a reader would, then fetches the events from the connected account, signs them with the test endpoint secret and posts them to `/api/v1/stripe/webhook` in order, and checks D1 and entitlements. No Stripe CLI or public URL is needed. Checkout itself needs a browser, so the Gift Pass's `checkout.session.completed` is the one event the suite writes; its payment is real.

1. In a Stripe **test-mode** platform account with Connect enabled, connect (or create and onboard) a Standard account until it can take charges. Test clocks run on that account.
2. Run it:

## Account security (Phase 7)

No new bindings or secrets: passkeys, TOTP, recovery codes and SSO use `APP_ORIGIN`, `AUTH_KEYS`, `FIELD_KEYS`, `CACHE`, `DNS_RESOLVER` and the sign-in mail path that already exist. Migration: `0017_security.sql`.

- **Passkeys.** The WebAuthn relying party ID is the hostname of `APP_ORIGIN` and the expected origin is `APP_ORIGIN` itself. Changing the dashboard hostname makes every registered passkey unusable (operators fall back to TOTP or recovery codes and register again), so treat it as a migration.
- **TOTP secrets** and SSO client secrets are sealed with `FIELD_KEYS` by the vault, which also checks TOTP codes and exchanges the SSO code itself; keep old keys in the ring after rotating.
- **SSO (OIDC).** Off by default, behind the `sso` flag: see [self-hosting.md](self-hosting.md#single-sign-on). Operators register `<APP_ORIGIN>/api/v1/auth/sso/callback` as the redirect URI at their identity provider. The api worker fetches each issuer's `/.well-known/openid-configuration`, token endpoint and JWKS (cached in `CACHE` for an hour), so outbound HTTPS to identity providers must be allowed. Issuers, token endpoints and JWKS URLs must be https on a public host name (the outbound URL guard), and the worker does not follow their redirects.
- **Domain proof.** SSO domains are verified with a TXT record `_swarm-sso.<domain>` through the DNS resolver (`DNS_RESOLVER=doh`). The jobs worker looks every verified domain up again once a day with its own `DNS_RESOLVER` (`doh` in staging and production). Locally (`DNS_RESOLVER=dev`) the record is read from KV instead: `wrangler kv key put --binding CACHE --local "dev:txt:_swarm-sso.example.com" '["swarm-sso=<token>"]'`.
- **Mail categories** `new_device` and `recovery_code_used` go out from `MAIL_FROM`, like QuickPass.
- **SAML** is not deployed (deferred, see `docs/security.md`).

## Queues

| Queue                      | Producer        | Consumer | Notes                                                                                                                         |
| -------------------------- | --------------- | -------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `swarm-<env>-send`         | api, send, jobs | send     | snapshot, fan-out and batch messages; 10 per batch, 8 retries                                                                 |
| `swarm-<env>-send-dlq`     | Queues          | none yet | messages that failed 8 times; inspect and redrive by hand                                                                     |
| `swarm-<env>-jobs`         | api, jobs       | jobs     | imports, exports, bulk actions, Circle refresh, Flows, email checks; 5/batch                                                  |
| `swarm-<env>-jobs-dlq`     | Queues          | none yet | jobs that failed 8 times                                                                                                      |
| `swarm-<env>-webhooks`     | api, jobs       | jobs     | one message per webhook delivery attempt; 10/batch, 3 retries; state lives in D1                                              |
| `swarm-<env>-webhooks-dlq` | Queues          | none yet | webhook messages whose handler crashed 3 times (the minute sweep re-queues their deliveries anyway)                           |
| `swarm-<env>-public`       | capture, events | jobs     | the only queue the public workers can write to: `channel_changed` and a confirmed signup's `email_check`; 10/batch, 8 retries |
| `swarm-<env>-public-dlq`   | Queues          | none yet | public messages that failed 8 times                                                                                           |

**What each queue may carry.** The jobs worker reads a batch by the queue it came from (the name's last part: `-jobs`, `-webhooks`, `-public`) and parses every body against what that queue carries (`readQueueMessage` in `packages/engine/src/jobs.ts`). A body of another type, or of the wrong shape, is logged as `message refused` with the queue, its type and the reason (`not_allowed` or `malformed`) and acked, never run. A batch from a queue it does not know is logged as an error (`batch from an unknown queue; retrying`) and retried. On the public queue, `channel_changed` names only a Channel: the jobs worker marks that Channel's Circles pending and queues their `circle_refresh` messages on the jobs queue itself. A `message refused` line in the jobs log means a producer sent something it should not; look at it.

**Dead-letter queues.** They are the install operator's to watch: nothing consumes them, so a message stays there until Cloudflare's queue retention removes it (4 days unless the queue is created with a different `--message-retention-period-secs`; keep it at or below your erasure commitment). Messages carry ids only, never an address or other Member data (email checks name Member ids since the security review, `packages/engine/src/jobs.ts`), so a dead-lettered message holds nothing erasure can't reach, and one whose Member was erased since does nothing when redriven. Inspect them in the Cloudflare dashboard's queue view, redrive what you fixed, and purge the rest (`wrangler queues purge`). The retention period is a platform setting this repository does not show; check it per install.

Create them with `wrangler queues create` before the first deploy. Crons: `send` every minute (scheduled Dispatches, the stuck-Broadcast reaper, domain checks); `jobs` every minute (the Flows sweep, the Champions referral count and milestone awards, the webhook fan-out and sweep), every 5 minutes (pause expiry, export and import file clean-up, Circle re-evaluation, pending web hostnames, the payments lifecycle) and daily at 03:30 UTC (site edge housekeeping, the Flows unengaged check, webhook pruning); `capture` every 15 minutes (Gentle Reminders). Phase 7: the `jobs` minute cron also runs Privacy Center exports and erasures, and the 5-minute cron runs export destinations (operators' own R2 or S3 buckets, written with the keys they entered, sealed with `FIELD_KEYS`) and deletes expired Privacy Center export files. Export emails go from the Channel's sender, so `jobs` needs `DSR_EXPORT_SIGNING_KEYS` and `CAPTURE_ORIGIN` (already set) for the download link. After the switch to per-link keys, the minute cron also emails sponsors a new report link once (`SPONSOR_REPORT_SIGNING_KEYS`; docs/self-hosting.md "Per-link keys").

Flows (Phase 6):

- Delays of up to 12 hours are scheduled on the jobs queue with `delaySeconds` (Cloudflare's limit is 43,200 s). Longer delays are only stored as `flow_runs.next_at`.
- The `jobs` every-minute cron (`* * * * *`, in every environment) re-queues waiting runs that are due. It also catches any delayed message that was lost.
- The daily cron emits `unengaged` events and prunes processed member events older than 90 days.
- Flow emails are queued on the send queue, so `jobs` is also a producer of `swarm-<env>-send` (binding `SEND_QUEUE`).
- Flow steps retry on the jobs queue with backoff. After 5 attempts the step fails and the run pauses, so a step never reaches the dead-letter queue as done.
- Queued steps carry a 15-minute lease in `flow_runs.next_at`: the sweep re-queues a run whose message was lost. Sweeps claim due runs with a conditional update, so overlapping sweeps never queue a run twice.
- `jobs` emails operators (notify_author steps, runs paused after failed steps) from `notifications@<PLATFORM_MAIL_DOMAIN>`, so it needs the mail vars: `MAIL_ADAPTER`, `AWS_REGION`, `SES_CONFIGURATION_SET` (`swarm-<env>-transactional`), `PLATFORM_MAIL_DOMAIN`, the `DEV_MAILBOX` bucket locally, and `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` secrets with `ses` or `RESEND_API_KEY` with `resend`.
- webhook_call steps sign with each Flow's webhook secret, which the vault seals and signs with.

Event Webhooks (Phase 7):

- `jobs` produces and consumes `swarm-<env>-webhooks` (binding `WEBHOOKS_QUEUE`); `api` produces on it for test events and redrives. A message names one delivery; attempts, retries and their schedule live in D1 (`webhook_deliveries`), so the queue’s own retries only cover a crashed handler.
- Retries up to 12 hours are queued with `delaySeconds`; the every-minute cron re-queues anything overdue (lost messages, longer delays) and fans new member and platform events out to endpoints.
- Endpoint secrets are made and sealed by the vault; jobs asks it for each delivery's signature. The disabled-endpoint email goes out from `notifications@<PLATFORM_MAIL_DOMAIN>` with the mail vars above.
- Endpoints are called from the jobs worker with `fetch`; nothing extra is needed for egress.

R2 buckets added in Phase 3: `swarm-<env>-imports` and `swarm-<env>-exports`, both private, bound to `api` and `jobs`. Phase 7 also binds `swarm-<env>-exports` to `capture`, which streams a Member's Privacy Center export from it.

The capture worker serves Capture Forms, confirm pages and the Member Center on its own origin, `CAPTURE_ORIGIN` (for example `https://forms.<domain>`). ## Copilot (Phase 8)

The platform's Copilot provider is Cloudflare Workers AI through the api worker's `AI` binding (`COPILOT_ADAPTER=workers-ai`, set in `wrangler.jsonc` for staging and production); Anthropic is the optional external provider (`COPILOT_ADAPTER=anthropic` with `ANTHROPIC_API_KEY`) and the only provider a workspace can bring its own key for. Apply `0022_copilot.sql` and `0030_copilot_actions.sql`, then turn on `copilot` (and `copilot_byok`, `copilot_actions`) per workspace. See [copilot.md](copilot.md).

- **The `AI` binding** is declared per environment (`"ai": { "binding": "AI" }` under `env.staging` and `env.production`); it bills to the account the worker is deployed to. Local development and tests use the offline `dev` adapter and have no `AI` binding (a local `wrangler dev` with `workers-ai` would call the real service). The worker refuses requests when `COPILOT_ADAPTER=workers-ai` and the binding is missing.
- **The model** is `COPILOT_WORKERS_AI_MODEL` (`@cf/moonshotai/kimi-k2.6`, an instruction-tuned chat model with tool calling from the Workers AI catalogue). Any chat model of the catalogue that takes OpenAI-style `messages` and `tools` works; Ask Copilot to do it needs one with tool calling.
- **AI Gateway (optional).** Create a gateway in the dashboard (AI → AI Gateway), then set `AI_GATEWAY_ID` (its name) and `AI_GATEWAY_ACCOUNT_ID` (the account id) as vars in `wrangler.jsonc` for the environment; set both or neither. In the gateway's settings turn **Logs off** (no request or response bodies stored) and **Cache off**; leave **Authenticated Gateway** off (Workers AI calls use the binding, Anthropic calls carry the provider key, so an open gateway URL can't spend Swarm's credits) and **DLP** off. Swarm also sends `cf-aig-collect-log: false` and `cf-aig-skip-cache: true` on every Anthropic request and `gateway: { collectLog: false, skipCache: true }` on every Workers AI call, so a changed setting can't start keeping content. What the gateway keeps then is analytics only: request counts, tokens, cost estimate, latency, model, provider and status. Rate limiting on the gateway is optional; Copilot's own plan limits already apply.

## The vault

The `vault` Worker alone holds `FIELD_KEYS`, and the keys for Member Center, goods and signup links that the public workers don't hold (docs/security.md "The vault"). It has no route; `api`, `capture`, `site` and `jobs` reach it through `VAULT`, each bound to its own entrypoint. Nothing to provision beyond the D1 database it shares: its tables are `vault_audit`, `vault_mints` and `vault_rate` (`migrations/0150_vault.sql`), and its re-seal keeps progress in `field_key_reseal` (`0125`) next to the jobs worker's.

- **Order.** Deploy it after `realtime` and before its callers (the installer does: `DEPLOY_ORDER`). A caller uploaded first fails: its service binding names a script that does not exist. `pnpm swarm update` deploys every worker, runs the health step, and only then removes the keys a worker no longer has in the matrix (`FIELD_KEYS` from api, capture, site and jobs; the signup, member and goods signing keys from capture, site and the api; the preview key from jobs). If a worker is unhealthy, nothing is removed and the update says so: the previous release, which still reads those keys itself, can then be rolled back to.
- **Health.** A caller's `/healthz` answers 503 while the vault does not answer through its binding, so the installer's health step fails rather than leave encrypted data unreachable. jobs has no public host: its minute cron pings the vault through its binding and records the answer in `worker_heartbeats`, and the health step waits (up to three minutes) for a successful heartbeat recorded after this run deployed jobs, reading it from D1; without one, jobs counts as unhealthy and no key is removed. `pnpm swarm doctor` reports it too, as a problem when the last success is more than ten minutes old. `pnpm swarm doctor` also checks that each binding names its own entrypoint and that no other worker binds to the vault.
- **How it seals.** `VAULT_WRITE_FORMAT=legacy` (the default) writes the formats a release from before the vault reads, so rolling back is safe. `pnpm swarm vault` shows where it stands (also in `pnpm swarm doctor`: the write format, legacy opening and the re-seal's progress). `pnpm swarm vault --write-format v3` switches to the row-bound format; it refuses until every worker bound to the vault answers its health check and the install has run on the vault for 7 days (state `vault.since`, recorded at its first deploy), and `--force` goes ahead anyway with a warning. From then on the cron moves every stored value to the row-bound format, and code from before the vault can't read those values. `pnpm swarm vault --legacy-open off` comes last: it refuses until the re-seal (`field_key_reseal` row `v3:<current kid>`) has finished with no unreadable values, and has no `--force`. Each switch re-renders and redeploys the vault alone.
- **Keys.** It gets `MEMBER_KEYS` while v1 links are still signed and, after the switch to per-link keys, for 30 days (the longest a v1 Member Center link it checks may live); `pnpm swarm update` removes it afterwards. `STRIPE_SECRET_KEY` and `DEBOUNCE_API_KEY` go to it when those features are on, for the proxy it runs: capture and site hold neither (capture's sign-up check and both workers' Stripe calls go through it).

## Secrets

Set them with `wrangler secret put <NAME> --env <env>`. Locally they go in `<worker>/.dev.vars`, which is gitignored. The installer generates the keyrings once (its key registry, `packages/installer/src/keys.ts` `KEY_REGISTRY`, says which worker signs and which checks each one), keeps every secret in `.swarm/<env>.secrets.json` (encrypted under the operator's passphrase, docs/self-hosting.md), and uploads them with `wrangler deploy --secrets-file`. That never removes a secret, so after each deploy `pnpm swarm update` deletes the keyrings a worker should no longer hold (only names in the registry); by hand, run `wrangler secret delete <NAME>`. In staging and production a worker refuses requests if a key is still the placeholder from `.dev.vars.example` (or an Ed25519 key with the id `dev0`), and logs which one.

Every keyring is `kid:secret[,kid:secret]`, first key current. An HMAC secret is at least 32 characters. An Ed25519 keyring (`*_SIGNING_KEYS`) holds base64url PKCS#8 private keys; the workers that only check its links get `*_VERIFY_KEYS` instead, the base64url raw 32-byte public keys under the same key ids (`publicKeyring` in `@swarm/tokens`, which the installer runs at each deploy). The workers that hold a link keyring also get the variables `LINK_SIGNING_MODE` (`v1` while links are still signed with `MEMBER_KEYS`, `v2` after the switch) and, with `v2`, `LINK_LEGACY_CUTOFF` (the switch, in milliseconds since 1970). docs/self-hosting.md "Per-link keys" describes the switch. The per-link keyrings reach the workers before they sign with them: until the switch (`LINK_SIGNING_MODE=v1`), `MEMBER_KEYS` still signs those links and `UNSUBSCRIBE_KEYS` the bounce codes, and every worker already accepts both. A worker refuses to start without `LINK_SIGNING_MODE`, without a keyring it signs or checks with, with a private key where it should hold only the public one, and, in `v1`, without `MEMBER_KEYS` if it signs links. The `events` worker gets `LINK_SIGNING_MODE` and `LINK_LEGACY_CUTOFF` too: it takes bounce codes signed with `UNSUBSCRIBE_KEYS` for 14 days after the switch. Local development runs `v2` with `LINK_LEGACY_CUTOFF=0` (`wrangler.jsonc`). A Checkout Session carries its signed reference in metadata (`swarm_ref`): an Ed25519 token is longer than Stripe's 200 characters for `client_reference_id`.

## Checks before deploying

For an installer-managed environment, `pnpm swarm doctor [--env staging]` runs most of these (configs, resources, secrets, migrations, health, mail DNS, provider status and sign-up mode).

- Copilot (Phase 8): with `COPILOT_ADAPTER=workers-ai`, the `AI` binding is declared for the environment and `COPILOT_WORKERS_AI_MODEL` is in the Workers AI catalogue; with `COPILOT_ADAPTER=anthropic`, the Anthropic organisation behind `ANTHROPIC_API_KEY` has zero data retention enabled and `COPILOT_MODEL` is a model it covers. With a gateway, its logs and cache are off. A subject-line request from the editor on staging streams and shows up in Settings → Copilot.
- `pnpm check:provisioned <env>` finds no `unprovisioned` value and no shared rate-limit namespace.

- `pnpm check:dry-run` bundles every worker.
- With Resend, an unsigned `POST https://<events host>/resend` answers 401; with SES (no `RESEND_WEBHOOK_SECRET`) it answers 404.
- With Mailgun, an unsigned `POST https://<events host>/mailgun` answers 401; with any other provider it answers 404.
- With Postmark, `POST https://<events host>/postmark` without the password answers 401; with any other provider it answers 404.
- With your own mail server, an unsigned `POST https://<events host>/smtp-feedback` answers 401; with any other provider it answers 404.
- `/healthz` on each worker returns `200`, with `environment` matching the target.
- `/.well-known/security.txt` is served by `api`, `capture`, `site` and `track`.
- A Channel site answers on `<slug>.<PLATFORM_SITE_DOMAIN>`, an unknown host gets the 404 page, and a page response carries a CSP with a nonce.
- `/__dev/mail` answers 404.
- `/v2/openapi.json`, `/v2/reference` and `/.well-known/api-catalog` answer 200 without credentials; `/v2/channels` without a key answers 401.
