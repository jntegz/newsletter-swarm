# Architecture

Swarm runs on Cloudflare. Outbound mail goes through an email service behind a `MailAdapter` interface, because Cloudflare cannot send bulk email: Amazon SES, Resend, Mailgun, Postmark or the operator's own SMTP server (`packages/mail/src`). Stripe handles payments, with PayPal as a preview. Nothing else is off-platform, and no third-party JavaScript runs on any product surface.

## Principles

1. **Contract first.** Zod schemas in the API worker and `@swarm/domain` produce `docs/openapi.json` and the dashboard's typed client.
2. **Fail closed.** Each worker validates its env on the first request. A missing secret or binding means the worker answers `503 unavailable` and logs which key is wrong. There are no defaults in code.
3. **No state changes on prefetchable GETs.** Sign-in links, confirm links, unsubscribe and Member Center actions render a page and act on POST. RFC 8058 One-Click unsubscribe is a POST by design.
4. **Async by default.** Anything that touches more than one Member goes through Queues. HTTP handlers enqueue and return.
5. **One tenancy check.** `channelAccess()` in `@swarm/db` resolves an operator's effective role on a Channel. A Channel the operator cannot access answers 404.
6. **Vocabulary everywhere.** See [vocabulary.md](vocabulary.md).
7. **Flags for everything optional.** The registry is in `packages/flags/src/registry.ts`. Every flag is off by default and enforced on the server. The installer, not a migration, turns features on for a real install ([self-hosting.md](self-hosting.md#features)).

Every worker starts from `@swarm/runtime`, which gives it:

- request ids;
- JSON logs with emails and tokens redacted;
- env validation;
- security headers;
- the error envelope;
- `/healthz`;
- `security.txt` on the public-facing workers.

A worker bound to the vault also reports it on `/healthz`: `vault: "ok"` when the vault answers its `ping` through the binding, a 503 when it doesn't. jobs, which has no public host, pings the vault from its minute cron instead and records the answer (`worker_heartbeats`: when it checked, whether the vault answered, the last time it did), which the installer reads before it removes keys.

### The vault

The vault Worker (`workers/vault`, its code in `packages/vault`) is where sealed data and service secrets are opened. It has no route, no `workers.dev` name and no preview URL. It exports four named entrypoints, `ApiVault`, `CaptureVault`, `SiteVault` and `JobsVault`, and each caller's wrangler config binds `VAULT` to its own one (`services[].entrypoint`). The binding is the caller's identity: capture can call `CaptureVault`'s methods and none of the others. send, track, events and realtime have no binding; they never touch sealed data.

- **The contract** is `packages/vault/src/api.ts`: per entrypoint, the methods, the principals each takes and the result shape (`VaultResult`, never an exception across RPC). Callers wrap the binding in `vaultClient` (5-second timeout; a transport error or timeout becomes `unavailable`) and fail closed: an encrypted field is not shown (the api returns it as null and flags the Member `encryptedUnavailable: true`), a save that needs a seal answers 503. Tests use `createFakeVault`, which runs the same operations in process.
- **Who may open what** is decided by the vault, from D1: a credential the api passes through (session, API key or OAuth token, resolved with the same lookups the api uses, `@swarm/db` `credentials.ts`), a Member Center link it verifies with its own key, or a stored job (an export that is running and whose creator is still an admin, a data request being processed, a pending webhook delivery, and so on). The check is coarse ("reaches this Channel with this role or scope"); route policy stays in the api.
- **Row-bound sealing.** Values the vault writes in format v3 (`fv3.<purpose>.<kid>.<iv>.<ct>`, `packages/engine/src/fields.ts` `sealV3`) are bound to their row: the additional data names the workspace, Channel, Member and field (or the request, endpoint, Flow, operator, connection, destination). A value copied into another row does not open. The vault writes the older formats until the operator switches it (`pnpm swarm vault --write-format v3`, a week after it first went out), so a rollback to a release from before it stays possible until then.
- **Callers hold no `FIELD_KEYS`.** api, capture, site and jobs reach every sealed value through it: engine code that once took a keyring takes a port instead (`packages/engine/src/vault-ports.ts`: erasure markers and data request addresses, `FieldVault` for profile fields, the Flows and export ports, the provider fetch), which each caller builds on its vault client (`workers/*/src/vault.ts`, `@swarm/vault` `vaultFetch`, `markerPort`). The api hands the vault the request's own credential (`c.get('credential')`, carried into in-process /v2 calls by `internalV2Fetch`); jobs a stored row; capture and site the evidence they hold. Only `packages/vault` and `workers/vault` may import the sealing primitives (`eslint.config.js`).
- **Records.** Every call writes a log line (op, entrypoint, principal kind, tenant, count, decision, time, never a value). Refusals, rate-limit hits and bulk opens go to `vault_audit`, links it mints to `vault_mints`, and a bulk open (an export, a data request, a destination run) also to the workspace's audit log once per job (`vault.export_open`, `vault.dsr_open`, `vault.destination_open`). Rows are kept 90 days.
- **Cron**, every 5 minutes: a bounded share of the re-seal (`@swarm/engine` `resealSealedColumns`: after a `FIELD_KEYS` rotation, and once writes are v3, every older value), the rewrite of older erasure markers, then pruning of its own tables.

### Queues

Each queue carries only what its producers legitimately send, and the consumer reads a batch by the queue it came from and parses every body against that queue's types (`readQueueMessage` in `packages/engine/src/jobs.ts`). Anything else is logged as `message refused` and acked, never run ([security.md](security.md), "What the public workers can queue").

| Queue                  | Producers       | Messages                                                                                                                                                            | Consumer |
| ---------------------- | --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| `swarm-<env>-send`     | api, jobs, send | `snapshot`, `fanout`, `batch`, `cohort_halted`, `wait_notice` (`SendMessage`)                                                                                       | send     |
| `swarm-<env>-jobs`     | api, jobs       | `import_analyze`, `import_run`, `export`, `bulk`, `circle_refresh`, `flow_events`, `flow_step`, `email_check_plan`, `email_check_run`, `email_check` (`JobMessage`) | jobs     |
| `swarm-<env>-webhooks` | api, jobs       | `webhook_delivery` (`WebhookMessage`)                                                                                                                               | jobs     |
| `swarm-<env>-public`   | capture, events | `channel_changed` (Circles of this Channel need a re-evaluation) and `email_check` for one Member who confirmed a signup (`PublicMessage`)                          | jobs     |

The internet-facing workers (capture, events) bind only the public queue. Its `channel_changed` names nothing but the Channel: the jobs worker marks the Channel's Circles pending and queues their `circle_refresh` messages on the jobs queue, so the public workers write no Circle rows. site, track and realtime produce on no queue; what they record (`member_events`, `dsr_requests`) is picked up by crons. Each queue has a dead-letter queue named `<queue>-dlq`.

## Database

D1 (SQLite) with forward-only migrations in `migrations/`. These conventions apply to every table:

- Ids are prefixed UUIDv7 text (`ws_`, `op_`, `ch_`, …).
- Timestamps are integer milliseconds.
- Emails use `COLLATE NOCASE`.
- Rows scoped to a Channel or workspace cascade when their owner is deleted.

Schema v1 (`0001_foundation.sql`) has these tables:

- `workspaces`, `operators`, `seats`, `channel_roles`
- `channels`, `media`
- `sessions`, `quickpass_tokens`, `oauth_identities`
- `audit_events`, which is hash-chained per workspace
- `feature_flags`

`0003_dispatch_send.sql` adds Dispatches and revisions, sending domains and sender identities, Broadcasts, recipients, deliveries, link targets, clicks and opens, suppressions and soft bounces, the Reputation Ramp and a minimal `members` table.

`0004_audience.sql` (Phase 3) rebuilds `members` with six statuses (`pending`, `active`, `paused`, `unsubscribed`, `bounced`, `complained`), attribution, digest and pause columns, and adds profile fields and values, tags, Capture Forms with versions and daily stats, confirm requests, referrals, Circles and their materialised members, import, export and bulk jobs, and Dispatch audiences. `0005` and `0006` add indexes for Circle engagement rules and member activity.

`0007_site.sql` adds the site tables, `0008_money.sql` Membership levels, Gates and Stripe, and `0009` the gated email variants. `0010_growth.sql` (Phase 6) adds Flows (`flows`, `flow_versions`, `flow_runs`, `flow_run_steps`, `flow_emails`), the member event log (`member_events`), `templates`, Split Tests and Cohort Sampling (`split_tests`, `split_test_variants`, `cohort_samples`, plus held, variant and Smart Block columns on `broadcast_recipients`), Champions (`champion_settings`, `champion_rewards`, `champion_milestones`, `champion_awards`, `members.champion_code`, review columns on `referrals`), Ask (`asks`, `ask_questions`, `ask_options`, `ask_responses`), `signup_journeys` and `signup_journey_daily`, Smart Prompt columns on `capture_forms`, `series` and `series_dispatches`, and `funnel_daily`; `0011_funnel.sql` adds the funnel rollup state (`funnel_cursors`, `funnel_members`). Phase 7 adds API keys and webhooks.

## Email pipeline (Phase 2)

1. **Send.** Sending a Dispatch creates a Broadcast with status `queued`.
2. **Snapshot.** A job resolves the audience (active Members in the chosen Circles, minus suppressions). It writes recipients in chunks and enqueues fan-out. A paid Dispatch with a gate divider has two frozen renders: the full email and the teaser that stops at the gate with "Continue reading on the web". The snapshot records each recipient's variant once: full when they hold a current paid entitlement whose level the Gate admits (an empty level list admits any paid level), teaser otherwise. Retries send the recorded variant, and both renders share one set of link targets. Preflight reports the split, and test sends can use either email.
3. **Fan-out.** `send` splits the recipients into batches of 50, reserving Reputation Ramp capacity atomically. Out of capacity, it waits for the next UTC day; a paused ramp waits for an operator.
4. **Batch.** Each batch personalises a cached render with escaped merge tags, rewrites links to the branded link domain, adds the open pixel, and builds raw MIME. Every message carries:
   - quoted, encoded From;
   - Reply-To;
   - `List-Unsubscribe` and `List-Unsubscribe-Post: List-Unsubscribe=One-Click`;
   - a text part.

   It then calls SES v2 with a configuration set, records deliveries in one batch, and retries idempotently.

5. **Events.** `events` verifies SNS signatures. A hard bounce suppresses the address, a complaint suppresses and unsubscribes, and an anomaly pauses the ramp. `jobs` then emails the owners and admins about the pause once, and keeps the SES account-level suppression list in step with ours both ways ([deliverability.md](deliverability.md) "Suppressions").
6. **Monitor.** After each queue batch, `send` publishes the Broadcast's counters to its `SendMonitor` Durable Object, which pushes them to open dashboards over WebSocket (proxied and access-checked by `api`). Engagement numbers are refetched, not pushed; without a socket the dashboard polls.

**Pacing and sending limits.** The install's sending limits (`sending_limits`, migration `0066`, edited under Settings > Instance; contract in `packages/domain/src/sending-limits.ts`) hold for every email together, because they all go through one email account. One `SendPacer` object in the realtime worker (named `install`) decides every turn, however many queue consumers and request handlers ask at once. Callers pass the stored limits with each turn (read through a 30-second cache) with when they were saved (`limitsSavedAt`, from `sending_limits.updated_at`, which only grows); the object keeps the most recently saved limits it has been given and applies them to a turn that brings older ones. Saving in Settings tells it (a turn for nothing) before any waiting send resumes, so a worker whose cache still holds the old limits can't stop a resumed send again for them. A change applies without a deploy. Broadcast batches name their workspace: while two or more workspaces have asked for bulk turns in the last 10 minutes (`SEND_WORKSPACE_ACTIVE_MS`), each may use only an equal part of what bulk mail may use of the hour, day and month, and a workspace past its part is sent back for a minute rather than paused, so one large Broadcast can't take the install's whole window from the others. A workspace sending alone may use all of it. The per-second line is shared too: while several workspaces have asked for bulk turns in the last 15 seconds (`SEND_LINE_ACTIVE_MS`), each gets an equal part of the rate through a lane of its own (kept in memory, like the line), so one large Broadcast can't fill the next seconds for everyone; a workspace alone gets the whole rate, and its lane goes back within seconds once the others stop. On an install with more than one workspace (the send worker reads it through the limits' 30-second cache and passes `sharedInstall`), a workspace's bulk mail is also admitted in parts: at most `SEND_ADMISSION_SHARE` (half) of what is left for it of the hour and the day, after the other workspaces' use, until the last fifth of each window (`SEND_ADMISSION_RELEASE`) releases the rest, so a very large send can't take a whole window before others arrive. A turn held back for any of these shares says so (`share: true`); the batch goes back on the queue for when it may ask again, and the send report shows "Waiting for capacity" (`broadcasts.share_wait_since` and `share_wait_until`, migration `0119`, reason `share` in `SendWait`) until a batch goes out again. Fair lanes can leave a little of the line unused while several workspaces send.

- **Who asks.** The send pipeline takes bulk turns for its batches (one turn per chunk with a per-second limit, one per batch without); Broadcasts and Flow emails both go through it. Every other email goes through `mailAdapter` (`packages/engine/src/adapters.ts`), which wraps the provider in `LimitedMail` when the worker binds `SEND_PACER` (`api`, `send`, `jobs`, `capture`, `site`) and takes a transactional turn per email: sign-in links, confirmations, invites, receipts, notices, test sends. Direct Send takes its turn before it records the send: transactional for `transactional`, bulk for `one_off`.
- **Per second.** One line for every email: a turn reserves count / rate seconds of it, so turns never overlap and the rate holds for all mail together. A bulk turn more than 2 s ahead sends the rest back to the queue as a new delayed message, because a queue retry would count against `max_retries`; they aren't failures, and the claim is undone. A transactional turn takes the next place after the turns already handed out (their callers are already waiting to send at their times), ahead of every bulk turn not handed out yet, so it waits at most the 2 s look-ahead plus one bulk turn (the pipeline's chunks are at most a second's worth, or one email below one a second). The trade-off: the short look-ahead sends more of a big send's chunks back to the queue when many consumers ask at once (they come back when the line has moved on, so its throughput is unchanged); keeping a share of each second free for transactional mail instead would cost bulk throughput every second, whether or not anyone signs in. `MAIL_MAX_PER_SECOND`, passed by the send worker and remembered by the object, caps the setting for everyone.
- **Hours, days and months** are fixed UTC windows (the clock hour, the calendar day, the calendar month), counted in the object's SQLite storage in the same synchronous step as each decision, so the counts survive eviction. Bulk turns may use all but a tenth of each limit (at least one email is always kept back); transactional turns may use all of it. What a turn counted for emails that did not go out (a retry, a quota error) is given back to the window it was counted in.
- **The email service's quota.** A provider error that says the account's daily or monthly quota is used up (`MailProviderError.quota`: Resend `*_quota_exceeded`, SES "Daily message quota exceeded", Postmark `405`) is told to the object, which refuses bulk turns, and turns whose caller can come back later (`canWait`: Direct Sends of both kinds, answered `429` with Retry-After before anything is recorded), until the next UTC day or month. Mail Swarm sends itself (sign-in links, confirmations, notices) is still tried. A batch keeps its handle on the object after a later turn fails, so it still gives back what earlier turns counted and still reports a used-up quota.
- **Waiting, not losing** (`packages/engine/src/send-waits.ts`). A send held back by an hour or a day (this install's or the service's) records `waiting_for` and `resume_at` on the Broadcast; its unsent recipients go back on the queue as a new message delayed until the window resets (12 hours at most per hop), and the fan-out checks again at least every 15 minutes. A month, ours or the service's, pauses the send: nothing is in flight, and the minute cron resumes it at `resume_at`. A provider that stops accepting mail (`halting`: a suspended account, a refused key or domain) pauses it as `service_stopped`, with `resume_at` the next try (`SERVICE_STOPPED_RETRY`): the minute cron (`retryStoppedSends`) sets the try after it first, as long after as the send has been stopped (5 minutes doubling, at most 6 hours), then sends one pending recipient as a `probe` batch, which goes through the pause. An answer other than a halt resumes the whole send; another halt keeps the stop's `waiting_since` and sends no new notice. Seven days after the stop, `endStoppedSend` ends it in one transaction: open recipients become `failed`, today's warm-up they held goes back, a post's Broadcast becomes `failed` (`partially_failed` if some went) with its Dispatch settled (back to draft when nobody got it), and a Flow email's standing Broadcast drops the wait and stays open, so recipients waiting on it never pile up past one stop; the owners get a second notice. It used to fail the Broadcast at the first halt and skip everyone left. Batches that arrive during a pause leave their recipients `pending` and give back the warm-up capacity they hold for today. Resuming (the cron, `POST /api/v1/broadcasts/{id}/resume` for admins, or saving new limits for sends waiting on this install's own) clears the wait and walks the fan-out again from the start, or for a Flow email's Broadcast puts its pending recipients back on the queue. The owners, admins and creator are emailed once per pause; the send report, the live monitor (`BroadcastProgress.waiting`) and Home say what the send waits for.
- **Warm-up held per recipient** (`broadcast_recipients.reserved_on`, migration `0070`). The UTC day whose Reputation Ramp capacity a recipient holds: set by the fan-out (or a Flow email's run) when it reserves, cleared when a pause gives it back, used up when sent. A walk that goes over a send again (a resume, a best-time release) reserves only for recipients that hold nothing for today, so one waiting in a delayed batch is handed out again without being counted twice (whichever message gets there first sends it; the claim stops the other), and one whose reservation ended with its day is counted on the day it really goes. Give-backs count and clear in one transaction, so a recipient held by two messages gives back once. The fan-out moves its cursor before it queues batches, guarded on where it started, and only the fan-out that moved it hands its slice out: two at the same place (a resume beside a delayed one) become one, and the other gives back what it reserved.
- **Throttling** (`429`, `5xx`): the queue's own retry the first two times, then the unsent recipients go back as a new message carrying the count (`throttled`), with a delay doubling from 30 s to 15 minutes and at least the provider's Retry-After. A batch never reaches the dead-letter queue for waiting. Claims and provider idempotency keys still keep each recipient to one email.
- **Unreachable object.** A turn that fails or takes over 2 s is skipped: batches keep to the per-second limit on their own, windows aren't counted, and transactional mail is sent.

**Click map** (`packages/engine/src/click-map.ts`, `packages/mail/src/click-map.ts`, flag `click_map`). A send's report shows each frozen email (Split Test version, full, teaser) with human clicks marked per link, using the same counts as the Links table. The email may hold raw HTML and goes in `<iframe sandbox="">`, so the server rewrites it from allow-lists before display: it writes the badges, removes placeholders, pixels and anything that fetches or navigates, and links have no href, since a fragment in a srcdoc document resolves against the page around it. People deleted since the send have no recipient row, so a send with several emails reports their clicks as `unplaced`.

**Best time** (`packages/engine/src/best-time.ts`, flag `best_time_send`). A send can hold readers until their best hour, in UTC, using the same `held` column as Split Tests: fan-out, batches and the reaper already skip held rows, and open rows keep the Broadcast open. The snapshot sets `send_after`; the send worker's minute cron releases what's due and restarts the fan-out, which reserves warm-up capacity when each reader really goes. The combination with a Split Test or Cohort Sample is refused. While warming, it applies only when the day's limit reaches the whole audience, since otherwise the limit would go to the earliest hours, not the likeliest readers.

The dashboard's Overview reads `GET /api/v1/channels/{channelId}/overview` (active Members, joined and unsubscribed in the last 30 days, and the latest eight sent Broadcasts with human opens and clicks, aggregated in one query), plus the existing sending-domain, Reputation Ramp, Dispatch and, when Stripe is connected, revenue reads. It shows no sample data: a Channel that hasn't sent yet sees its setup steps.

### Code embeds and custom email CSS

Both are flags (`code_embeds`, `custom_email_css`) that the engine resolves itself in `renderForWorkspace` (`emailStyleFor`), so every email render path applies them the same way: the Dispatch's stored render, previews, test sends, Broadcasts, Split Test variants and Flow emails.

- **Highlighting.** `@swarm/mail/highlight` is a dependency-free tokenizer (sticky patterns per language, no WASM, nothing that backtracks badly; code over 20,000 characters stays plain). Email gets `<span>`s with inline colours plus a class that a `prefers-color-scheme: dark` rule in the head overrides; the site gets classes only (its CSP allows no inline styles) coloured by the site stylesheet in light, dark and auto schemes; the editor gets the same classes as decorations. The code block's `language` attribute is set with the toolbar's language picker. Without the flag code renders plainly.
- **Table of contents.** `tableOfContents` is a top-level block listing the top-level headings. On the site, headings get `id`s (slugs, unique on the page) and the block links to them; a block in the free part never lists the gated part's headings, and the list stays out of the excerpt and search text. In email it is a plain list (no in-message anchors). Without the flag the email renderer refuses the block and the site leaves it out.
- **Custom email CSS.** One stylesheet per Channel (`channel_email_css`, 0029), edited in Settings → Sending by admins. `lintEmailCss` parses it with its own small parser: errors refuse it (`@import` and other loading at-rules, any `url()`, `expression()`, `javascript:`, `behavior`, `position: fixed`, `<`, `{{`, escapes, unbalanced braces, over 20 KB), warnings flag what major clients ignore (flex and grid, `box-shadow`, `position`, `var()`, `:hover`, `@keyframes`…). The render lints it again and works only from the parsed rules: rules with simple selectors (`p`, `.sw-button`, `a.sw-button`) are inlined after the renderer's own styles, everything else (`@media`, descendant selectors, pseudo-classes) goes into a `<style>` element in the head. The renderer's elements carry stable classes for it to target (`EMAIL_CSS_CLASSES`).

## Audience (Phase 3)

- **Member statuses** change only through the state machine in `@swarm/domain` (`canTransition`). Operators can't confirm on a Member's behalf or bring back an unsubscribed, bounced or complained Member; only the Member can return from unsubscribed, by confirming.
- **Capture.** The `capture` worker serves the embed script (`/v1/<form>.js`, versioned for SRI), the form iframe, subscribe (JSON from the iframe or the no-JS form post), confirm pages, the Member Center (`/m/<token>`) and `attr.js`. Subscribe answers identically whatever the address and does the work in `waitUntil`. Rate limits are sliding windows in the realtime worker's `RateLimiter` Durable Object. The no-JS form post is core and not gated (the Channel website runs no JavaScript, so its own form is that post; the snippet's HTML form renders every profile field type the frame does, and the server validates both paths the same way). UTM, referrer and landing-page attribution is stored only with flag `subscribe_attribution_fields`; the form id and a Champion's `ref` are always kept. The Member Center's digest choice shows, and is accepted, only with flag `digest`: nothing sends digests yet, so a stored value never changes sending.
- **Member Center billing (Phase 5).** A paying Member sees their Membership level, status and renewal, end or trial date. For a Stripe subscription they can also cancel at period end or resume, change level after a proration preview, update the payment method in a Billing Portal session, and open their invoices; all but canceling and resuming need a link emailed on request in the last hour, and the footer link shows a summary only (see [security](security.md), "Two kinds of Member Center link"). Every call runs on the Channel's connected account against the subscription found for the token's Member; nothing a form posts selects it. `member_subscriptions` is updated optimistically and the webhooks confirm. Comp, gift and lifetime access only show their end date.
- **Confirm opt-in.** Double opt-in is on by default per Channel (`doubleOptIn`), with a per-form override. Confirm tokens last 7 days; a GET only shows the page and the POST confirms, only from `pending`. One Gentle Reminder goes out 48 hours later.
- **Circles.** A rule tree (depth ≤ 20, ≤ 100 conditions) is compiled by `@swarm/engine` to SQL over one Channel's Members, with every value bound through a single JSON parameter and every column and path fixed in the compiler. Membership is materialised by the `jobs` worker in one transaction per refresh, guarded by a generation number; previews and sends compile the rules live. The five-minute cron queues Circles last evaluated over an hour ago and refreshes that were lost: 50 a run, at most 10 from one workspace, oldest first, with a lost refresh waiting 15 minutes and twice as long after each further loss (up to 8 hours), so Circles that keep failing can't hold up the rest. A manual refresh of a Circle pending for longer than 15 minutes queues it again at once and clears that wait.
- **Targeted sends.** A Dispatch's audience is `{ include, exclude }` Circle ids. Preflight and the snapshot use the same predicate, so the count in the confirm modal is the number sent; the rules are frozen into the Broadcast when it starts.
- **Jobs.** Imports (dry run, then chunked import), exports (CSV or JSONL to R2, 24-hour signed links) and bulk actions run on the `jobs` queue with a cursor on the job row, so a retried message resumes.

## Channel websites (Phase 4)

- **Publishing.** A Dispatch reaches the site when its send starts, or through "publish to web only". Publishing sets `web_published_at`, gives it a unique slug (`dispatch_slugs`; old slugs keep redirecting), indexes the readable part in `dispatch_search` (FTS5; for a members-only or paid Dispatch, the free part from `webShare` in `@swarm/mail`, the same split the page uses, or nothing when it has no gate divider the website shows) and bumps the Channel's `site_settings.cache_version`. `web_visibility` (public, members, paid, hidden) decides who reads past the gate divider.
- **Rendering.** The `site` worker renders pages on the server from the editor document (`renderWeb` in `@swarm/mail`): home in two layouts, archive, Dispatch pages, about, sections, custom pages, search, RSS, JSON Feed, sitemaps and `robots.txt`, with canonical URLs, OG tags and JSON-LD. The Channel's Capture Form renders inline.
- **Edge pipeline.** Tenant from Host → redirects → Bot Rules → reader session → verified crawler → route → headers, edge cache (keyed by host, Channel, path, the query parameters a route renders from (in a fixed order; tracking tags and other parameters are answered from that entry and never stored), reader class, `cache_version` and, on a home page with A/B tests running, the view's variants; search is never cached and is limited to 10 a minute per client) and analytics (daily rollups in D1, optionally Analytics Engine).
- **Site Studio.** The API manages settings, sections, pages, redirects (with CSV import), Bot Rules, web domains (Cloudflare for SaaS; the `jobs` cron refreshes pending ones) and site analytics. Every write bumps `cache_version`, which is the only cache purge.

## Membership levels and payments (Phase 5)

- **Money moves on the publisher's own Stripe.** Each Channel connects a Stripe Standard account over OAuth; every call runs on that account and no application fee is set (0% take).
- **Catalog.** Membership levels have immutable prices (a change is a new price; scheduled changes are promoted by the `jobs` cron, grandfathering or migrating existing Members), optional trials, a Founding Level and pay what you want. Coupons are Stripe promotion codes.
- **Buying.** The site's `/subscribe` page posts to `/_swarm/checkout`, which writes a `checkout_sessions` row and opens Stripe Checkout with a signed reference to it. Gift Passes, tips and lifetime purchases go the same way; pledges are taken before a Channel can charge.
- **Entitlements.** The webhook (`/api/v1/stripe/webhook`) keeps `member_subscriptions` in step with Stripe; comp grants, Gift Passes and lifetime purchases are rows there too. `recomputeEntitlement` turns them into the one `member_entitlements` row the site and the send pipeline read. The `jobs` cron ends grace periods and expired grants.
- **Gates.** A paid Dispatch admits readers whose level its Gate lists (any paid level when empty), on the web and in email; others get a metered allowance, then the Gate. Members manage billing in the Member Center.
- **Trials need the email up front.** A level's trial is card-required (Checkout always takes a card) and once per address per Channel (`trial_claims`). Stripe only learns the address inside Checkout, after the session (and its trial) is fixed, so the site offers the trial only when the address is known before Checkout: a signed-in reader, or the email typed on `/subscribe`, which the plans page requires for a level with a trial. Without it the reader pays from day one. Card-optional trials are not offered: without a card the only abuse control would be the address, which costs nothing to change.
- **Revenue analytics.** MRR counts paying Stripe subscriptions only (active, or past due within grace), at what they bill: the webhook stores `discounted_amount` and `discount_end` from the subscription's discounts (coupons that repeat while they last, or forever; a `once` coupon changes one invoice and not MRR), yearly plans as a twelfth. Trials are reported apart, as a count and the MRR they would add. Churn counts subscriptions that were paying when the range began; a trial starts paying when it converts (active, or an invoice paid), which also drives new paid Members and conversion by source.
- **Gift Pass reminders.** The `jobs` 5-minute cron mails the holder of a claimed Gift Pass a week before it ends (with a link to `/subscribe`; not when they pay or hold a longer grant), and the recipient of an unclaimed one (the buyer when there is none) a fortnight before `claim_by`, with a second claim link (`reminder_token_hash`; the first link keeps working). Each is sent once: the row is marked first and unmarked if sending fails.

### Flow graphs

- **Shape.** `graph_json` is `{ schema: 1, nodes, edges }`. Nodes have an `id`, a `type` (`trigger` or an action) and a typed `config`. Edges have `from`, `to` and a `label`: `default`, `true`, `false`, `a`, `b` or `timeout`.
- **Start events.** The trigger node holds every start event of the Flow, at most `FLOW_MAX_TRIGGERS` (10), with no plan limit. Its `config` is the first and `config.alsoStartOn` lists the others, each with its own settings and `filter`; `triggersOf(graph)` returns them in order. A graph saved before there could be several has no `alsoStartOn`, so old drafts and versions read as they are and nothing is rewritten.
- **Validation.** `validateFlowGraph` requires:
  - one trigger, with no edge into it, and no two start events the same (`duplicate_trigger`);
  - every edge between existing nodes, with a label its source type can produce, each label at most once per node;
  - no cycles (graphs are DAGs);
  - every node reachable from the trigger;
  - a different email on each send node.
- **Same-Channel check.** `collectReferencedIds(graph)` lists every Circle, tag, level, Dispatch, form, Flow, field, Ask, Roster, milestone and operator id the graph uses, across all its start events. The API checks them when a graph is saved and when it is published. The engine checks them again before each step and exits the run with `invalid_reference` when one fails.
- **Versions.** Publishing writes an immutable `flow_versions` row and sets `flows.live_version` and `trigger_type` (the first start event's). `extra_trigger_types` on both tables is a JSON array of the other event types, so enrolment can find the Flow; NULL means there are none. Runs stay on the version they enrolled on unless the operator migrates them.

### Runs

1. **Enrol.** The engine drains unprocessed events and matches each one to live Flows by `trigger_type` or `extra_trigger_types`, then to the start events of that type by their config and optional enrolment filter (a Circle rule); `chooseStartEvent` takes the first that lets the Member in. A match inserts one `flow_runs` row, whose `context_json.trigger.index` says which start event started it (stats and run history read it; a run with no index counts as the first). `flow_runs_one_open` stops a Member from having two open runs of one Flow, and `reentry` decides whether they can come back after a run ends.
2. **Step.** A `flow_step` job message (`runId`, `nodeId`, `attempt`) runs one node. The `flow_run_steps` row keyed on `(run, node, attempt)` makes it idempotent.
3. **Fail.** Errors retry with backoff. After 5 attempts the step is `failed` (never `done`), the run is `paused` with `step_failed`, and the operator is notified.
4. **Delay.** A delay of up to 12 hours is queued with `delaySeconds`. Every delay also sets `next_at`, and the every-minute sweep picks up waiting runs that are due.
5. **Statuses.** A run is `running`, `waiting`, `paused`, `completed`, `exited` (with an exit reason) or `failed`.
6. **Locks.** The pending `flow_run_steps` row is the lock for a node: a parked delay or wait keeps it pending with `result_json.until`, and the timeout, the awaited event or the delay's end resolves it with a conditional update, so exactly one of them moves the run on. Moving to the next node is conditional on `current_node_id`. A queued step holds a 15-minute lease in `next_at`; the sweep re-queues expired leases (lost messages) and a pending step older than 10 minutes can be taken over.
7. **Starting runs.** `startFlowRun` inserts the run at the trigger node and queues it; enrolment, `enrol_flow` steps, Add people and the API's test runs all use it. Re-entry `never` counts earlier non-test runs; a run per trigger event seq at most. Re-entry `after_exit` allows `FLOW_REENTRY_MAX_PER_HOUR` (10) runs of a Flow per Member per hour, which ends a Flow that re-fires its own trigger; further events start nothing. A Flow with several start events and re-entry `after_exit` also refuses a run when another started at most `FLOW_SAME_MOMENT_MS` (60 s) before the event, so a sign-up that emits two of its start events enters once even if the first run ends at once.
8. **Versions and Flow state.** `migrateRuns` moves open runs whose current node id exists with the same type in the new version and exits the rest with `migrated`. An archived or deleted Flow exits runs (`flow_archived`) at their next step; a paused Flow pauses them (`flow_paused`) except test runs; `resumeFlowRuns` restarts paused runs.
9. **Step details.** Delays "until a weekday and time" use the Member's `timezone` profile field (a valid IANA zone), else the Channel's `settings_json.timezone`, else UTC. `ab_split` takes arm `a` when the first 32 bits of SHA-256(`<runId>:<nodeId>`) mod 100 are below `percentA`. `webhook_call` POSTs JSON with `Swarm-Signature: t=<unix>,v1=<hex HMAC-SHA256 of "<t>.<body>">` and `Swarm-Webhook-Id: <runId>:<nodeId>`, https only, private hosts refused, 10 s timeout. `change_level` grants are comp grants whose note names the Flow and run; revoke ends only that Flow's grants. Comp grants need the admin role, so only an admin adds or changes a grant step, publishes a Flow that can reach one (itself or through `enrol_flow`), or adds people to it by hand (Add people, `/v2` enrolments, where keys and OAuth tokens act as editor); editors still edit the other steps. `notify_author` and pause notices mail the Channel's owners and admins.
10. **Unengaged.** The daily check emits `unengaged` (`days` = each threshold a live Flow uses) for active Members who joined more than N days ago with no human open or click in N days, once per stretch of silence (no event for that threshold since their last engagement), at most 1,000 per Channel and threshold per day.
11. **Who can be mailed.** `recheckBeforeSend` gates each send step, and the send consumer checks every recipient again when it claims them, so a Member who leaves while the message is queued gets nothing. `workers/jobs/tests/flows-fuzz.test.ts` holds this over random graphs, inbox rules and state changes (`FLOW_FUZZ_ITERATIONS` for a longer run, `FLOW_FUZZ_SEED` to replay a printed seed).

### Test runs

A test run skips `change_level` steps (`skipped: 'test_run'`), so it never grants or revokes a Membership level. It sends real mail from its own copy of each email (`broadcasts.test_run_id`, made on the first send, links included, closed by the sweep once the run has ended). A Member holds one recipient row per Broadcast, so a test sent from the real one would use up their real email and land in its numbers. The copy isn't in `flow_emails`, so stats, winner picking and `alreadyReceived` don't see it. A test run and a real run of one Member can be open side by side (`flow_runs_one_open`, `flow_runs_one_open_test`). Test sends from before this are still on the real Broadcast, and `broadcastStats` leaves them out (`OLD_TEST_SENDS_SQL`).

### Rehearse

`POST /api/v1/flows/{flowId}/rehearse` says what a Flow would do for a Member, on the draft or the live version, with nothing written, sent or called.

- **One decision.** `decideStep` in `flows-decide.ts` reads and answers: the outcome of a step, an inbox rule hold, or the action to take. `execute` in `flows-engine.ts` calls it, then does the writing; `rehearseFlow` in `flows-rehearse.ts` calls it, then only records the answer. So the Member recheck, the paused publication, `alreadyReceived` and `decideInboxRules` run the same in both. Entry goes through `chooseStartEvent`, `whyRunRefused` and startFlowRun's own guards (`entryGuardsSql`).
- **Reading as the run would by then.** `readOnlyView` refuses anything but a read. What earlier steps would have changed (tags, profile fields, paid access, emails sent and the ledger, a hold waiting, an assumed open) is laid over the real tables as common table expressions, so the real SQL, down to compiled Circle rules, sees it. Where a run parks, a rehearsal moves its clock on and decides again from the top.
- **What it can't know.** Whether someone opens or clicks is the writer's answer (`answers`); no answer means they don't. An A/B split is drawn from the rehearsal's own id unless picked. It assumes webhooks answer and that a paused publication or warm-up comes back. It doesn't follow another Flow a step or event starts, whose emails would count toward the limits, and it reads Circle membership as of now. A draft has no warm-up yet, so its emails don't wait for one.
- **The check.** `workers/jobs/tests/flows-rehearse.test.ts` runs random graphs from the fuzz generator, with random inbox rules and several start events, through a rehearsal and then the real engine and send pipeline, and compares entry, every step, its time, every hold, every email and the end. It also compares every table, the queues and the outbox before and after each rehearsal (`FLOW_REHEARSE_ITERATIONS` for a longer run, `FLOW_REHEARSE_SEED` to replay a printed seed).

### Add people

`POST /api/v1/flows/{flowId}/people/preview` counts who would enter a live Flow and why the others wouldn't; `POST .../people` starts a bulk job (`flow_enrol`) once `confirmCount` matches that count, and audits `flow.people_added`. The verdict (`flows-admit.ts`) refuses anyone who can't be mailed, uses startFlowRun's guards, and asks the start events' filters: there is no event to match, so anyone one start event would let in may enter. The job asks again for each chunk, and a retried chunk finds the runs it already started (`context_json.addedByJob`). `bulk_jobs.entered` counts them. Once in, a run is a run: its emails recheck the Member and obey the inbox rules.

### Inbox rules

A Channel's limits on automated email, across all its Flows (`channels.settings_json.inboxRules`, `GET` and `PUT /api/v1/channels/:id/inbox-rules`, Viewers read and Editors set). Every rule is off until a person sets one, for existing and new Channels.

- **The rules.** `perDay` and `perWeek` per Member over any 24 hours and any 7 days, `quietHours` (may cross midnight), and `newsletterDay` (the calendar day of a post that Member got or will get, plus `hoursAround` on either side). Times are read in `memberZone`: the Member's `timezone` field, else the Channel's, else UTC.
- **The decision.** `decideInboxRules(facts)` in `flows-inbox-rules.ts` is pure, with no database and no clock of its own, so anything that needs the answer without a real run can call it. It returns `send`, `hold` with a reason and a time, or `expire`. `loadInboxRuleFacts` reads the facts for a real run. Limits are checked again as one statement when the place is taken (`takeLedgerSlot`), so two runs deciding at once can't both use the last one.
- **A hold.** The send step parks like any deferred send (`result_json.until`, `deferred: 'inbox_rules'`) with one `flow_holds` row per (run, step), which keeps when the wait began and the latest reason. When it comes due the step runs again from the top, so `recheckBeforeSend` runs first, and the send consumer's check still applies after that. Held runs behave the same whichever start event began them.
- **Order and spacing.** A Member's held emails go in the order they were held. An email behind another waits at least `IN_LINE_GAP_MS` (60 s) after it, and each one decides again when it comes due, so a limit spaces them out.
- **Going stale.** An email whose wait would pass `maxHoldDays` (14 by default, 90 at most) exits with `hold_expired`, without the email.
- **Send regardless.** A `send_email` step with `sendRegardless` is never held and still counts toward the limit. Left unset, it is on for the first email of a Flow whose start events are all `confirmed` or `member_joined`, and off otherwise (`defaultSendRegardless`). The answer belongs to the step, so a mixed Flow's first email obeys the rules for everyone.
- **The ledger.** `flow_email_ledger` has one row per automated email a Member was given, for 8 days (the daily check prunes it), whether or not a rule is on, so limits count from the first day they are set. The migration fills it from the last 7 days of Deliveries. Test runs are never held and never count.
- **What goes with what.** `flow_holds` and `flow_email_ledger` cascade with the Member, so erasure removes them. The Member export lists holds as `flowHolds`.
- **Stats.** `GET /flows/:id/stats` has `held` per node (waiting now, in total, expired), and runs carry `hold` and, in detail, `holds`.

### Why a Member did or didn't enter

The Member's page lists every live Flow of the Channel with what happened (`GET /api/v1/members/:id/flows`, `memberFlowHistory`, Viewers and up).

- **What is stored.** `flow_enrol_decisions` holds at most one row per Member and Flow: the latest start event that matched them and did not start a run, with its reason (`FLOW_ENROL_DECISIONS`), version and event type. A run is already a `flow_runs` row, so starting one deletes the row instead of writing another. An event that matches no start event writes nothing, so busy event types cost one in-memory match.
- **Why not one row per event.** Enrolment sees every event for every Flow listening to its type. The upsert caps storage at Members times live Flows, at about 200 bytes a row with its index, and skips the write when the answer is unchanged and under a day old, so a Member clicking every link of a Flow they already ran writes at most once a day. Only a refused start reads anything extra (`whyRunRefused`). Working the answer out when the page opens can't say what happened, because the Member and the Flow have changed since, and it can't tell an event that never fired from one that was refused.
- **What goes with what.** Rows cascade with the Member, so erasure removes them. The daily check drops the rows of archived and deleted Flows (`pruneFlowDecisions`), in pages. The Member export lists them as `flowDecisions`.
- **Enrolment by other routes.** `enrol_flow` steps and the API don't clear a row, so the page ignores one older than the run.
- **Email counts.** Received means a delivery of the run's Broadcast that was sent and didn't bounce. Possible is what the run sent, the email it stopped at, and the most any path ahead holds; a branch not taken doesn't count.

### Flow emails

- A Flow email is a Dispatch of kind `flow`. It is never listed with Dispatches, never published and never sent to an audience.
- Publishing a version freezes one Broadcast of kind `flow` for each send node (`flow_emails`). It uses the same renderer, link targets, tracking, unsubscribe and text part as any Broadcast.
- Before each send, `recheckBeforeSend` confirms the Member is still active and not suppressed. For paid-only or free-only emails it also checks the entitlement. If a check fails, the run exits with the reason.
- The engine then adds one `broadcast_recipients` row and queues a `batch` message on the send queue, so the batch sender's gate and MIME path apply unchanged.
- A Member gets a given node's email at most once per version. Flow Broadcasts stay `sending` while their version can send; the reaper and completion skip them.
- A new version doesn't send an email again. An email is its Dispatch, which versions share, so a Member holding a recipient row for that Dispatch from another version skips the step (`already_received`, `alreadyReceived`), unless the row was stopped or failed. A writer can ask for an email to go again when publishing (`resendNodeIds`, `flow_emails.resend`): versions before the newest such one no longer count. Test runs skip this check.

### Email or website blocks

A linked snippet is a top-level `snippet` block (`attrs.snippetId`, flag `snippets`). `expandSnippets` in `@swarm/mail` swaps it for the snippet's blocks before either renderer runs, so gates, the free share of a post, the table of contents, media and polls treat them as the post's own. Snippets are read by Channel only. A snippet can't hold another snippet, a gate or a Smart Block. `renderForWorkspace` expands for email; a send reads each snippet once (`RenderInput.snippets`) and freezes the result with the Broadcast, and Flow emails freeze when the Flow is published. The site expands on every render in `render/data.ts`, and changing a snippet bumps `cache_version` and refreshes `dispatch_search` for the posts that use it. A snippet that is gone renders nothing, and the email renderer warns.

A block's `attrs.showOn` is `email` or `web` (absent or null shows it on both; anything else is refused by both renderers). `renderDispatch` leaves `web` blocks out of its html, text, links, footnotes and table of contents; `renderWeb` does the same for `email` blocks, which keeps them out of excerpts, feeds and `dispatch_search`, since all of those read its output. Each still checks the block it leaves out, so a broken one is refused. A website-only Smart Block takes no index in `smartBlocksOf`, so the send pipeline's conditions and the renderer's markers stay in step. The flag `block_visibility` only guards saving: the API answers `feature_disabled` for a document that uses the attribute while it is off, and rendering follows a stored value either way, so turning the flag off never puts email-only text on the website.

### Smart Blocks, Split Tests and Cohort Sampling

- **Smart Block.** A top-level editor node `smartBlock` whose `attrs.condition` is a Circle rule. In the frozen html and text, each block is wrapped in `<!--swarm:sb:<i>-->…<!--/swarm:sb:<i>-->`. The snapshot decides which blocks each recipient sees (`broadcast_recipients.smart_blocks_json`; one compiled query per block per snapshot chunk), and personalisation removes the hidden ones. A Flow send calls `smartBlockVisibility(db, channelId, memberId, document)` for the same answer. Conditions may use the Circle leaves `circle` (a Circle's materialised members) and `level` (the current paid entitlement and its level); ids must belong to the Channel when a Dispatch is saved, and a foreign id matches nobody in SQL. A condition that no longer compiles hides its block. Text that imitates a marker is refused by the renderer. `GET /dispatches/:id/preview?memberId=` renders the email as one Member.
- **Smart Blocks on the web.** The site renders every reader the anonymous view (`attrs.anonymous`, hide by default): pages are cached and shared, so a per-reader evaluation would need an uncached render per signed-in reader. `renderWeb` takes a `smartBlockVisible` callback for when that is wanted. Hidden blocks are kept out of the page text and the search index.
- **Split Test.** 2 to 4 variants of the subject (with an optional preheader) or the content (`split_test_variants`; variant A is the Dispatch). At start each variant's render is frozen and its links join the Broadcast's link targets. The snapshot assigns each Member by a hash of the test id and the Member id: the test share is spread evenly over the variants (`split_variant_id`) and the rest is held back (`held = 1`); fan-out, batches and the reaper skip held rows. The jobs worker's minute cron (`decideHoldBacks`) decides once `decide_at` has passed and the test part has gone out: per-variant rates of human opens, clicks or goal events (`member_events` after the send), `pickSplitTestWinner`, `decision_json`, and the held recipients are released with the winner in one batch guarded on the test status, so a retry releases nobody twice. A 100% test only reports. The full/teaser split of a gated paid Dispatch still applies per recipient; on such a Dispatch only the subject can be tested, and only variant A may carry Smart Blocks.
- **Cohort Sampling.** Holds recipients back the same way (`inShare`). They are released when the sample's bounce (of sent), complaint and unsubscribe rates (of delivered), and optionally its open rate, stay within the thresholds. Otherwise the sample halts: the held recipients are marked skipped, the Broadcast completes, and the send worker emails the workspace's owners and admins (`cohort_halted` on the send queue). A Dispatch has a Split Test or a Cohort Sample, not both.

### Ask, Signup Journeys and Smart Prompts

- **Ask.** Polls (one choice question) and surveys (up to 20 questions). `ask_responses` keeps one answer per Member per question; a new answer replaces the old one while the Ask is open (status `open`, before `closes_at`). A question with `field_id` copies the answer into that profile field in the same batch (a select field for choice questions, a text field for text ones, never an encrypted one), so Circles filter on it with an ordinary `field:<key>` leaf. Every new or changed answer appends `ask_answered`.
- **One-tap email polls.** The editor block `askPoll {askId, questionId}` renders one button per option with the placeholder `{{@ask:<optionId>}}`. The send pipeline finds those placeholders in the frozen templates (`askOptionIds`) and signs one link per option per recipient (`askLinks`: `<CAPTURE_ORIGIN>/a/<token>`, token purpose `ask`, `{m, o, c}`, 90 days, `ASK_SIGNING_KEYS`, which capture checks with the public key), passed to `personalize` as the `ask` callback. Previews and test sends get `#`. The capture worker's GET shows a confirm page; only the POST records. On the web the block's options link to the survey page.
- **Survey page.** `/_swarm/ask/<id>` on the site. Answering needs a signed-in reader or a survey-page link (`?t=`, purpose `ask-page`, `{m, a}`, 7 days, offered after a one-tap answer to a survey). Anonymous visitors are asked to sign in.
- **Signup Journeys** (flag `signup_journeys`). After a successful sign-up with a message (not a redirect), the visitor goes to `/v1/j/<token>/0` on the capture origin: up to three steps of the live journey for the form (or the Channel-wide one). The token (purpose `journey`, one day) carries the journey, the variant, the form, the address and the id the sign-up will give a Member it creates (both sealed; the vault mints and opens the token), because the sign-up runs after the (address-independent) response. The variant is a weighted pick from a keyed HMAC of the address, so it is stable per Member and reveals nothing. Answers are recorded only for the Member with that id, which exists only when this sign-up added the address: a known address, or one added minutes earlier or later by another sign-up, an import or the API, has a different id, so its Member gets nothing. Steps: `ask` (flag `reader_survey_on_subscribe`), `recommendations` (flag `partner_exchange`; shows nothing until Phase 8), `upsell` (the site's `/subscribe?level=`), `welcome` (flag `welcome_page`, with the opt-out text). Views, completions and skips go to `signup_journey_daily`; promoting a variant sets `winner_key`.
- **Smart Prompts** (flag `smart_prompts`). Capture Forms with `kind = 'prompt'` and `placement_json`. The site renders `dispatch_end` and `gate_hit` prompts server-side as a plain form; `scroll`, `exit_intent` and `delay` prompts render hidden and a nonce'd inline script under 2 KB reveals them. "No thanks" posts to `/_swarm/prompt/dismiss`, which stores the prompt id and the end of its cooldown in a first-party cookie; requests with that cookie skip the edge cache.

### Champions and the Funnel Explorer

- **Counted referrals.** A referral counts toward milestones (`referrals.status = 'counted'`) once the referred Member has confirmed and opened an email within 14 days.
- **Held referrals.** Referrals from disposable domains are rejected. When one Champion gets more than 3 referrals from one /24 or /48 within 24 hours, they are held for review.
- **Awards.** `champion_awards` is unique per Member and milestone, so each reward is granted once.
- **Funnel Explorer.** Reads `funnel_daily`. Lookback is 30 days on the free plan (an earlier start is moved forward) and unlimited on paid plans.
- **Funnel rollups** (`@swarm/engine` funnel.ts). Visits and form views are anonymous counts: the site edge adds a visit for each visitor's first page view of the day, with that view's source and UTM tags, and form views are copied from `capture_form_daily`. Subscribes, confirms, first opens and paid count once per Member, on the day they happen, attributed to the Member's first touch (`source_json`), sign-up form and referring Champion. The jobs worker's minute cron reads `member_events` with its own cursor (`funnel_cursors`; it never touches `processed_at`) and scans `deliveries.human_opened_at` by time. `funnel_members` (`0011_funnel.sql`) holds one row of stage flags per followed Member, so a re-run never double counts. Imported and operator-added Members are not funnel traffic.
- **Codes and links.** A Member's `champion_code` (8 symbols, no look-alikes) is assigned on first use and is unique per Channel. The share link is `<site>/?ref=<code>`; the short link `<site>/r/<code>` sets a first-party cookie (`__Host-swarm_ref`, 30 days) and redirects home. The site edge adds the code as a hidden `ref` input to its subscribe forms after the edge cache, so cached pages never carry it; the embed reads `?ref=` itself. The capture worker resolves the code to a Member of the same Channel.
- **Recording.** At sign-up the referral is stored `pending` with the sign-up's /24 or /48 (`referrals.ip_prefix`, never the full address). Self-referrals (same Member, or the same address ignoring dots and `+tags`) are refused. With `block_disposable` a disposable address is stored `rejected` (`disposable_domain`).
- **Counted referrals.** The jobs worker counts every minute. A referral counts toward milestones (`referrals.status = 'counted'`) once the referred Member has confirmed and opened an email (a human open) within `engagement_days` (14) of confirming. Still pending after that window, it is `rejected` (`not_engaged`); a referred Member who leaves first is `rejected` (`unsubscribed`).
- **Held referrals.** When one Champion gets more than `cluster_limit` (3) referrals from one /24 or /48 within `cluster_window_hours` (24, counted back from each referral), the extra ones are `held` (`ip_cluster`). Editors approve (count) or reject them.
- **Awards.** While Champions is on for the Channel, reaching an active milestone inserts a `champion_awards` row; it is unique per Member and milestone, so each reward is granted once however many runs race, and only the run that inserted it fulfils it. `comp_level` creates a comp grant for `comp_days` and recomputes the entitlement; `coupon` emails the coupon code; `manual` and `goods` (Phase 8) stay `pending` until an admin completes them. The Champion gets an email from the Channel's sender. A new award also emits `referral_milestone`, which can start a Flow; the built-in email is sent either way, and `fulfil_flow_id` is stored for a Flow-sent email later. A referral emits `referral_succeeded` when it becomes `counted`: the referred Member confirmed and opened an email, or a teammate approved a held referral. A bare confirmation doesn't, so the fraud checks hold for Flows too. The payloads carry ids only, never the referred Member's address. Referrals are recorded and counted whether or not Champions is on, as before, so `referral_succeeded` can fire while it is off; `referral_milestone` can't, because awards need it on. Adding a milestone or turning Champions on awards Champions who already qualify.
- **Public top Champions.** `/champions` on the site (flag `referral_awards`, Champions on, `public_leaderboard`) lists first names and an initial, never addresses.
- **Funnel Explorer.** Reads `funnel_daily`. Lookback is 30 days on the free plan and unlimited on paid plans.
- **Series** (flag `post_series`). An ordered group of Dispatches; a Dispatch is in at most one Series. The site shows `/series/<slug>` in order, "Part N of M" and a "Next in series" link on Dispatch pages (counting only Dispatches on the site), and lists Series in the sitemap. Every Series change bumps the site cache version.

## Platform (Phase 7)

Tables are in `migrations/0012_platform.sql`; shared constants (plans and limits, scopes, key formats, webhook events and signature, DSR timers, second factors, DMARC) in `packages/domain/src/p7-platform.ts`. Each surface's request and response schemas sit beside it in `p7-*.ts`.

### Plans and limits

Plans are ordered `free < pro < scale < enterprise` (`planAtLeast`); "paid" means above free. `PLAN_LIMITS` sets, per plan, active API keys, OAuth apps, webhook endpoints, `/v2` requests per minute and burst, Direct Send messages per day (none on free), audit retention, export destinations, and whether SSO and dedicated IPs are available (Pro and up). A limit is checked on create and answers `plan_required` when the plan does not include the feature at all, `conflict` when the count is reached.

### The public API (`/v2`)

- **Credentials.** `Authorization: Bearer sk_live_…` (a scoped key) or `Bearer oat_…` (an OAuth access token). `/v2` never reads the session cookie, so it has no CSRF check. Both resolve to an `ApiPrincipal` (`workers/api/src/v2/context.ts`): workspace, optional Channel list, scopes, plan and rate cap. Unknown, revoked, expired and IP-blocked credentials all answer the same `401`.
- **Scopes.** Each `/v2` route asks for exactly one scope (`requireScope`, `requireApiChannel`); a `:write` scope grants its `:read`. A Channel outside the principal's workspace or Channel list answers `404`. Missing scope is `403 insufficient_scope`.
- **Keys.** Only `sha256` of the full key is stored, with an 8-character prefix for display. Keys carry scopes, optional expiry, optional CIDR allowlist, `last_used_at` and an optional per-minute cap below the plan's limit.
- **OAuth2.** Authorization code with PKCE (`S256` only, required for every client). Codes are single-use and live 60 seconds. Access tokens live an hour; refresh tokens 30 days and rotate on every use. Presenting a refresh token that was already used revokes its whole family.
  - An app is registered by one workspace and may be authorised by an admin or owner of any workspace, who picks the workspace (and optionally Channels) on the dashboard's consent page. `/oauth/authorize` only checks and hands over; the decision is a CSRF-checked `POST /api/v1/oauth/consent`. `/oauth/token` and `/oauth/revoke` are form-encoded, outside `/api` (no cookie, no CSRF check) and authenticate the client. An OAuth principal's id is the grant, so limits and idempotency survive a refresh. Details: `docs/oauth.md`.
- **Direct Send.** `POST /v2/channels/{channelId}/sends` (`sends:write`, paid plans, `directSendsPerDay`): one email to one Member from a Template or a Dispatch, sent synchronously through the MailAdapter on its own SES configuration set. Suppression always blocks; `one_off` needs an active Member and carries One-Click unsubscribe, `transactional` does not. Details: `docs/direct-send.md`.
- **Rate limits.** A token bucket per principal in a Durable Object (`ApiRateLimiter` in the realtime worker, one object per principal). It refills at min(plan rate, key cap) a minute and holds that plus a burst; a key cap scales the plan's burst by the same ratio (`apiRatePolicy`), so a low cap is not undone by a large burst. Every response to an authenticated request carries `RateLimit-Limit` (the bucket size), `RateLimit-Remaining`, `RateLimit-Reset` (seconds until full) and `RateLimit-Policy`; a refusal is `429 rate_limited` with `Retry-After`. Middleware order on `/v2/*`: authenticate, rate limit, idempotency, then the route's scope check.
- **Writes** accept `Idempotency-Key` (24 hours, per principal, `api_idempotency`; `/api/v1` too, per operator, and replayed only to the session that sent it): the same key with the same method, path and body replays the stored response (`Idempotent-Replayed: true`); a different request with that key is `409`, and so is a retry while the first is still running. 5xx and 429 answers are not stored. The jobs worker's daily cron prunes rows older than 24 hours.
- **Who acts.** `/v2` writes run the same code as the dashboard (`lib/members.ts`, `lib/imports.ts`, the exported Dispatch functions) with an `Actor` that has no teammate: audit entries have a null actor and `metadata.via` naming the key or token; `created_by` columns stay null.
- **Resources.** Channel resources live under `/v2/channels/{channelId}/…` and answer `404` for rows of another Channel. Lists are cursor-paged with opaque base64url cursors. Resource shapes are the dashboard's (`MemberDetailSchema`, `DispatchSchema`, …) so webhooks can send the same ones; a Channel omits the seat role (`ApiChannelSchema`).
- **Documents.** `/v2/openapi.json` (OpenAPI 3.1, built from the `/v2` routers only; every operation has an `operationId` and `x-swarm-scope`), `/v2/reference` (rendered on the server from that document, no script) and `/.well-known/api-catalog` (RFC 9727). `pnpm openapi:v2` writes `docs/openapi-v2.json` and regenerates the TypeScript SDK (`packages/sdk`) from it.
- **Migration shim (D2).** Import only: an import's `source` is `csv`, `platform_csv` or `platform_json` (exports of other newsletter platforms). Platform exports get column aliases (their names for name and paid plan onto first name and tags), and exclusion rules stored with the job: rows whose status says unsubscribed, or whose email was turned off, are counted as suppressed in the dry run and never imported. JSON is converted to CSV on upload. The same sources are accepted by `POST /v2/channels/{channelId}/members/bulk`, which creates an ordinary import job (dry run, then confirm). It is not a second API surface.

### Audit log retention

Retention (the workspace's `audit_retention_months`, 24 by default, or the plan's `PLAN_LIMITS.auditRetentionDays` when shorter, on every plan: `auditRetentionMs` in `lifetimes.ts`) is applied by the jobs worker's daily cron, and the hash chain must still verify afterwards. Pruning a workspace: verify the kept chain (a broken chain is never pruned, only logged); append an `audit.pruned` event naming the last pruned seq and its hash; then, in one batch, move `audit_anchors` (`0013_open_api.sql`) to that seq and hash and delete the events up to it (at most 5,000 a run). Verification starts from the anchor instead of the genesis hash: the first kept event must have the anchor's seq + 1 and chain from its hash. Editing a kept event or moving the anchor breaks verification, and the `audit.pruned` entries, which are themselves chained, record every anchor the chain has had. Exports (CSV, JSONL) include `prev_hash` and `hash` so a copy can be verified outside Swarm.

### Event Webhooks

- **Sources.** Member events are read from `member_events` with their own cursor (`event_cursors`, never `processed_at`), and the rest (`dispatch.*`, `broadcast.completed`, `flow.completed`, `member.deleted`, …) from the `platform_events` outbox. The jobs worker fans each event out to the matching active endpoints as `webhook_deliveries` rows (unique per endpoint and event) and queues the attempts.
- **Signature.** `Swarm-Signature: t=<unix seconds>,v1=<hex HMAC-SHA256(secret, t + "." + body)>`; during a rotation the previous secret adds a second `v1=` for 24 hours. Receivers refuse timestamps more than 5 minutes off. `Swarm-Event-Id` is stable across retries and redrives.
- **Delivery.** A 10-second timeout, up to 8 retries with exponential backoff, and the endpoint is disabled after 72 hours of failing every delivery, with an email to the workspace's owners and admins. The log keeps the response code, a 1 KB excerpt and latency; redrive re-sends the same event id.
- **How it runs** (`packages/engine/src/webhooks.ts`, `0015_webhooks.sql`). The jobs minute cron reads each source in bounded pages and writes at most `WEBHOOK_FANOUT_MAX_DELIVERIES` (5,000) deliveries per source per run and at most `WEBHOOK_FANOUT_QUERIES` (300) D1 queries per run for both sources together, a batch counting as one, so a backlog never uses up the minute invocation's 1,000 queries that the other cron steps share (whole seqs only; the cursor stops before the first seq left out). A workspace that takes more than `WEBHOOK_FANOUT_WORKSPACE_DELIVERIES` (1,000) in a run is held: the shared cursor goes on with the other workspaces, and the held one catches up in seq order from its own cursor in `event_cursors` with what is left of the run, rejoining once it reaches the shared cursor, so one workspace's backlog never delays the others; a page's deliveries and its cursor move commit together, and event ids are `ev_` + sha256 of `<source>:<seq>`, so a re-read page creates nothing twice. Matching endpoints are active, list the type, have no Channel filter or the event's Channel, and existed when the event happened. The envelope is built and stored at fan-out; every attempt and redrive sends those bytes. A `webhooks` Queue message only names a delivery: the consumer claims it with a lease on `next_attempt_at`, records the attempt in `webhook_attempts` and schedules the retry in D1 (queued with `delaySeconds` up to 12 hours; the minute sweep re-queues anything overdue). Deliveries to paused or disabled endpoints are canceled when their turn comes; test events go to any status and never count towards auto-disable. Redrive resets the retry budget (`attempts_base`) and is a no-op for a pending or retrying delivery.
- **Payload sources.** Member data is the Member as it is at fan-out (`toMember`, now in `api-shapes.ts` with the Dispatch, Broadcast and FlowRun mappers). Tag and field changes of one Member in one page become one `member.updated`. `member.unsubscribed` and operator edits of name, digest or status have no member event, so they use the outbox with payload `{}` and the Member attached at fan-out (`memberUnsubscribedStatement`, `memberUpdatedStatement`, placed before the write like the tag helpers). Emitters: `unsubscribeDelivery` (unsubscribe page and One-Click), `unsubscribeMember` (Member Center), `leaveBeforeConfirming`, complaints (`suppress`), the Member PATCH and bulk unsubscribe; `member.deleted` from the Member DELETE and bulk delete (ids only, `member_id` NULL); `dispatch.scheduled` from the schedule route; `dispatch.sent` and `broadcast.completed` from `maybeComplete`; `flow.completed` when a run reaches its end (test runs left out). Receivers' guide: [webhooks.md](webhooks.md).

### Privacy Center

Members ask for an export or erasure from Member Center; operators see a queue with SLA timers (export 24 hours, erasure 30 days). Erasure hard-deletes personal data in every table, keeps deliveries with the Member reference removed so aggregate stats still add up, and keeps the suppression as `sha256(lower(email))` so the address cannot be imported again. A test lists every table and checks no personal data remains.

- **Scope.** A request is about one address across the whole workspace: every Member with it, in every Channel (the suppression is per workspace, so a per-Channel erasure could not hold). While a request is open, `dsr_requests.email_enc` holds the address sealed by the vault for that request; it is cleared when the request completes or is rejected, and only `email_hash` stays. Code: `@swarm/engine` `privacy.ts`; the run columns are in `0016_privacy.sql`.
- **Lifecycle.** `pending` waits for an admin; `processing` is queued for the jobs worker; then `completed`, `rejected`, or `failed` after three runs (an admin can retry). Member Center exports start in `processing`: the file's link is mailed to the address, so only its inbox gets it. Member Center erasures start in `processing` only once confirmed from the inbox (below); for an address Swarm can't mail (a hard bounce or complaint, or every Member `bounced` or `complained`) they always start `pending` with source `member_center_unverified`, whatever link opened the page: a forwarded footer link proves nothing, and neither does one emailed a moment ago, which a holder of the member signing key could forge. The queue and the approve dialog warn the admin to confirm with the person another way first. A request the Member confirms from their inbox that finds an unverified one pending runs it (audited as `privacy.request_verified`), so a forged one cannot hold the person's own back. A pending request an admin or the API filed is left for the admin. Operator requests (`POST /api/v1/workspaces/{id}/privacy/requests`, admins and owners, for someone who asked another way) start `pending`; approving an erasure needs `confirm: "erase"`. One open request per kind and address. Erasure waits while a Stripe subscription still renews (it could not be canceled afterwards). Every step is audited without the address.
- **Member Center.** "Email me a copy of my data" and "Delete my data" are POSTs from the page. The page's link is in every email footer, so whoever holds a forwarded email can open it; deleting therefore takes two confirmations. The page's checkbox only mails the address a single-use link (`dsr_confirmations` in `0064_rights_and_keys.sql`; token purpose `dsr-confirm` with `CAPTURE_KEYS`, payload `{ c, m, n }` where `n` is a nonce the row keeps only hashed (`nonce_hash`, 0145), `DSR_CONFIRM_LINK_HOURS` = 24; at most one email per `DSR_CONFIRM_RESEND_MINUTES`). `/m/erase/<token>` is a page with a button; its same-origin POST uses the link (once, atomically) and files the request. A renewing paid subscription refuses it at both steps, without using the link up. Unsubscribing stays one step. The jobs worker's minute cron runs exports and confirmed erasures. An export is one JSON file in R2 `EXPORTS` (`dsr/<workspace>/<request>.json`): per Member, the profile with decrypted fields, tags and Circles (with tracking and inactive-reader state), confirmations, consent records and member events, deliveries, opens and clicks with the network data kept with them (network prefix, network number, browser family), Ask answers, referrals (with the network prefix of their own signup when someone referred them) and Champion awards, memberships, payments, comp grants, pledges and Gift Passes (amounts and dates; there is no card data), Flow runs and enrolment decisions, website sign-ins, payment and customer references, access grants, metered reads, per-send copies, automation and direct emails, then the rows that hold the address without a Member (`addressOnly`: checkouts, orders, Gift Passes, trial claims, sponsor bookings, bounce counters), the suppression, and `excluded`: every person-linked table left out on purpose, with the reason (`EXPORT_INVENTORY` in `privacy.ts`; the jobs privacy test fails on an unclassified table). Each history keeps its newest 25,000 rows (`EXPORT_ROW_LIMIT`, read 5,000 at a time); `truncated` names the kinds that had more. The email links to `/m/data/<token>` on the capture origin (purpose `dsr-export`, `DSR_EXPORT_LINK_DAYS`); the GET is a page and only its POST sends the file, so link scanners download nothing. Files are deleted when the link expires.
- **Addresses Swarm can't mail.** Subscriber settings hide "Email me a copy" for a `bounced` or `complained` Member and tell them to ask the publisher. An export filed by an admin for such an address is built but not emailed (the request's note says so), and an admin downloads it from the queue (`POST …/privacy/requests/{id}/download`, audited as `privacy.export_downloaded`) to hand over another way.
- **Erasure** (`eraseAddress`, the only one). Deletes the Members, which cascades to field values, tags, Circle rows, recipients, confirmations, referrals, events, Flow runs and enrolment decisions, Ask answers, sessions, entitlements, subscriptions, comp grants, pledges and Champion awards. Deliveries stay with `email = 'erased'`, no Member, no provider message id or error; opens and clicks lose their network prefix; `payments` keep amounts without the Member. Funnel rows credited to the Member as a Champion fold into the "no Champion" cut, so funnel totals, Broadcast stats and Ask aggregates still add up. Rows that hold the address or the id as text are scrubbed: gifts, checkouts, trial claims, soft bounces, gate meter reads, import reports, bulk selections, webhook deliveries, idempotent replays and platform events. Resume cursors that point at the Member move to the id just below it, which selects the same rows. The suppression becomes `email = 'erased+<suppression id>@invalid'` with the hash. One `member.deleted` platform event per Member carries ids only, for webhooks and export destinations. The audit log keeps Member ids it already holds, because its hash chain can't be rewritten; it never holds addresses. Channels that lost Members get a Circle refresh.
- **Erased addresses** are refused wherever a Member or an address is added, through one helper (`isErasedAddress` / `erasedAddresses`): subscribe (and pledges and Smart Prompts, which use it), imports (reported as suppressed), operator create (409), site checkout for the buyer and a Gift Pass recipient, Gift Pass claims, and the Stripe webhook's buyer creation. `/v2` routes that add Members must call it too.
- **Not rewritten.** Operator bulk exports in R2 (deleted 72 hours after they finish, `EXPORT_TTL_HOURS`) and uploaded import files (deleted 7 days after an import ends) are not edited; neither are copies already written to an operator's export destination (it receives the `deletions/` record), SES's own account-level suppression list, or Stripe's customer record (the publisher's Stripe account).

### Imported people who never confirm

An import without the attestation ("Everyone on this list agreed to receive this publication") adds new people as `pending`; nothing is sent to them. If they never confirm, the jobs worker deletes them `IMPORT_PENDING_DAYS` (30) after the import, unless a confirmation email sent to them is still open (`expirePendingImports` in `workers/jobs/src/handlers/maintenance.ts`, every five minutes, 5,000 a run). It is the same delete as an operator's: a `member.deleted` event, cascading rows, and one `members.pending_imports_deleted` audit entry per Channel and run. Subscribers added any other way are never touched. An attested import records a consent record per new subscriber (`member_consents.source = 'import'`): the attestation's wording, and who attested in `attested_by` (the teammate's id, or `key:<id>` / `oauth:<id>` for `/v2` imports, from `import_jobs.consent_attested_by`).

### Incremental exports

Paid plans (`PLAN_LIMITS.exportDestinations` per workspace) can sync a Channel to their own R2 or S3 bucket (`/api/v1/channels/{id}/export-destinations`, admins and owners). Access keys are sealed by the vault for the destination's row, so a value copied onto another row doesn't open; keys sealed before that still open, and the vault's re-seal moves them to the current format. They are never returned; "test connection" puts and deletes a small object. The jobs worker's five-minute cron runs due destinations (hourly or daily), each object request signed with SigV4 by the vault (`signDestinationRequest`), so jobs never sees the keys, and writes JSON Lines under the prefix: `members/` (changed Members by `updated_at`, then id, with tags and decrypted fields), `events/` (new `member_events` by `seq`) and `deletions/` (`member.deleted`, ids only). Each object is named after the cursor it starts from, so a retried run rewrites the same objects; rows younger than a minute wait for the next run. `cursor_json` is `{members, membersId, events, deletions}`. A failure sets `failing` with the storage API's error and is retried on the next due run; after three failures in a row the workspace's owners and admins get one email. Code: `@swarm/engine` `export-sync.ts`.

### Account security

Passkeys (WebAuthn), TOTP with ten single-use recovery codes, and SSO (OIDC, Pro and up, off by default behind the `sso` flag, with domain capture and just-in-time seats; SAML is not scheduled, ticket SEC-SAML-1 in `docs/security.md`). Passkeys are a second factor, not a passwordless first factor. A first factor creates a session with `mfa_pending = 1` when a second factor is needed: such a session can only reach the second-factor endpoints, sign-out and `GET /api/v1/auth/session`. Owners and admins must use a second factor; `workspaces.require_2fa = 'all'` extends that to every seat. Someone who has none gets a 14-day grace period from when the requirement first applied (`operators.mfa_required_since`, migration `0017_security.sql`), after which their sessions must enrol before anything else. "Sign out everywhere" revokes all of an operator's sessions; a sign-in from a new device emails the operator. Details: `docs/security.md` "Account security (Phase 7)".

### Deliverability Center

The recommended DMARC record carries `rua=mailto:dmarc+<sendingDomainId>@<DMARC_MAIL_DOMAIN>`. The events worker receives reports through Email Routing, unzips or gunzips them, keeps the raw file in R2 `REPORTS` and parses records into `dmarc_reports` and `dmarc_records`. The dashboard shows alignment and failing sources per domain, a per-mailbox-provider breakdown from deliveries, bounces and opens, the complaint rate against Gmail's 0.3% ceiling, and Reputation Ramp history. Paid Channels get their own SES configuration set; Pro and up can request a dedicated IP pool with managed warm-up. Details, limits and what each number means: [deliverability.md](deliverability.md).

- **Reports.** The report domain authorises every sending domain with a wildcard `*._report._dmarc.<DMARC_MAIL_DOMAIN>` record (RFC 7489 §7.1). A report must name the sending domain of the address it came to; bad input is logged and dropped, never rejected. Parsing is bounded (10 MB mail, 5 MB attachment, 25 MB XML, 5 zip entries) and refuses DTDs.
- **Dedicated sending.** A paid Channel's configuration set is created on its first send (or by an admin) and its Broadcasts go through it; a provider error falls back to the shared set rather than blocking the send. Dedicated IPs move `requested` → `warming` → `active`; the send worker's minute cron provisions requested pools and reads warm-up hourly.

Multi-region routing is not built (decision 2026-10-28: EU residency is not a launch requirement). See [data-residency.md](data-residency.md) for where data lives today and what EU residency would take.

### Open Operator

A remote MCP server at `POST /mcp` on the api worker (Streamable HTTP, MCP 2026-07-28 plus the 2025-11-25 and 2025-06-18 handshake, no sessions), authenticated with the `/v2` keys and OAuth tokens. Its tools are derived at runtime from the `/v2` OpenAPI document and run as in-process `/v2` requests through the app's own router (`v2/internal.ts` hands the resolved principal to `authenticateV2`), so scopes, tenancy and validation are the routes' own. Every call is logged in the hash-chained `agent_actions` (all plans); destructive calls are held in `agent_approvals` until an admin approves, which re-checks the credential and runs the stored request once. Engine: `operator.ts` (`runAgentTool`, `approveAgentApproval`) for reuse by other agents. Details: [open-operator.md](open-operator.md).

### Rosters

Several opt-in lists per Channel, behind the `rosters` flag; contract in [rosters.md](rosters.md), tables in `0019_rosters.sql`, logic in `@swarm/engine` `rosters.ts`. A Dispatch audience's optional `rosters` part (included and excluded Rosters plus a conflict policy) compiles into the same predicate as its Circles, so preflight, the snapshot and the count agree and every Member gets one Delivery. One-Click unsubscribe from a Broadcast sent to Rosters leaves those Rosters; the page also offers leaving everything. The engine reads the flag itself (`rostersEnabled`), so the capture, track and events workers apply it the same way the API does.

### Feed Sync

Feeds a Channel follows (`feed_sources`) and the items seen in them (`feed_items`, unique per feed on the GUID hash), in `0020_feed_sync.sql`. The jobs minute cron checks due feeds with conditional GET through the outbound URL guard, stores new items (the first fetch only records the backlog) and releases them as Dispatches within each feed's caps and quiet window: drafts, or Dispatches scheduled for now that the send worker's scheduler starts with the usual checklist. See [feed-sync.md](feed-sync.md).

## API conventions

- `/api/v1` uses a cookie session. `/v2` uses Bearer keys or OAuth access tokens.
- Responses use `{ data }` or `{ error: { code, message, requestId, details? } }`.
- Pagination is an opaque base64url cursor with `limit` up to 100.
- Writes accept `Idempotency-Key` on both APIs (same rules as the `/v2` **Writes** item above): keys belong to the `/v2` key or grant, or on `/api/v1` to the signed-in operator (a response replays only to the session that sent the request, since step-up checks are per session), so a double-submitted dashboard write (a Dispatch send, a form saved twice) replays instead of running again. The dashboard can send one per user action; requests without the header are unaffected.
- Every `/api/v1` operation declares who may call it in `workers/api/src/lib/policy.ts`; see `docs/security.md` (Authorization).
- Timestamps are ISO 8601, and money is integer minor units plus `currency`.
